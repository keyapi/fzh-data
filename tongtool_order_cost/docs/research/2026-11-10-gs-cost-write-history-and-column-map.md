# GS 写回成本列：历史、列用途、BOM 版本

> 结论先说：**不是三套随机数，是三次不同范围的写回 + 两个 BOM 版本叠在一起。**
> 2026-11-10 已完成 **29 列最小修补**（8/9 月 6 个写回 ws，readback 0 差异）；
> 行集合、销售额、运费、商品属性、EN包装、是否皮壳等列**本次未动**。

## 1. 到底写过几次 GS

| 时间 | 动作 | 写入列 | 结果/证据 |
|---|---|---|---|
| 2026-11-06 | 首次 `fill-tables` 写回脚本（`out/_gs_full_write*.py`） | 29 个成本/系数列 | 脚本存在；本地无留存 backup，无法证明执行次数 |
| 2026-11-09 | 拆单合并成本修复后重写 | 同样 29 列 | `out/gs_diff_20261109/summary.csv`：202608 self 20 行 +23,751.83；202609 self 10 行 +12,543.13；FBA 0；merged 同步 |
| 2026-11-10 | **今天：29 列最小修补** | 同样 29 列 | 202608 self 46 行 +1,920.04；202609 self 9 行 +370.55；FBA 只改含/不含；readback 0 |

**关键错误**：三次都只写 29 列，而 `皮壳含包装/不含` 属于这 29 列，`皮壳成本` 也在其中；
2026-11-09 那次把 `皮壳成本` 换成了 1104 BOM 的 53.939，但旧模板里的
`皮壳含包装成本/不含/系数` 仍是 0903/历史值 76.961——同一行两代成本并存。
今天的最小修补就是把这 4 列拉回当前 `皮壳成本`。

`out/merged_202609.csv`（11-04）是**旧 Colab 表**：76.961 / 0 / 64.79 / 8.5，
不是 0903 BOM 的完整口径（0903 的二次加工是 206.479），不要拿它当最终表。

## 2. 两个 BOM 版本（同一 SKU：TT0312614K0064239 / 92×56×75 阅读枕）

| 版本 | 皮壳 | 绍兴二次 | 二次加工 | 头程 | 用途 |
|---|---:|---:|---:|---:|---|
| `EN产品BOM成本列表 20260903` | 76.961 | 0（发货方式=皮壳） | 206.479（美中加工 USTX） | 8.5（皮壳）/0（半成品缺） | **特殊规则参考值 C 的制定基准** |
| 1104 BOM（`bom_cost_product_with_kits.csv`，GS 已更新 1104 版） | 53.939/53.846 | **16.522567**（发货方式=半成品） | **90.306**（USTX valuation） | **33.15** | 11-09 GS 29 列 + 今天最小修补 |
| 11-04 Colab merged（旧表） | 76.961 | 0 | 64.79 | 8.5 | 旧显示口径，不是 0903 完整成本 |

- 0903 BOM 的“皮壳 76.961 + 绍兴 0 + 二次 206.479”与 C 参考值（71.34 / 0 / 116.22）
  同代，所以按 0903 算，参考值是**扣减**（约 −77.8/件）。
- 1104 BOM 的“皮壳 53.939 + 绍兴 16.52 + 二次 90.31 + 头程 33.15”与 C 不同代，
  同一组 C 就反过来变成**增加**（约 +21/件）。
- 这是**版本时间差**，不是规则表或引擎算错；对齐 1104 后重跑 202609，参考值会翻回扣减。

## 3. 列用途地图

### 3.1 引擎/写回负责的 29 列

| 列 | 来源/公式 | 备注 |
|---|---|---|
| 皮壳成本 | 当前 BOM `cost_fg` | 单位成本 |
| 皮壳含包装成本 / 不含包装成本 | **= 皮壳成本**（2026-11-10 起） | 新引擎无独立包装拆分；旧 Colab 的 76.961 不再继承 |
| 两列 `*系数` | 皮壳成本 × 系数 | 同上 |
| 绍兴二次加工成本 | 半成品→`cost_sxbzbcp`；成品→`cost_sxbzcp`；皮壳→0；FBA→`sx_cost_all−cost_fg` | 单位成本 |
| 绍兴二次 `*数量` / `*系数` / `*系数*数量` | 上述 × 数量/系数 | |
| 二次加工成本 | 目的地 `valuation_rate`（USNJ/USTX/PL）；FBA=0；`-Cover` 行=0 | 单位成本 |
| 二次加工 `*数量` / `*系数` / `*系数*数量` | 上述 × 数量/系数 | |
| 头程运费金额 | BOM 头程列（按 method + 价格表）；FBA 按 FBA 头程 | 单位成本 |
| 头程 `*数量` | 上述 × 数量 | |
| 1件产品成本 | 皮壳 + 绍兴二次 + 二次 | 不含头程 |
| 产品成本*数量 | 1件 × 件数 | |
| 订单总成本 | 产品成本*数量 + 头程*数量 + 运费 + 海外仓*数量 | `运费` **不在 29 列内**，见下 |
| 订单利润 | 售价*汇率 − 订单总成本 | |
| 绍兴成本系数 / 二次加工成本系数 / 绍兴二次加工成本系数 | 财务系数；旧写回同键继承，缺失=1 | |
| 各 `*系数` 派生列 | 成本 × 系数 | |

## 5. method 规则（一句话版）

> **定价 method 一律取 BOM 主档 `shipping_method`**（1104 BOM）；
> EN 订单行的 `shipping_method` 只写 `en_method` 审计，不参与定价。
> 仓库（美中主仓 / 退货产品仓 / 皮壳仓库）不改变 method 或成本算法。
> 组件后缀 `-Cover/-Foam/-PPCotton` 同样按 BOM method + 后缀矩阵。

- 202608/202609 实测：EN vs BOM method 仅 **46 / 9 行**不同（全是 EN=皮壳、BOM=半成品），
  其余 10,708 / 6,094 行完全一致；GS 29 列实际金额变化 46 / 9 行
  （+1,920.04 / +370.55）。
- 覆盖行会出现在 `out/build_tabs/<月>/self_method_warehouse_audit.csv`
  （EN_method / BOM_method / 实际计价method / raw vs EN 仓库）。
- 202609 有 468 行 raw `美中-FZH-DANEEY` 但 EN `美中-FZH-DANEEY-退货产品仓`：
  这就是你在 GS 里按 raw 仓库过滤却看到 0/16.52 混用的原因；现在全部按 BOM 半成品。
