# 历史尾程建模用错费用列，导致波兰线预测整体偏低约 30%

## Problem

建模时把 gsheet 的 `包裹总运费` 当作「实际尾程成本」，但该列口径并不稳定。
用错列使训练目标整体偏移，波兰线的费率层被系统性压低约 30%，
而该错误不会在「训练集 vs 验证集」内部一致性检查里暴露——两侧用的是同一个错列。

## Symptoms

- 波兰仓 × GLS-PL 渠道预测中位 96.00，实际 124.31（2026-05），偏差 −19.56
- 逐包裹比对两个数据来源：US 一致率 65.1%、DE 42.3%、FR 40.0%、CH 20.8%
- 分渠道看「模型只对了一半」：美国线偏高、欧洲线偏低，方向还相反

## What Didn't Work

- **按「哪个列有正值」选列**：早期统计发现 2025-12 起 `包裹总运费` 正值最多，
  于是把它排在第一优先级。但「正值多」不等于「语义对」——该列在同一包裹上
  有时等于 `物流商运费`、有时等于 `通途运费`。
- **只看分位数是否合理**：`包裹总运费` 的中位数（106.96）与真实费用分布很接近，
  单看统计量完全看不出问题。
- **认为是「月份口径切换」**：一度以为 2025-11 用 `物流商运费`、之后切到 `包裹总运费`，
  其实 `物流商运费` 一直是真值，只是 11 月以外它被月初的占位值污染过。

## Solution

把费用列优先级固定为 **`物流商运费` → `包裹总运费` → `通途运费`**，
并在注释里写清每列语义：

```python
# `物流商运费` 是实际回传的承运商扣款（月初先是预估占位，之后被真实费用替换），
# 是唯一可信的建模目标。`包裹总运费` 口径不稳，只能兜底；
# `通途运费` 是通途自己的阶梯预估，最后兜底。
for column in ("物流商运费", "包裹总运费", "通途运费"):
    use = (fee_source == "") & (package_meta[column] > 0)
    observed_fee = observed_fee.mask(use, package_meta[column])
    fee_source = fee_source.mask(use, column)
```

判据（用真实包裹逐列核对得出）：

| 包裹号 | `物流商运费` | `包裹总运费` | `通途运费` |
|--------|------|------|------|
| P80810125 | **126.17**（与通途系统一致） | 52.88 | 52.88 |
| P80810098 | **123.03** | 47.22 | 47.22 |
| P80726438 | **124.31** | 124.31 | 52.11 |
| P80726322 | **62.64** | 62.64 | 46.52 |

同时确认了月初工作流的机制：月初把预估先写进 `物流商运费` 占位，
之后由财务同事上传的真实费用替换——这解释了「未加预估 → 已加预估」的差异
**恰好只出现在 `物流商运费` 一列**（2,143 行）。

## Why This Works

`物流商运费` 是唯一与外部系统（通途）能对上的列，因此它承载的是真实扣款；
`包裹总运费` 是一个语义漂移的遗留列。选定正确列后：

| | 用错列 | 用对列 |
|---|---|---|
| 严格时间 Holdout MAE | 20.30 | **17.96** |
| Holdout 偏差 | +4.21 | **−1.61** |
| 月初工件 202605 偏差 | +11.88 | −2.67 |

先前报出的「时间外系统性高估 +4.21」「6 月偏差 +9.25」**都是这一列造成的假象**，
换列后 6 月偏差为 +0.02。

## Prevention

- **每个数值列都要有口径断言**：用可追溯到外部系统的少数样本（本例 4 个包裹号）
  逐列核对，把结论写进代码注释与该列的取值优先级。
- **不要用「正值比例/分位数」代替语义确认**——它能筛掉空列，但筛不掉错列。
- **区分「缺失」与「口径错」**：先问「这一列到底代表什么」，再问「有没有值」。
- 本模块的字段用例见 `docs/reference/`（如已补充）与
  `docs/research/2026-09-11-history-last-leg-field-profiling.md` 第 4 节（含更正说明）。
