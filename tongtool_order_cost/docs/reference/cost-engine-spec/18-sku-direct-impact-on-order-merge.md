# 改用「通途SKU 直连」对订单合并/拆分/去重的影响

> 背景见 [16-customer-sku-direct-path.md](16-customer-sku-direct-path.md)（`通途SKU → 客户物料号 → 美中加工成本, USTX`，
> 7 月美中 4372/4379 = 99.8%）。本页只回答一个问题：**换成 SKU 直连后，订单的「合并 / 拆分 / 去重」会不会垮**。
>
> 口径：代码只说「怎么写的」；数据来自本机只读快照
> `tongtool_order_cost/out/profitability_audit/2026年7月订单_ustx2/`（7 月非 FBA `writeback/` + FBA 合并 `writeback_combined/` + `en_bom_cost/`），
> cell 定位对应 10/10 notebook 备份。**未证实项一律标「未证实」，不猜。**

## 结论摘要

1. **合并/拆分逻辑本身不按 `品类尺寸面料编码` 分组，也不按 `通途SKU` 分组**——它按**订单号公共部分 + 平台SKU(统一)** 分，用 `通途SKU` 只做「组内是否多值」的判据（`nunique>1`）。
   所以**换键不会改变"哪些行被合并"**（分组不变）。
2. **但合并的"存留行"取值是 `first`**（cell_077 / cell_090）：合并后那一行留下的是**组内第一条**的 `品类尺寸面料编码` **和** `通途SKU`。
   现键（`品类尺寸面料编码`）在同一产品的多包裹（皮壳/海绵/成品）上**通常同值** → `first` 稳定；
   **换成 `通途SKU` 后各包裹 SKU 不同 → 存留键 = "碰巧排第一的那个包裹"**，键的身份从"产品级"降为"包裹级"。这是本次评估的**核心风险点**。
3. **有 3 处确凿的「合并/拆包」逻辑依赖产品名称解析的产物 `品类`**：`cell_072 add_package_suffix`（`品类==['松饼大沙发-放大版']`）、
   `cell_071 normalize_sku`（`产品名称.startswith('松饼大沙发-放大版')`）、`cell_094`（已注释，`品类=='麻将沙发衍生款'`）。
   这三处**是"靠名字认松饼沙发"**，不是靠 SKU。若解析下线，需改锚点。
4. **`通途SKU` 在"稳定性/可对 EN"上整体优于名称解析**：7 月实测 **825 个 SKU 中仅 1 个**（`TT0031179K0063904-Cover`）
   映射到 **2 个** `品类尺寸面料编码`（同订单同产品名，因渠道不同被解析成 弧形海绵 / 弧形PP棉）；反向 `品类尺寸面料编码 → 通途SKU`
   则有 **149/332 个键**各对应多个 SKU（最多 13 个）。**方向性明确：SKU 更细、更稳；名称键会"一 SKU 多键"。**
5. **但有实测反例（不是假想）**：EN `importBOMCostList` 里 **6 个 `LM-HS-001` 族 SKU**（如 `TT0031177K0063900-Cover`）
   **同时登记在 `KS0342`（弧形海绵）与 `KS0340`（弧形PP棉）两行，`美中加工成本, USTX` 分别 = `0` 与 `85.75843`**。
   即 **`通途SKU` 直连在"弧形海绵 vs 弧形PP棉"这一处天然有歧义**——而这恰是 [16](16-customer-sku-direct-path.md) §1.3 那 23 行不一致的根因。
   → 直连**必须做"一物多行"断言**（EN 侧 `客户物料号` 字面重复且 USTX 不同 = **5 个**；含 `删除` 前缀 **115 行**，需清洗）。
6. **`-N` 数字后缀语义不统一**：`TT…-<数字>` 是**拆单/包裹/补发序号**；非 TT SKU（`BN…/CEN…`）的 `-<数字>` 是**尺寸**。
   若为"合并"而写"剥掉 `-N` 尾缀"的通用规则，会把不同尺寸混为一谈（本次实测误剥后一度虚增出 99 组"成本不一致"）。
   **不能对非 TT SKU 剥数字尾缀。**

> **一句话**：换 SKU 直连**不破坏合并/拆分的分组**，但会**把合并行的成本键从"产品级"变成"包裹级"**，并暴露 EN 侧 `LM-HS-001` 族的
> `通途SKU` 歧义；**合并主链本身可以承受**（因为沙发族的各变体在 EN 里同价），**但必须补两条断言 + 保留 `品类` 供 3 处拆包逻辑用**。

## 是否依赖产品名称解析

| 逻辑 | 依赖 `品类/尺寸/面料`？ | 证据 |
|---|---|---|
| A 合并**分组** | ❌ 不依赖（键 = 订单号公共部分 + 平台SKU_统一） | cell_072/075/077 |
| A 合并**存留值** | ⚠️ **间接受影响**：`品类尺寸面料编码` 是 `first` 取到的；换成 SKU 后存留键变成包裹级 | cell_077 |
| A **拆包裹标记** | ✅ **直接依赖** `品类`（`松饼大沙发-放大版`）与 `产品名称`（含 皮壳/海绵块/纸箱） | cell_072 |
| A **SKU 归一化** | ✅ **直接依赖** `产品名称.startswith('松饼大沙发-放大版')` | cell_071/072 |
| B TikTok 合并 | ❌ 不依赖（已用 通途SKU / 电话 / 订单备注） | cell_082/083/089 |
| C FBA 拆行 | ❌ 不依赖（MSKU + 站点） | cell_138 |
| D 成本表去重 + 并入订单 | ✅ 全部以 `品类尺寸面料编码` 为键 | cell_036/043/102/106/108/125 |
| 品类白名单清零 / `mask_cost_fillna_zero` | ✅ 读 `品类` / `产品名称`（与合并无关，但同属"名称解析的下游"） | cell_125 |

**小结**：
- **"哪些行被合并"** → 不依赖名称解析（可以安全换键）。
- **"拆包裹标记 / 松饼 SKU 归一化"** → **依赖 `品类`/`产品名称`**；SKU 直连**不能**替掉它们（SKU 没有"这是松饼沙发"这个语义）。
- **"成本落到哪一行"** → 依赖 `品类尺寸面料编码`（cell_102/106/125），换键后需重新定 `first` 取哪个 SKU。

## 通途SKU 作为合并键的优劣

**优点**
1. **更稳**：7 月 825 SKU 中仅 **1 个**跨 2 个 `品类尺寸面料编码`；反向有 **149/332** 个键跨多 SKU → SKU 是更细、更确定的键。
2. **可直接对 EN**：`通途SKU → 客户物料号` 原样命中 **801/825**，去 `-Cover` 尾再命中 **6**（共 807），仅 **18 未命中**（多为 `Buttonkit`/`T238…`/`TT…-zuhe-all` 等非标准 SKU）。见 [16](16-customer-sku-direct-path.md)。
3. **已被现有系统采用**：TikTok 合并（cell_082/083/089）与本地 1.7.0 `DUP_COLS` 都以 通途SKU 为键。
4. **绕开尺寸档归并**：名称解析要把 `135→?`、`138→140` 等做经验归并；EN `客户物料号` 直接带尺寸（如 `…-135x152x80-…`），无此跳。

**缺点 / 反例**
1. **`LM-HS-001` 族（弧形海绵 vs 弧形PP棉）歧义**：**6 个 SKU** 在 EN 同时挂 `KS0342`(海绵, USTX=0) 与 `KS0340`(PP棉, USTX=85.75843)。
   名称解析路径**也**分不清（同一个 `TT0031179K0063904-Cover` 在 亚马逊/Wayfair 被解析成两个不同 `品类`），但两者是**不同的"分不清"**：名称键是"同 SKU 出两键"，SKU 直连是"一键指向两价"。
2. **`客户物料号` 字面重复**：EN 侧 `客户物料号` 有 **5 个字面值**（多行）对应**不同** `USTX`（如 `TT0031177K0063900-Cover`）。
   → 建表**必须断言唯一**，多值判歧义（[16](16-customer-sku-direct-path.md) §4 Q3）。
3. **脏值**：`客户物料号` 含 `删除`/`已删除` 前缀 **115 行**、含空格 **31 行**、含 `#` **38 行**（多为非 TT 的 FBA 别名）。
   → 归一化规则要显式、且**只对 TT 族**剥后缀。
4. **SKU 改名 / 带 `-Cover` `-Foam` 尾缀**：[16](16-customer-sku-direct-path.md) §4 Q4 已标"换客户/换登记口径会漂"——**未证实**当前是否稳定。
5. **非 TT SKU 的 `-N` 是尺寸不是序号**（见下节反例）。

## 迁移风险与反例

| # | 风险 | 证据（7 月实测） | 严重度 |
|---|---|---|---|
| R1 | **合并行成本键由"产品级"降为"包裹级"** | cell_077 `first` 同时取 `通途SKU` 与 `品类尺寸面料编码`；沙发族各变体（`TT0031245K0064084/-Cover/-Foam/-2/-3`）在 EN **同价 208.775**，故当前无害；但一旦某产品 皮壳 SKU 与 成品 SKU 登记价不同，合并行的成本就会随"谁是第一条"漂移 | **中**（当前未观察到，机制存在） |
| R2 | **弧形族歧义被直连带出来** | 6 个 TT SKU 在 EN 一键两价（0 vs 85.75843） | **中-高**（`LM-HS-001` 有实际订单行） |
| R3 | **拆包裹标记失去依据** | cell_072 靠 `品类=='松饼大沙发-放大版'`；若解析下线，包裹 1/2/3 不会被打上 → 合并（cell_075 `包含包裹`）**静默失效** | **高**（会导致沙发订单多行不合并 → 运费/售价不累加） |
| R4 | **`-N` 尾缀语义不统一** | TT `-2/-3` = 序号；`BNUSFBA-Velvet-Black-138/-153/-194` 的 `-138/-153/-194` = **尺寸**（对应 `KS0001-HLR-140/153/194`）。若为合并而通用剥 `-N`，会把不同尺寸并成一个 | **中**（写规则时的陷阱） |
| R5 | **`是否皮壳` 与合并语义耦合** | cell_078 合并后清空 `是否皮壳` → 当成品；若改用 SKU 键且"第一条"是皮壳 SKU，取到的若是皮壳口径成本则不符 | **低-中**（沙发族同价，暂无实证） |
| R6 | **7 月仅 12 行合并** | `已合并多行` 12/9579 行；样本小，**"合并无副作用"的结论强度有限** | **提示**（非缺陷） |

> R6 说明：合并是**低频但高影响**的路径——12 行里任何一行算错，订单总成本/利润就错。**不能用"行数少"当作"可以不测"的理由。**

## 建议

1. **不要为"换键"动合并分组逻辑**（cell_072/075/077/090）。分组键 `订单号_公共部分 + 平台SKU_统一` 与成本键无关，**保持原样**。
2. **`品类` / `产品名称` 至少保留到合并步之后**：拆包裹标记（cell_072）与松饼 SKU 归一化（cell_071）需要它们。
   若确实要下线名称解析，**先把这两处改成 SKU 前缀锚点**（如 `通途SKU` 前缀白名单），并单独验证。
3. **建 SKU 直连表时做两条断言**（对齐 [16](16-customer-sku-direct-path.md) §4）：
   - `客户物料号`（去 `删除` 前缀、**仅 TT 族**剥 `-Cover`/`-Foam`）**唯一**；多值 → 判 `ambiguous_customer_sku`，**不取首/末**。
   - 命中率与"未命中 18 个 SKU"逐条留痕（[AGENTS.md](../../../../AGENTS.md) 的「未匹配记录必须保留」）。
4. **对 `LM-HS-001` 族（弧形海绵/PP棉）走人工/业务裁决**，或**保留"名称解析"作为该族的补充判据**（名称键在亚马逊/Wayfair 上反而分了岔）。这是**唯一已证实的"SKU 不如名称键"之处**。
5. **合并行 `first` 取值要加断言**：建表后校验「同一 `订单号_公共部分` 组内各包裹 SKU 解析出的成本是否一致」；不一致则告警（当前沙发族一致，但机制上不保证）。
6. **不要对非 TT SKU 剥数字尾缀**；把"剥 `-N`"限定在 TT 族且**记录被剥的 SKU 清单**。
7. 相关联动：本页与 [16](16-customer-sku-direct-path.md)、[11](11-plan-new-ustx-processing-table.md)（建表骨架）、[08](08-special-cases.md)（`-COVER`/`-FOAM`/拆单/Product Bundle）同改。

## 未证实

1. **EN `客户物料号` 对"订单侧 通途SKU"的登记是否长期稳定**（换客户 / 换登记口径是否会漂）——[16](16-customer-sku-direct-path.md) §4 Q4 已列，本页未新增证据。
2. **沙发族"各变体同价"是否普遍**：仅实测 `KS0394`(松饼大沙发)、`KS0390`(圆沙发)两族同价；**未**逐族验证。
