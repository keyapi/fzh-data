## 0. 一句话

**「通途SKU → 客户物料号」作为「身份解析的候选路径」有价值，值得优先验证；
但 [16](16-customer-sku-direct-path.md) 的「更准、严格占优、零损失、四类问题消失」——全部不予通过。**

## 1. ⚠️ 我犯的方法错误（必须自己认）

**我的比较脚本对每个 `客户物料号` 取 `USTX` 的 `max`** —— 这**掩盖了多候选**。
而这正是我在别处反复批评的反模式（「按模板取 max 会抹平差异」「不能取首/末值」）。**我用它得出了错误结论。**

**自证反例**（冻结 BOM 物理行 758 / 3142）：**同一个完整码** `TT0031187K0063920-Cover` 同时指向：

| 父件 | 填充 | 发货方式 | USTX |
|---|---|---|---:|
| `KS0340-DM-50-IVORY` | **PP棉** | 皮壳 | **85.75843**（有 active 默认 BOM，PP棉 qty=1.7） |
| `KS0342-DM-50-IVORY` | **海绵** | 成品 | **0**（**无 active 默认 BOM** → 报表回退 `valuation_rate` = 0） |

→ 它**本来就是多候选冲突**；我取 max 得到 85.75843，**是掩盖冲突，不是消歧**。
→ 我在 [16](16-customer-sku-direct-path.md) §1.3 拿它当「件级更准」的正面样例，**是错的**。

## 2. 覆盖率：定义更正（**不是争一位百分数**）

| 规则 | 有数值候选 | **产品与数值唯一** | 多产品/多值歧义 | 无候选 |
|---|---:|---:|---:|---:|
| 完整 SKU 精确匹配 | 4370 | 4367 | **3** | 9 |
| 先精确；无匹配才去末尾 `-Cover` 再查 | 4372 | **4369** | **3** | 7 |

- **99.77% 与我的 99.8% 是同一个数**；**关键更正是「覆盖定义」与「3 行歧义」**，不是百分数。
- 「4372」是**候选命中数**，**不等于「可唯一可靠取成本」**；阻断歧义后唯一数为 **4369**。
- 去尾 `-Cover` 只应作为**待验证别名**（本期救回 2 行：物理 164 / 413），**不能从一次数值命中推广为「普遍可去尾」**。
- 全订单 **825** 个 SKU / USTX **329** 个 SKU；801/825 是**全订单** SKU 的交集，**不是 USTX 覆盖率**（我原文表述易误读）。
- 大小写：EN 侧 Python 精确去重 3480 vs DB `COUNT(DISTINCT)` 3478（45/60cm 的 `CM/cm` 变体）→ **SQL 与 Python 去重口径需明确**。

## 5. 「0」的来源（我原表述不准）

| 件 | 事实 |
|---|---|
| PP（`KS0340`） | **有** active 默认 BOM，`total_cost` = 85.75843 |
| 海绵（`KS0342`） | **无** active 默认 BOM → 报表 `get_item_valuation_rate` **回退 `valuation_rate`** = 0 |

→ **「0」来自「无 BOM 估值回退」，不是「BOM 已算出加工费为 0」**。
→ `zero_literal` 应保留，但**必须增加「成本来源状态」**（有效 BOM 成本 / 估值回退 / 缺 BOM 回退 0 / disabled / 无成本源），**不能把所有原始 0 自动批准**。

## 6. 历史可回算性：**未证实**

- **最小反例**：五件套客户行当前 `creation=2026-05-21`，但 **Version `tpupqneo9v` 明确在 `2026-08-11 17:39:21` added customer_items**（`ref_code=TT0031102-zuhe-all`）。
  → **按 `child.creation <= 7月` 过滤，会把 8 月新增误放回 7 月。**
- `Item.track_changes=1` 但 `Item Customer Detail.track_changes=0`；**父 Item 的 Version 只记录部分子表增删**。
- 抽查 PP/海绵两父件共 29 条 Version，**客户码重复登记的新增事件早在 2025-12 已发生**。
- **结论**：9/3 快照可复现「9/3 导出对 7 月订单的重估」，**不能冒充 7 月当时登记与成本**。要承诺历史回算，必须冻结/恢复当月映射、客户码别名、套件构成、仓库费用规则、成本源/BOM/估值/工资率。

## 7. 客户维度与漂移

- `Item Customer Detail` 确有 `customer_name`/`customer_group`，但**4234 行中只有 4 行 `customer_name` 非空**，多数按 `customer_group`（美国公司/欧洲公司）登记。
- **生产校验 `validate_item_ref_code`（`work_order_task/doc_events.py:426–505`，由 `hooks.py:242–245` 调用）查询其它 parent 时**不加客户/客户组过滤** → 意图是**跨产品全局唯一**；但 `ref_code` **无 DB 唯一约束**。
- 同一函数 `480–482`：当前 ref_code 集合与既有集合相同时**直接返回** → **旧的跨产品重复可继续存在**。
- **「增加客户组键也消不了那个反例」**（`TT0031187…Cover` 两个 parent 都各有美国公司/欧洲公司登记）。
- `TT0031187…Cover` 两 parent 的 `customer_name`/`special_mark` 空、分摊系数 0。
- **「随 EN 自动更新」同时也是「历史重跑会漂」的机制。**

## 9. Codex 的**可落地修订方案**（我接受，作为下一步的规范）

1. **把直连限定为「身份解析候选」**：保留完整 SKU、命中的原始 `ref_code`、唯一 Item、**全部候选 parent**、命中方式（精确/显式别名）。**精确多候选立即阻断，不得转基码消歧，不得取 max/首值。**
2. **成本选择另做一层**：按仓库、真实交付形态、Product Bundle/拆包关系、获准费用规则选成本；**保留「实际身份」与「历史成本代理」两列**，不因身份更精确就默默换费用政策。
3. **0 与异常分开**：保留「有效 BOM 成本 / 估值回退 / 缺 BOM 回退 0 / disabled / 无成本源 / 客户码歧义 / 别名待确认 / 套件待展开 / 明确业务豁免」；**原始数值 0 与批准的零成本是两个字段**。
4. **固定计算版本**：当前重估与历史复原**分别命名**，每次产出冻结（原始 SKU / resolved Item / 映射快照日期 / 别名规则版本 / 成本来源与值 / 仓库规则 / 行身份）。**不能用一列不断更新的当前值承担历史复原承诺。**
5. **先做离线证据表**（本轮已交付 4379 行状态、7 未命中、7 重复码全部候选、17 差异）：先修登记冲突与明确别名、业务确认剩余语义，**再**对拍 8/9 月——**不要求先建 3315 行新表**才能验证方向。
6. **保留隔离与歧义阻断**（见 §8）。
