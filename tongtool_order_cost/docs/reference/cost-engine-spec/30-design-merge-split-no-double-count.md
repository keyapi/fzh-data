# 拆包裹/合并 → 合成一件成品再对 BOM（设计稿）

> 目标：订单里「一件成品被拆成多个包裹（皮壳 / 海绵 / 成品）记成多行」时，**先合成一件**再对 BOM 成本，做到**不重不漏**（成本既不重复计、也不漏计）。与 [18](18-sku-direct-impact-on-order-merge.md)（影响评估）配套；本页给**算法与落点**。

## 1. 落点判断（三处，各司其职）

| 层 | 现状 | 本设计的态度 |
|---|---|---|
| **Colab**（`cell_070–092`/`138/148`） | **生产**：按 `订单号_公共部分 + 平台SKU(统一)` 分组、条件 `产品名含"包裹"`、聚合**存留取 `first`**；`cell_078` 合并行一律当"成品" | **不改**（走 guard/审批）；本设计给它一份**对拍基准** |
| **EN `Tongtool Order`** | **权威源**：原始单 + 拆分子单都在；`order_items` 带 `erp_item_code / quantity / shipping_method / split_package_cost_factor` | **本设计的输入源**（doc 18 §7 已实测） |
| **离线引擎 `ustx_cost_compare.py`** | 现役：逐行 A/B1/B2，**不合并** | **本设计的落点**（read-only、可测、不动生产） |

> 一句话：**先在离线引擎里把"合并"做对并可验证**，再由它对 Colab 提改法。

## 2. 算法（不重不漏）

**输入**：订单行（写回 `写回{月}订单`）＋ 可选 EN `Tongtool Order`（原始单/子单，取 `order_items`）。

**A. 分组（"哪些行是同一件成品"）**
- 兜底键 = **`订单号_公共部分` + `平台SKU(统一)`**（与 Colab 一致，保证与现状可比）。
- 若按 `通途SKU` 反查 EN `ref_code` **同一 EN 产品** ⇒ 同成品（doc 18 §判据③：**同 ⇒ 合并、不同 ⇒ 不合并**）。
  → 两法**取交集**：既满足结构分组、又满足 EN 同产品，才算"该合并"（防误并）。

**B. 聚合（合成一件）**
- **累加类**：`售价/售价*汇率(人民币)/运费/发货数量` → `sum`（与 Colab `cell_077` 同口径）。
- **身份类**：`品类尺寸面料编码 / 通途SKU / 产品名称` → **不取 `first`**（Colab 旧法的风险点，doc 18 §结论2）。改为：
  - `通途SKU` = 组内**全部** SKU 的集合（存起来供成本取值/血缘）；
  - **成本键（`品类尺寸面料编码`）= 用"成品那一行"的**（见 C）。
- **件数**：= **Σ(皮壳行 `发货数量`)**（doc 18 / `tongtu-order-suffix-and-merge-criteria` 的判据；**不是 max、不是首行**）。

**C. "哪一行是成品"**
- 优先 **EN `shipping_method` / `custom_shipment_type_to_branch`** 定交付形态；
- 无 EN 时回落 Colab 旧法（`是否皮壳=='皮壳'` → 按成品处理）。
- **成品行的成本键** 才对 BOM。**非成品行（皮壳/海绵）不再各自对 BOM** ⇒ **这是"不重"的关键**。

**D. 不重不漏的断言（写成闸门）**
1. **守恒**：`Σ(合并前行的 售价/运费/数量) == Σ(合并后行的 售价/运费/数量)`（逐列、逐组）。
2. **件数守恒**：`Σ(合并后件数) == Σ(皮壳行数量)`（无皮壳组单列，不静默补）。
3. **键不退化**：合并后的 `品类尺寸面料编码` **必须** ∈ 组内原键集合（**禁止 string 拼接**）。
4. **成本不重**：同组**只有成品行**进 BOM 成本；皮壳/海绵行成本 = 0（或按口径并入成品行）。
5. **歧义即阻断**：组内无法唯一确定成品行 / 成本键多候选 → **阻断**（不取 first/max），与 [20](20-codex-round3-corrections.md) §9.1 一致。

## 3. 与 Colab 现状的差异（改了什么、为什么）

| 点 | Colab 现状 | 本设计 |
|---|---|---|
| 合并触发 | `产品名含"包裹"`（靠命名，不保证贯彻） | **结构分组 ∩ EN 同产品**（不靠名字） |
| 存留键 | `通途SKU/品类尺寸面料编码 = first` | **成品行的键**；全小组 SKU 留血缘 |
| 件数 | 未明确（多件/多包裹混） | **Σ(皮壳行数量)** |
| 成本 | 合并行一律当成品 → 取"含包装"三项 | **只有成品行对 BOM**；其余置 0/并入 |

## 4. 待拍板（沿用 [18](18-sku-direct-impact-on-order-merge.md) Q1–Q7，挑最卡的）

- **Q：非成品行（皮壳/海绵）的成本怎么处理？** 置 0 并入成品行，还是单列？→ 影响"不重不漏"的定义。
- **Q：EN `Tongtool Order` 缺失子单时**（doc 18 §待拍板5：25 组查不到裸原单）→ 只能子单口径，是否接受。
- **Q：共享内胆**（海绵只登记在一个颜色下）→ 是否做"同底号+部件角色"的宽松配对（默认**不做**）。
- **Q：`first` 的历史包袱** → 改成"成品行键"会让**历史月不可直接回算**，是否只在**新口径**生效。

## 5. 实施步骤（本设计的执行顺序）

1. `ustx_cost_compare.py` 加 `merge_split_orders(rows, *, en_orders=None) -> (merged_rows, audit)`（纯函数）+ 上面的 5 条断言各一个测试。
2. CLI `ustx-compare` 加 `--merge-split`（默认关，便于 A/B）。
3. **A/B 对拍**：合并前 vs 合并后，逐项比 `Σ售价/运费/数量`（断言1）与 B2 成本总额（看"重复计"是否被消掉）。
4. 用 7 月快照跑，产出「重复计了多少」的量化，交给 Codex 评（并入 [29](29-review-brief-for-codex.md)）。
5. 通过后再谈是否把同一逻辑回灌 Colab（另开）。
