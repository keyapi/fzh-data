# 通途有库存 SKU 三方主线补齐复盘

## 目的和不变量

这项工作处理的不是“把编号凑到某个表里”，而是建立销售订单、库存同步和商品维护共同依赖的主索引：每个有库存的通途 SKU 都必须能定位到 EN 的产品成品变体，再定位到赛狐的产品 SKU。

1. 通途完整 SKU 必须存在于至少一个 EN KS 产品变体的 customer_items.ref_code。
2. EN 目标是产品成品变体，不是 PK# 皮壳或 HM1510 海绵。销售订单 Excel 先用通途 SKU 找产品，再用“皮壳/成品/半成品”列决定交付形态。
3. 赛狐对象是该 EN 产品的 item_code，不为通途 -Cover 或 -Foam 原码、PK#、HM1510 单独创建商品。
4. 既有一个通途码挂到多个产品变体的历史关系可以保留并报告；本主线不清理。
5. 套件、已知非产品项、主体骨架以及配套物料上的历史客户码不因主线审计被写入、迁移或删除。

这些边界优先于“看上去相似”的字符串匹配。它们是弱模型最容易误改的部分，也是继续演进库存同步前必须守住的约束。

## 为什么旧审计会漏报

最初的排查脚本沿用了某些简化路径：它会去掉 -Cover 或 -Foam 后缀，再把基码与 EN 客户码匹配；BOM 成本列表还可能只展示一个客户码。这会把“基码恰好存在”误判为“完整半成品 SKU 已登记”。结果是皮壳和海绵的风险被静默压低，而真实完整码可能根本不能被销售订单导入识别。

修复后的主线采用两层匹配。第一层只以小写归一后的**完整通途 SKU**匹配从 EN 产品 Item 回读的全部 customer_items.ref_code。第二层才用去 -Cover/-Foam 的基码寻找候选产品，并明确标记为“仅基码匹配”，绝不计作已登记。EN 侧的回读范围也限定为产品成品变体，因此配套物料上的客户码不能制造假阳性。

另一个数据源陷阱是 BOM Cost List 的筛选条件。重建报表时必须包含：

python
{
    "item_group": "产品",
    "show_disabled": 1,
    "show_ref_code": 1,
    "sum_columns_at_end": 1,
    "pllc_sfg_missing_use_cover": 0,
    "simplified_column_view": 0,
}


缺少 show_disabled 会漏掉禁用但仍需核对的产品；缺少 sum_columns_at_end 会改变列序；而 show_ref_code 不能替代逐 Item 回读，因为报表行不保证完整呈现子表。

## 本轮实施路径

1. 重新导出 EN BOM Cost List，并保留来源时间戳。
2. 拉取通途有库存 SKU、EN 产品 Item 及全部 customer_items、赛狐 SPU/SKU。
3. 用 audit_three_systems.py 分类每条通途 SKU：已精确登记、仅基码匹配、真正未登记、候选不唯一或暂缓。不得静默丢行。
4. 对真正未登记的完整半成品码，先用基码、产品属性、产品族和已有关系形成候选。候选不唯一时停止并报告。
5. 仅对候选已确认的产品执行 register_product_customer_codes.py --apply。脚本默认 dry-run，写入前检查目标是 KS 产品并检查客户码占用；写入后从产品 Item 回读逐条验证。
6. 以映射后的 EN item_code 查询赛狐，而不是搜索通途 -Cover/-Foam。赛狐属性缺失时先生成属性导入 Excel，由用户导入确认；OpenAPI 不能创建属性簇或属性值。
7. 用 build_mainline_report.mjs 生成面向业务复核的工作簿，并让每条输入 SKU 都落入一个明确分类。

本轮唯一需要生产写入的三条完整皮壳码是：

| 通途完整 SKU | 登记到 EN 产品 | 结果 |
|---|---|---|
| C/Linen-Coffee-194-661-WOW-Cover | KS0001-CMM-194-COFFEE | 已回读验证 |
| C/Linen-Natural-183-688-wow-Cover | KS0001-XMMBS-183-HEMPNATURAL | 已回读验证 |
| TT0000750K0063009-Cover | KS0002-DL-100-BLACK | 已回读验证 |

写入后重新拉数得到：1411 个有库存通途 SKU = 1397 个精确登记到 EN 产品 + 14 个明确暂缓项。14 个暂缓项由 2 个套件和 12 个已知非产品项组成。108 条皮壳 SKU 与 25 条海绵 SKU 均已精确登记，且其映射的 EN 产品 SKU 在赛狐回读中全部存在。

## 讨论与设计时间线

1. 初始范围：用户指出 29 个 SKU 是“赛狐有 SPU 但缺 SKU”；另有 12 个 SPU 对应 20 多个 EN 产品编号。设计原则与 EN 一致：属性簇 → 属性值 → SPU → SKU 组合，目标是“不重不漏”。
2. 赛狐属性 API 调研：OpenAPI 可读 SPU、属性和 SKU，也可创建产品 SKU，但没有创建属性簇/属性值的端点。工作顺序固定为：生成属性导入 Excel → 用户导入确认 → API 创建 SKU → 列表回读。
3. 属性集完整性纠错：`KS0013-HLR-80`（无颜色）被错误创建，用户删除；根因是 KS0013 模板历史缺颜色属性。审计 2026-08-10 全部新增物料后确认只有 KS0013 受影响；正确对象为 `KS0013-HLR-80-COFFEE`。规则：产品有颜色就必有颜色属性，目标产品族缺属性先补再建。
4. 编号命名纠错：KS0018 石头 12 个单石曾使用中文颜色值（浅灰1号等），违反 abbr 约定且赛狐 SKU 只接受英文。REST 不能改 `item_code`，最终通过 SSH `frappe.rename_doc` 批量改为 `LIGHTGREY1..6` / `DARKGREY1..6`，并恢复启用、ItemPrice 和客户码。
5. 赛狐状态边界：用户明确禁止把有库存 SKU 改成停售；EN 禁用只表示不生产，赛狐在售状态由业务单独管理。
6. 主线审计修正：早期报告误报皮壳 23 条、海绵 20 条未登记。修正为完整码精确匹配 + EN Item 完整 `customer_items` 回读后，真正缺口只有 3 条 `-Cover`；补登后全部归零。
7. 最终工作簿迭代：artifact-tool 渲染返回非零但文件已成功生成，要检查文件本身而不是只信退出码；文件名时间戳原用 UTC 显示为凌晨，改用 `Asia/Shanghai`；明细补充“分类、匹配依据、建议动作”三列。
8. 只读调查边界：PK#/HM1510 的客户码调查在主线归零后执行，不迁移、不删除；结果只作为后续数据治理输入。

回归要点：10 条拉链款弧形靠枕 `-Cover` 全部应显示已精确登记，已有多挂关系完整保留；`Curve-Pillow-50-Foam` 应显示已精确登记到既有 `KS0342` 产品，不再误报未登记。

## 执行中问题与解决

| 问题 | 决策 | 结果 |
|---|---|---|
| 29 个 SKU 被误当成普通缺失商品 | 先区分“赛狐有 SPU 但缺 SKU”与“SPU 本身缺失” | 按 EN 产品 `item_code` 逐个核验，不再按 SPU 数量代替 SKU 数量 |
| 12 个 SPU 对应 20 多个 EN 产品编号 | 创建对象是 EN 产品变体，不是 SPU | 以完整 `item_code`/`item_name`/属性创建并回读 |
| 赛狐后台 KS0019 看不到宣称新增的 SKU | 不信任“请求成功”，先验证再继续 | 从赛狐列表 API 回读，缺口未归零前不报告成功 |
| 赛狐属性缺失 | 先做属性管理 Excel 导入 | 用户导入确认后再 API 创建 SKU |
| 旧审计误报皮壳/海绵缺口 | 完整码精确匹配，基码仅作候选 | 真正缺口 3 条，补登后主线归零 |
| artifact-tool 非零退出 | 检查生成的 xlsx/PNG 和结构 | 文件正常，删除 `.inspect.ndjson` 临时文件 |
| 工作簿时间戳显示为凌晨 | 文件名使用本地时区 | 改用 `Asia/Shanghai` 时间戳 |
| 想把 EN 禁用同步为赛狐停售 | 两系统语义不同，停止该操作 | 不修改既有赛狐在售状态 |
| 石头中文颜色编号 | 用 SSH `frappe.rename_doc` 批量重命名 | 12 个编号改为英文 abbr，BOM 引用自动更新 |
| 一个通途码挂多个产品 | 历史共用关系先保留 | 输出一对多历史关系页，不在主线清理 |

## 赛狐创建规则

赛狐与 EN 都是“属性定义 → 属性值 → SPU → SKU 组合”的模型，但赛狐没有 EN 的模板物料概念。创建或补齐时应先核对 SPU 已配置的属性和值，再创建产品 SKU。SKU 编号、名称、属性名和属性值必须与 EN 产品变体一致，且不擅自改动既有 SKU 的在售状态。

属性 API 的限制改变了工作顺序：

1. 只读获取赛狐多属性列表和属性管理。
2. 缺属性时生成符合现有模板的 Excel，等待用户在赛狐后台导入并确认成功。
3. 再通过 API 创建缺失的 EN 产品 SKU。
4. 从赛狐全量 SKU 列表回读，核对 SPU、SKU、名称、属性和值以及在售状态。

不要从旧手工记录假定某个 SKU 创建成功。例如无颜色的 KS0013-HLR-80 曾被误创建，因为机械沿用了历史模板中不完整的属性集。产品实际有颜色时，EN 和赛狐都必须含颜色属性；正确对象是 KS0013-HLR-80-COFFEE。

## 报告和复核入口

最终业务工作簿为 missing_products/out/通途SKU未在EN产品登记及赛狐状态_202608110237.xlsx。工作表按汇总、套件暂缓、其他非产品项暂缓、皮壳通途 SKU、海绵通途 SKU、主体骨架后续、一对多历史关系、通途映射全量拆分。每行应能解释完整 SKU、库存、EN 精确登记次数、全部 EN 产品编号、候选及依据、赛狐状态和建议动作。

配套物料只读调查输出 missing_products/out/PK_HM1510客户物料号只读调查_20260811_104253.json。本轮观察到 PK# 没有客户码；HM1510 有 75 个原始子表行、53 个唯一“物料+客户码”组合和 52 个唯一客户码，许多值带“删除”前缀。唯一跨物料重复为 删除Curve-Pillow-Foam-50。这些是后续调研输入，不是清理指令。

## 失败模式与防护

| 失败模式 | 根因 | 防护 |
|---|---|---|
| 用 -Cover/-Foam 基码算已登记 | 将候选规则当成事实 | 完整码精确匹配；基码结果单列 |
| 只读 BOM 报表中的一个客户码 | 子表显示不完整 | 逐 EN 产品回读完整 customer_items |
| 为半成品码创建赛狐商品 | 混淆通途交付码和赛狐产品对象 | 只以 EN 产品 item_code 核验/创建赛狐 SKU |
| 把配套物料客户码当作产品登记 | 忽略销售订单导入入口 | 目标限定为 KS 产品变体 |
| 擅自处理一对多历史关系 | 试图让数据“看起来唯一” | 全部保留并输出；另立规则讨论 |
| 赛狐缺属性就直接 API 创建 | API 没有属性簇/值写接口 | 属性 Excel → 用户确认 → API SKU → 回读 |
| 把 EN 禁用理解成赛狐停售 | 两系统状态语义不同 | 不修改既有赛狐在售状态 |
| 依赖过期 handoff 继续建 SKU | 文档状态未刷新 | 新会话先读时间戳和最新审计；以回读为准 |

## 后续演进的起点

主线归零后，才做只读调查：通途客户码是否也登记在 PK# 或 HM1510、这些关系是否服务其他流程、以及拉链款弧形靠枕共用皮壳和通用海绵应如何维护。调查完成前不迁移、不删除配套物料客户码。

库存同步也不能直接从这份审计开始写。先把每个通途完整 SKU 到 EN 产品、赛狐产品 SKU、成本的关系显式化，再让业务确认一对多/多对一的库存归属、扣减方式和校准周期。

## 新 Agent 起步清单

1. 阅读本复盘、AGENT_HANDOFF.md 和最新工作簿，不依赖旧截图或旧“缺失”报告。
2. 重新获取三方数据，运行 audit_three_systems.py，先对账总数再看个案。
3. 所有可能写 EN 或赛狐的步骤必须先生成 dry-run/Excel/候选报告，并让用户确认写入范围。
4. 写入后对同一条记录从目标系统回读；“请求成功”不等于数据已正确出现。
5. 任何无法由数据唯一确定的产品关系保留为待确认项。完整、可解释的未匹配比错误自动匹配更有价值。
