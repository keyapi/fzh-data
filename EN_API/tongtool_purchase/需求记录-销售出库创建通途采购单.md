# 需求记录：销售出库单 → 通途采购单

> 状态：**已实现并部署到测试环境**（2026-09-16）。运维/部署说明见同目录 `AGENT_HANDOFF.md`。
> 记录人：Agent（与业务方 2026-09-15 沟通整理，2026-09-16 实现）
> 关联代码/文档：`EN_API/tongtool_purchase/`、`tongtool_api/docs/reference/purchase-orders.md`

---

## 一、目标

在 EN 的**销售出库单（Delivery Note）**上，把"去通途手工建采购单"这一步自动化。

业务方描述的通途手工流程：

> 采购管理 - 采购单 - 新建采购单 → 添加必填信息 → 添加商品 → 通过通途SKU搜索商品 → 确定 → 编辑填写采购数量

本需求就是把上述步骤用 API 打通。

---

## 二、交互方式：**按钮**（2026-09-15 业务方确认）

原设想是"杨义森提交后自动创建采购单，彭建填完物流单号再回填外部流水号"。
因通途**不支持更新采购单的外部流水号**（见第五节 #4），该方案作废。

**改为：在销售出库单上放一个按钮，由操作员手动点击创建。**

- 按钮仅在**已提交**（docstatus=1）时可见
- 只对 `CENTRADE` / `DANEEY` / `波兰公司` 三个客户生效，**其余一律置灰不可点击**
- 因是手动触发，`外部流水号` 取**点击当时**的物流单号（可能为空）——具体口径见第六节 #4
- 不需要自动触发，也就不需要改审批流来驱动创建

---

## 三、必填字段

| 业务方给的 | 值 / 来源 | 对应通途字段 |
|---|---|---|
| 采购人员 | **袁新春、彭建**（二选一） | `purchaseUserId` —— **需要通途的员工 ID，不是姓名** |
| 采购仓库 | **美东-CENTRADE**、**波兰-FZHPoland-covers**、**美中-FZH-DANEEY** | `warehouseIdKey` —— 需要这 3 个名字在通途仓库表里的 ID |
| 供应商 | 业务方**后期提供** | `supplierId` |
| 外部流水号 | **物流单号**（销售出库字段 `logistic_number`） | `externalNumber` |
| 运费 | **总运费**（销售出库字段 `logistic_cost`） | `shippingFee` |

销售出库单上已有这三个自定义字段（2026-09-15 核实）：

| 字段 | 类型 | 标签 |
|---|---|---|
| `logistic_cost` | Float | 总运费 |
| `logistic_number` | Data | 物流单号 |
| `logistics_provider` | Data | 物流商 |

## 四、处理范围与过滤

### 4.1 只处理三个客户（按钮门禁）

**判定字段 = 销售出库单的 `customer`**（2026-09-15 业务方确认，并已在生产核实三者都存在）：

| DN `customer` | 含义 | 核实到的 `customer_name` |
|---|---|---|
| `CENTRADE` | 美东公司 | 美东公司（CENTADE） |
| `DANEEY` | 美中公司 | 美中公司（DANEEY） |
| `波兰公司` | 波兰公司 | 波兰公司 |

- ✅ 只有这三个客户的 DN 能点按钮
- ❌ 其余（含各类 FBA）**按钮置灰不可点击**

### 4.2 采购范围：物料组属于「产品」的后代（白名单）

业务方口径：

> 出库明细中只用关注皮壳、成品的物料，不用考虑内胆、扣子等配件 → **只需要考虑存在客户物料号的行**

**明细行参与采购的数据只有两个：数量 + 客户物料号（`customer_items.ref_code`）。**

#### 过滤规则（2026-09-15 用生产数据定下）

业务方选了**白名单**，并要求排除**海绵**（当前不做）与**套件#**。

实测发现不需要枚举几百个组，**一条规则即可精确命中**：

```
明细行的物料同时满足：
  ① Item 上有客户物料号（customer_items.ref_code 非空）      ← 拿到通途 SKU
  ② 该物料的 item_group 属于「产品」的后代物料组             ← 白名单
```

生产数据验证（4234 个带客户物料号的 Item）：

| 分组 | 数量 |
|---|---|
| ✅ 在「产品」后代组 → **纳入采购** | **4050** |
| ❌ 套件# | 104 |
| ❌ 海绵（← 填充材料 ← 原材料，不在「产品」下） | 75 |
| ❌ 套件#沙发支撑垫 | 5 |
| 合计 | 4234 |

**被排除的 184 个恰好全是套件与海绵**，与业务方要求完全一致，且规则只有一条，后期要把海绵纳入只需放宽这一条。

#### 附带发现：皮壳行本身没有客户物料号

- **以 `PK#` 开头（皮壳）且有客户物料号的 Item：0 个**（生产共 2976 个皮壳）
- **以 `ND#` 开头（内胆）且有客户物料号的 Item：0 个**
- 以 `HM` 开头（海绵）：75 个

业务方 2026-09-15 指示：**皮壳行要"按逻辑获取其对应成品的客户物料号"**——通途 SKU 只登记在成品上。

⚠️ **但这条规则有两个坑，实测数据如下：**

### 4.3 皮壳 → 成品 的映射（客户组已定，后缀待实现时确认）

**坑 1：去掉 `PK#` 直接找成品，命中率只有约 80%**

抽查 200 个皮壳：`PK#KS0001-CMM-100-GREY` → 去掉前缀找 `KS0001-CMM-100-GREY`

| 结果 | 数量 |
|---|---|
| ✅ 成品存在且有客户物料号 | 159 |
| ⚠️ 成品存在但没登记客户物料号 | 7 |
| ❌ **没有对应成品** | 34 |

失败例：`KS0001-CMM-100-GREY` 不存在（只有 `-DEEPGREY` / `-LIGHTGREY`，色号命名漂移过）。
所以不能假设"`PK#` 前缀去掉就有同名成品"，**失配的行必须显式报出来**。

**坑 2（更关键）：一个成品常有多个客户物料号，格式还不一样**

「三角靠枕」组里有 SKU 的 592 个成品中，**56% 有多条不同的 ref_code**。这些码按两个维度区分：

| 维度 | 例子（`KS0001-DM-194-YELLOW`） |
|---|---|
| **客户组** `customer_group` | 美国公司 / 欧洲公司 / 美国FBA / 日本 / … |
| **交付形态**（后缀） | 基码 `CENKZ1325-Yellow-194` ↔ `-Cover` 码 `CENMM1620-Yellow-194-Cover` |

实例如下：

```
KS0001-DM-194-YELLOW
   美国公司   CENKZ1325-Yellow-194            ← 基码（成品交付）
   美国公司   CENMM1620-Yellow-194-Cover     ← -Cover 后缀（皮壳交付）
   美国FBA    BAI1325N0A10513SXFBA

KS0001-CMKTR-100-BLACK
   美国公司   C/Cord-Black-100-707-wow
   美国公司   C/Cord-Black-100-707-wow-Cover
   美国FBA    CENTR707-black-twin-FBA

KS0001-AHR-140-BLUE
   欧洲公司   TT0000759K0062943
   美国公司   TT0000759K0063275
```

`-Cover` / `-Foam` 后缀与 CONCEPTS.md 里「按通途 SKU 后缀和交付形态切分成本」的口径一致。

**所以"皮壳取成品的客户物料号"还差两步定义：**

| 待定 | 结论 |
|---|---|
| A. 取哪个**客户组**的码？ | ✅ **已定（2026-09-15）**：`CENTRADE`/`DANEEY` → **美国公司**；`波兰公司` → **欧洲公司** |
| B. 取**基码**还是 **`-Cover`** 码？ | ⏸️ **业务方要求搁置，实现时再问** |

> A、B 两问都是"猜错就会采购到错的货品"，必须业务方明确。
> 另：通途 `goodsQuery` 是拿 SKU 去查，所以也可以**把该成品的多个候选码都拿去查，取通途能命中的那个**——
> 但这会多消耗限流配额，且若多个都命中仍需人来选。建议还是先定死规则。

## 五、已核实的技术事实（2026-09-15 实测）

### 5.1 通途接口

| 用途 | 接口 | 说明 |
|---|---|---|
| SKU → 货品ID | `POST /openapi/tongtool/goodsQuery` | **`productType` 必填**，实测 `"0"`（普通销售）才对，`1/2/3` 合法但 0 结果，缺失直接报 `525`。返回 `goodsDetail[].goodsDetailId` + `goodsSku`。`skus` 每批最多 10 个 |
| 供应商 | `POST /openapi/tongtool/supplierQuery` | `supplierId` / `corporationFullname` / `supplierCode`；实测 320 家 |
| 仓库 | `POST /openapi/tongtool/warehouseQuery` | `warehouseId` / `warehouseName` / `warehouseCode`；实测 58 个 |
| **创建采购单** | `POST /openapi/tongtool/purchaseOrderCreate` | 见下 |
| **更新采购单** | `POST /openapi/tongtool/purchaseOrderUpdate` | **只支持 `expectArriveDate` / `purchaseOrderId` / `remarks`** |
| 采购单查询 | `POST /openapi/tongtool/purchaseOrderQuery` | |
| 采购到货 / 入库 | `purchaseArrival` / `purchaseOrderStockIn` | |
| 查询所有员工 | `POST /openapi/userInfo/query` | ❌ 实测 **401 Unauthorized**（当前 App 无该接口权限）→ **采购员 ID 无法用 API 取**，只能业务方从通途界面拿 |

### 5.2 创建采购单字段

Go SDK（`hiscaler/tongtool`）视角的必填：

`currency`、`goodsDetail[]{goodsDetailId, quantity, unitPrice}`、`purchaseUserId`、`supplierId`、`warehouseIdKey`

官方文档补充了 1688 相关字段：`buyerMessage`、`flow`、`purchaseOrderType`、`transactionMode`、`purchaseOrderId`。

`externalNumber`（外部流水号）、`remark`、`shippingFee`、`trackingNumber` 为可选。

成功返回 `datas` = **新建的采购单号**。

### 5.3 EN 侧映射链路（已实测打通）

```
DN 明细 item_code
  → tabItem Customer Detail.ref_code      （客户物料号 = 通途 SKU，如 CENKZ1325-Yellow-194）
  → goodsQuery(productType="0")
  → goodsDetailId                        （实测 6464013595201906110000449049）
```

**DN 明细行上没有通途 SKU**（标准字段 `customer_item_code` 实测为空），必须经 Item 走。

### 5.4 已知约束

- 通途同一商户**所有 App 共享 5 次/分钟**限流。
- 526 超频重试退避是 15s + 30s，**单次调用实测卡 46 秒**。
- 现有 `TongToolClient._check_rate_limit()` 把计数记在实例属性上，**跨实例失效**，只能靠被动退避。
- ⚠️ **HTTP 级错误（401/403/超时）会被当成网络异常重试 3 次**，`retry_delay_minutes=5` 作基数指数退避
  → 实测一次 401 **卡了约 7 分钟才报错**。调用未授权的接口不会快速失败，实现时要留意超时设置。
- 测试服务器：`8.133.254.66`，site 名 `erpnext.vilavi.cn`，代码落在 `delivery_plan` app。

### 5.5 既有客户端

`tongtool_integration/api/client.py` 的 `get_tongtool_client()` 已封装认证 / MD5 签名 / 限流 / 重试 / 缓存，
凭证在 `Tongtool Settings`。**直接复用，不要另写。**

### #4 展开：外部流水号还要不要放物流单号

通途「采购单更新」接口只有 `expectArriveDate` / `purchaseOrderId` / `remarks`，
**没有 `externalNumber`**，也没有 `trackingNumber`。所以创建后**永远无法再改外部流水号**。

改成按钮后，操作员点按钮的**时机**直接决定外部流水号的值：

| 方案 | 说明 |
|---|---|
| A. 点按钮时取当时的值 | 若彭建还没填物流单号，`externalNumber` 就是空的，且事后补不了 |
| B. 外部流水号固定放 **DN 单号** | 稳定、可回溯；物流单号另行记录（不传给通途或写 `remark`） |
| C. 要求"彭建填完物流单号后"才点按钮 | 靠流程约定，`externalNumber` = 物流单号；但没人拦着提前点 |
| D. 干脆不用 `externalNumber` | 靠 DN 上的通途采购单号字段回查 |

**建议 B 或 D** —— 外部流水号放稳定的 EN 单号，比放一个"可能为空、事后补不了"的物流单号更可靠。

## 八、关键风险

1. **限流**：5 次/分钟共享。一张多行 DN 的货品映射就可能吃掉配额。
   必须缓存（实测热缓存 0.00s），冷缓存首次可能卡几十秒。
   若体验不可接受，需把创建丢到 `frappe.enqueue` 后台队列。
2. **审批流改造的影响面**远大于本需求本身，需单独评估与回归。
3. **测试环境数据陈旧**：`customer_items.ref_code` 大多为空、物料组层级与生产不一致，
   端到端验证需要先在测试造数据（注意「客户物料号」只能登记到「产品/套件#」后代组的物料）。
4. **自动化写生产**：创建采购单是真实业务单据，落地时必须保留人工确认或完善的回滚/作废路径。
