## 一、现象

提交 DN-26-00078 时弹出：

> 以下 36 个物料组的库存不足，无法提交 …… 共计缺少库存量：419.0

而列表里的跟踪单号（`WO-26-028xx-001` 等）**实际是有货的** —— 例如 `PK#KS0001-HLR-153-BLACK` 在「待包装成品仓 - FZH」有 250 件。

## 二、校验机制（先讲清楚，后面才好理解）

校验代码在 **`delivery_plan` app**：

| 项 | 内容 |
|---|---|
| 文件 | `delivery_plan/delivery_plan/doc_event.py` |
| 函数 | `validate_dn_tracking_number_dimension_stock(doc, method)` |
| 挂载 | `delivery_plan` 的 `hooks.py` → Delivery Note 的 **`before_submit`** |
| 口径 | 按 **(物料, 仓库, 跟踪单号)** 分组汇总需求量；可用量 = `SUM(Stock Ledger Entry.actual_qty)`，条件为 `item_code` + `warehouse` + `IFNULL(tracking_number,'') = 该单号` |
| 维度来源 | ERPNext 的**库存辅助核算 `Inventory Dimension`**：`Stock Tracking Number`（`source_fieldname=stock_tracking_number`，`target_fieldname=tracking_number`，`apply_to_all_doctypes=1`） |
| 关键特性 | **只看 SLE 的跟踪单号维度，不看 Bin、不看预留数量**；只要有一组有缺口就整单拦截 |

> 这也是为什么"Bin 里有货"不等于"能提交"。

## 三、根因（三层，逐层叠加）

### 根因 1：该生产计划下的**成品工单被批量删除**

- `PP-26-00033` 就是 `SO-26-00097` 的生产计划（计划里 `sales_orders` 含 SO-26-00097）。
- ERPNext 的 `Deleted Document` 台账显示：**该计划下 78 个成品工单被删除**（另有 357 个半成品工单）。
  - 删除人：`1un_pmvzg02m5@dingtalk.com`
  - 时间：2026-08-17 ~ 2026-08-25
  - 删除时状态：全部 Draft
  - 模式：**每种成品被删了 3 次**（`WO-26-022xx` → `WO-26-025xx` → `WO-26-028xx`），最后一批删掉后**没有重建**
- 后果链：
  1. 跟踪单号的 `finished_product_work_order`（成品工单）由 `work_order_task/doc_events.py` 回填，回填逻辑按 **`production_plan` + `production_plan_item`** 反查工单；成品工单不存在 → 查不到 → 字段留空（计划 2609004 的 36 个单号里 **33 个为空**）。
  2. 出货计划提交时 `_execute_strict_mode_finished_goods_on_submit()` 会逐个单号调用 `_create_manufacture_for_finished_goods()`；
  3. 该函数第一步就判断
     ```python
     fp_wo_name = getattr(tn, "finished_product_work_order", None)
     if not fp_wo_name:
         return          # 未回填成品工单，静默跳过（不报错、不提示）
     ```
  4. **成品入库因此从未执行**，成品仓里自然没有对应的成品库存。

### 根因 2：皮壳库存的**仓库位置**与代码预期不符

- 成品入库的取数函数 `get_strict_so_warehouse_and_stock()`：当跟踪单号的 `so_materials` 以 `KS` 开头时，**固定查「待包装成品仓 - FZH」**。
- 实测 33 个单号中，只有 **11 个**的皮壳在该仓；其余 22 个的皮壳在 **「成品仓 - FZH」**（1 个在「半成品仓 - FZH」）。
- 已确认为**人为挪动**，按调拨恢复处理。

### 根因 3（执行阶段踩到）：重建工单时漏了两个字段

| 字段 | ERPNext 默认值 | 正确值 | 若为错误值的后果 |
|---|---|---|---|
| `use_multi_level_bom` | `1` | **`0`** | 工单的 `required_items` 被按**多级 BOM** 展开成面料/拉链/春亚纺，而不是「皮壳 + 内胆」 |
| `transfer_material_against` | `Job Card` | **`Work Order`** | Manufacture 凭证**不会带原料行**（原料走 Job Card 单独发料） |

两者叠加 → 入库凭证**只有成品行、没有任何消耗行**（成品凭空入库、不结转材料）。
修正前的凭证内容：
```
KS0001-HLR-140-BLACK x4.0  t=成品仓 - FZH   ← 只有成品，没有消耗
```
修正后：
```
PK#KS0001-HLR-140-BLACK x3.0  s=待包装成品仓 - FZH   ← 消耗皮壳
KS0001-HLR-140-BLACK    x3.0  t=成品仓 - FZH        ← 成品入库
```

## 四、修复动作（生产，2026-09-20）

| 步骤 | 内容 | 数量 |
|---|---|---|
| ① 重建成品工单 | 在 `PP-26-00033` 下重建，参数取自 `Deleted Document`（`production_plan_item`、`bom_no`、数量），并带上 `use_multi_level_bom=0`、`transfer_material_against="Work Order"` | 27 个（`WO-26-03461`~`WO-26-03487`） |
| ② 回填跟踪单号 | `Tracking Number.finished_product_work_order` | 35 个 |
| ③ 皮壳调拨 | Material Transfer：从「成品仓 / 半成品仓」→「待包装成品仓 - FZH」，带跟踪单号 | 26 张，317 件 |
| ④ 成品入库 | **调用出货计划自己的方法** `_create_manufacture_for_finished_goods`（不是手搓凭证），消耗皮壳、产出成品入成品仓并带单号 | 36 张，全部成功 |
| ⑤ 作废 | 执行过程中产生的两批「无消耗行」错误凭证全部 cancel | 66 张 |
| ⑥ 清理 | 取消本单用不到的多余工单 | 8 个 |
| ⑦ 补工单关联字段 | 给重建的工单补 `production_plan_sub_assembly_item`，并写入 **标签组合**（`custom_label_combination`）、**成品销售订单**（`fg_sales_order`）、**销售订单明细**（`fg_sales_order_item`，同时写标准字段 `sales_order` / `sales_order_item`） | 19 个 |

### 关于第 ⑦ 步（标签组合 / 销售订单关联）

- 系统设计：`work_order_task/doc_events.py::update_work_order_fg_sales_order_info` 挂在 Work Order 的 **`on_submit`**，从**生产计划的 `sub_assembly_items` 子表行**取三个字段写到工单：`custom_label_combination`（标签组合）、`fg_sales_order`（成品销售订单）、`fg_sales_order_item`（销售订单明细）。
- 该钩子**只在工单有 `production_plan_sub_assembly_item` 时才会执行**；重建工单时该字段为空 → 三个字段全部没写进去 → 入库后无法与销售订单 / 标签组合关联。
- 匹配要点：PP-26-00033 里**每个 FG 的 `production_plan_item` 下都有 2 行子装配件** —— 皮壳行（`PK#…`，**带标签组合**）和内胆行（`ND#…`，标签为空）；两行共享同一个 `fg_sales_order_item`。所以必须取**皮壳行**，否则标签会取到空值。
- 已修正 19 个工单，回读核验：标签组合 `PP000-SX004-XH001`、成品销售订单 `SO-26-00097`、销售订单明细均无缺失。

> 注：`标签组合` 同时也是一个库存辅助核算维度（`Inventory Dimension: 标签组合 → label_combination`），但实测历史 SLE 上该列**普遍为 NULL**（系统自己产生的凭证也是），故本次入库凭证未带该列与既有数据一致。

**说明：内胆为什么没被消耗？**
成品 BOM = 皮壳 1 + 内胆 1。内胆在「待包装成品仓 - FZH」没有库存，`_build_manufacture_stock_entry` 会把库存不足的原料行**自动剔除**（这是既有逻辑，本次保持一致）。所以本次入库只消耗了皮壳。

## 七、遗留与建议

1. **临时 API Server Script**：处理期间在生产建的临时脚本已全部删除（`Server Script` 中已无 `zz_` 前缀记录）。
2. **多建的工单已清理**：重建时按"该计划下所有被删的成品工单"来做，多建了本单用不到的工单，**已取消 8 个**：
   `WO-26-03466`(KS0002-DL-100-IVORY)、`WO-26-03469`(KS0524-HLR-194-BLACK)、`WO-26-03472`(KS0524-HLR-100-BLACK)、`WO-26-03474`(KS0002-DL-100-DEEPBLUE)、`WO-26-03475`(KS0002-DL-194-DEEPBLUE)、`WO-26-03477`(KS0002-DL-194-BLACK)、`WO-26-03482`(KS0524-HLR-153-BLACK)、`WO-26-03487`(KS0194-DM-60-IVORY)。
   其中 `KS0524-HLR-194-BLACK / 100-BLACK / 153-BLACK` 三个正是第五节的「无跟踪单号」物料，已有手工入库，故工单不再需要。
   取消后复核：DN 仍 **39/39 PASS**。
3. **【建议改代码】静默跳过**：`_create_manufacture_for_finished_goods` 在 `finished_product_work_order` 为空时直接 `return`，**不报错也不提示**，导致"没入库"无人知晓。建议改为抛出/提示。
4. **【建议改代码】工单创建参数**：生产计划的「创建工单」入口必须保证 `use_multi_level_bom=0` + `transfer_material_against="Work Order"`，否则成品入库永远拿不到消耗行。另建议放宽 `finished_product_work_order` 的反查口径（目前死绑 `production_plan + production_plan_item`，跨计划即失效）。
5. **【建议改代码】工单关联字段**：任何方式重建工单时，都要补 `production_plan_sub_assembly_item`（取**带标签组合的皮壳行**），否则 `update_work_order_fg_sales_order_info` 不会执行，工单缺少标签组合 / 成品销售订单，入库后无法回溯销售订单。
5. **内胆未消耗**：成品入库时内胆被自动剔除，是否符合财务成本口径需确认。
6. **皮壳回待包装成品仓**：本次把 22 个单号的皮壳从「成品仓」调回「待包装成品仓」。若该挪动是业务有意为之，则应改代码适配，而不是每次靠调拨纠正。
