## 一、背景

| 销售订单 | 工单 | 计划 | 更正前已产 | 皮壳落仓 |
|---|---|---|---|---|
| SO-26-00101（DANEEY，要 **130 件皮壳**） | `WO-26-02571` | 130 | 78 | 待包装半成品仓 - FZH |

## 二、根因（一个上游动作 + 一个字段）

**开料工单 `753`（2026-09-14）** 一张单同时给两个工单开料，分配表 `woker_order_allocations` 实际是：

- `WO-26-03197`（工单行只要 **25**）→ 分了 **78**（13+26+13+26），其中 3 行带 `is_or_exceed=1`
- `WO-26-02571`（工单行要 **130**）→ 只分了 **78**（39+39）

于是两工单的 `open_material_qty` 都 = **78**。而 `work_order_task/.../overrides/work_order_override.py:20`
`update_work_order_qty()` 的逻辑是：

```python
if flt(self.get("open_material_qty")) > 0:
    completed_qty = flt(self.open_material_qty)   # 允许入库量被替换成「已开料数量」
else:
    completed_qty = self.qty + (overproduction_percentage / 100 * self.qty)
...
if qty > completed_qty:
    frappe.throw(..., StockOverProductionError)
```

**这一个字段同时制造了两个症状**：02571（计划 130）被**压到只能入 78**；03197（计划 25）被**抬到可以入 78**。
两边入库量都精确等于 78，不是巧合。

## 三、更正口径（用户分两轮确认）

**第一轮**：03197 名下 4 个菲号 `13/26/13/26`，**53 无法由整菲号组合得出**（只能 52 或 65）。
取 **52**（整菲号 `-001 + -002 + -003`）先改挂 → 02571 = **130**、03197 = **26**。

**第二轮（超量 1 件归位）**：那多出的 1 件实物属于 02571，所以把它加到 02571 的菲号上：
**`WO-26-03197-001` 13 → 14**，同时 **`WO-26-03197-004` 26 → 25** 减回。
终态：**02571 = 131（比计划 130 超 1）**、**03197 = 25（正好等于计划）**，合计仍 156 件。

> ⚠️ 这一步**必须改动员工报工数量**（两个菲号各 7 道工序的 `for_quantity`/`total_completed_qty` 各 ±1）。
> 不存在既不动报工、又能让 02571 = 131 的做法 —— 实物 156 件、需求 155 件，多出的 1 件必须落在某个菲号上。

### ⑥ 开料工单重算依据（`initial_work_order_override.py:846-880`）

算法：组按 **`group_number` 升序**处理；`wo_origion_fill_numb` = **该行分配前工单的剩余需求**；

| 6 | 02571-002 | 39 | 02571 | 39 | 0 |
| 4 | 03197-004 | 26 | 03197 | 25 | **1**（26 > 25，即那 1 件超量） |

### ⑤ 工序重算依据（`job_card.py:762 / 857`）

`Work Order Operation.completed_qty` 由 `job_card.update_work_order()` 写入，
聚合口径是 **`(work_order, operation_id)`** 下 `docstatus=1` 的 Job Card `total_completed_qty` 之和。
所以只改 `Job Card.work_order` 不够 —— **`operation_id` 必须同时换到目标工单的同名工序行**，
再调 `update_work_order()` 让系统自己重算（不要手工塞数字）。

执行方式：`preflight → open-gate → cancel → repoint → fix-wo-qty → redo → close-gate
→ fix-jc-op → recalc-op → fix-initial-wo`，
每步带前置校验、默认 dry-run、写操作走**临时 API Server Script**（`zz_` 前缀，用完即删，生产已无残留）。

## 六、踩坑清单（重做时务必照做）

1. **`fix-wo-qty` 必须排在 `redo` 之前**。否则 `redo` 提交 Manufacture 时
   `update_work_order_qty` 会用 `completed_qty = open_material_qty = 78` 判「入库量 91 > 78」并抛 `StockOverProductionError`。
2. **redo 必须显式带 `from_bom = 1`**：`erpnext/stock/doctype/stock_entry/stock_entry.py:229`
   `if not self.from_bom: self.fg_completed_qty = 0.0` —— 不带就报「数量（制造数量）字段必填」。
3. **redo 的成品行必须 `set_basic_rate_manually = 1` 并抄原凭证单价**：
   `set_basic_rate()` 里 `if d.allow_zero_valuation_rate: d.basic_rate = 0.0`，
   且 Manufacture 的成品单价会按「工单历史 outgoing 值」重算（无消耗行时算成 0）。
   本次 3 张重做单价 **27.880551432 / 27.880579257 / 27.880576677 与原凭证逐条一致**。
4. **`frappe.client.submit` 只收一个 `doc`，且必须是完整单据**：只传 `{"doctype","name"}` 会被当成新文档、
   字段为空（BOM 提交会报「请先选择一个公司」）。
5. **`Woker Order Allocation` 是子表，REST list 会 403** → 只能从父单据（开料工单）里读；
   但**沙箱 `frappe.get_all` 能读到**。
6. **改挂过的凭证不能再按 `work_order` 查**：`repoint` 已把取消件/耗用件的 `work_order` 改成 02571，
   所以 `redo` 取单价模板只能按**菲号**查。
7. **沙箱约束**（实测）：禁 `_` 开头变量/属性名、禁 `import`/`getattr`/lambda、AST 禁 `-=`；
   可用 `frappe.get_doc/get_all/new_doc/db.set_value/db.commit/delete_doc(force=True, ignore_permissions=True)`；
   每条删除要单独 `try/except` + `frappe.db.rollback()`，否则一条 404 会中断整批。
8. 沙箱**能改已提交 Job Card 的 `work_order`**（已实测并还原），报工层可安全改挂。
9. **只改 `Job Card.work_order` 不会更新工序数量** —— 工序 `completed_qty` 的聚合键是
   `(work_order, operation_id)`，`operation_id` 也必须换到目标工单的同名工序行，
   否则目标工单的工序行永远匹配不到这些报工。换完后要用 **`job_card.update_work_order()` 让系统重算**，
   不要手工塞数字。
10. **开料工单的兄弟子表要一起改**：只改 `woker_order_allocations.work_order` 不够，
    `work_order_batch_qtys` / `fg_qty_key_material_bns` 同样带 `work_order`，会与新归属自相矛盾。
11. **子表的 doctype 名可能和字段名不同**：`work_order_batch_qtys` 只是字段名，
    真实 doctype 要从行的 `doctype` 属性取（`row.doctype`），否则报 `Table '...tabwork_order_batch_qtys' doesn't exist`。
12. **沙箱禁「下标增强赋值」**：`out["k"] += 1` 会报
    `Augmented assignment of object items and slices is not allowed` → 用普通变量计数、最后显式构造字典。
13. 沙箱 `frappe.db.set_value` **接收 dict 一次设多字段**（`set_value(dt, name, {k: v})`）可用。

14. **取消「加工耗用」会被工单状态拦**：`stock_entry.on_cancel` 只对 `purpose == "Material Consumption for Manufacture"`
    调 `validate_work_order_status()`，工单 `Completed` 时抛「无法取消已完成工单的交易」
    → 临时把工单 `status` 降为 `In Process`，做完再置回 `Completed`。
15. **加工耗用重做也必须 `from_bom = 1`**，且**布料是批次管理物料**：
    行上要带 `batch_no` / `use_serial_batch_fields=1` / `uom` / `basic_rate` / `cost_center` / `expense_account` / `custom_s_warehouse`
    （整行从原凭证复制），并临时打开 `Stock Settings.auto_create_serial_and_batch_bundle_for_outward`（用完关回 0）。
16. **同批次物料要先全部取消、再统一新建**：否则先建的那张会因同批可用量不足报
    「Available qty is less than the Required Qty」。
17. **凭证号别靠记忆**：本次一度把 tn `-001` 的完工凭证写成了 `-003` 的（`STE-26-15626`），
    误取消了一张、多建了一张 —— 改挂前务必按菲号**逐条查出凭证名**再写进常量。

**用户会逐层核对**：这次用户三次指出问题 —— 报工层、工序数量层 + 开料工单勾稽层、以及**超量 1 件的归属**。
改挂类操作交付前，务必把「菲号 → 报工(Job Card + operation_id) → 工序 completed_qty → 完工入库 →
耗用 → 开料分配及其兄弟子表 → 工单 produced/open_material」整条链逐层核对，不能只改看得见的凭证。
