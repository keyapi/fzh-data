# 180 天 vs 35 天视界

用户口径：视界要覆盖 **3 个月提前期 + 春节**，预测看到 **6 个月**。
本文记录 r4（180 天预测）接入后的净额、决策包与春节统计；
**不覆盖任何旧包**，旧 r2（35 天口径）保持原样。

**结构变化**：91 个原建议键全部保留，缺口从 450.0 增至 3,858.6（8.6×）；
另有 **116 个键从「无需补货」变为「建议补货」**，新增缺口 2,348.4
（波兰 69 键、美东 46 键、美中 1 键）。336 个键在 180 天内仍无需补货。

**为什么不是简单 3 倍**：180/60 的 p50 比值中位数是 **3.03**（线性），但 35 天
决策包只消费了 60 天窗口里约 **32 天**（10-29 → 11-30），而 180 天决策包消费约
**180 天**；天数比 ≈5.6，与需求比一致。保护期的细微差异来自 r4 与 r2 的 60 天
窗口重算（同日数据、不同模型批次），不影响结论。

## 3. 怎么用这组长视界数字

- **6 个月只用于产能/春节排期，不作采购量**：越远越不准（预测区间是滚动经验分位、
  未标定；仓库分配是近 3 个月销量占比假设；窗口 p50 按天均摊，不保留逐月形状）。
- 3 个月（90 天）以内的数字可用于「提前期覆盖」讨论；180 天数字用于回答
  「春节前后会不会断、要不要提前排产/催单」，不直接变成下单量。
- 建议键仍只是**人工审核候选**；3,469 个待核键不因视界变长而变成零需求。

## 4. 春节穿越统计（97 张开放 SO）

锚点 **2027-02-06**；停工 1 个月 + 恢复 1 个月 = **+60 天**；
受影响窗口 = 锚点 ±30 天 = **2027-01-07 .. 2027-03-08**。
判定：生产+发运路径 `[交付日−90, 交付日+90]` 与窗口相交。

| 口径 | 单数 | 行数 | 件数 |
|---|---:|---:|---:|
| 全部开放 SO | 97 | 1,089 | 56,653 |
| **穿越窗口（全部开放行）** | **11** | 45 | **4,356** |
| **穿越窗口（计入工厂管线）** | **8** | 23 | **2,600** |
| 仅生产段穿越（对照） | 0 | 0 | 0 |

按交付月：2026-10 = 1,903 件、2026-11 = 440、2026-12 = 257。
结论：现有 97 张开放 SO 的交付都在 2026 年内，**生产段没有一张跨 2027 春节**；
受影响的是「发运/到仓段」——8 张单 2,600 件在春节窗口内仍在途，
已按 +60 天写入逐行 `spring_festival_buffer_days`，并汇总在
`so_backlog_summary.json → spring_festival`。

口径变化说明：旧 r4c 的「applied 12,299 件」按「交付月落在 1–2 月」判断；
本次改为锚点窗口 + 发运段判定，故数字不同，属**口径变更**而非数据变化。
