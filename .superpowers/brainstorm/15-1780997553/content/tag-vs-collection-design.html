Tag vs Collection：四个系统的设计对比

AEM、ERPNext File、Notion、Google Photos — 它们各自如何区分"标签"和"分组/专辑"

1. AEM：三层模型（Folders / Tags / Collections）

Folders 📁 Tags 🏷️ Collections 📋
回答什么问题 WHERE
资产在哪里？		 WHAT
资产是什么？		 WHICH / WHY
哪些资产用于什么目的？
结构 层次树 (hierarchical) 层次分类法 + 命名空间 (namespaces) 扁平列表 (flat references)
关系 1:1（资产只在一个文件夹） N:N（资产可以有多个标签） N:N（资产可在多个 Collection）
生命周期 永久（最"重"的决定） 持久（受控词汇表，治理严格） 临时/项目级（ad-hoc curation）
谁操作 管理员 DAM 管理员维护体系，所有人使用 任何人（运营、市场、品牌）
关键差异 物理位置，绑权限 Tags = 描述资产本身的属性（白色、枕头、正面）
Collections = 描述资产被用于什么目的（6月上贴、夏季Campaign）
Tag 说资产"是什么"，Collection 说资产"用来干什么"

2. ERPNext File：通用附件模型

tabFile 表的关键字段（经搜索验证）：

file_url文件路径
attached_to_doctype关联的 DocType 名（如 "Item", "Sales Order"）
attached_to_name关联的具体单据名（如 "KS0001"）
is_private访问控制

关键设计：一个文件可以有多条 tabFile 记录，分别附加到不同 DocType 的不同单据。这是通用外键模式 — (doctype, docname) 作为灵活的 FK 对。

比如同一张产品图可以同时附加到 Item KS0001 和 Sales Order SO-00042 和 Website Item hero_banner。

3. 对我们的 DAM 的启示

当前 DAM 的数据模型其实是合理的

Tag = Asset 的属性（当前已有）

  • 描述资产"是什么"：颜色、角度、品类、场景
  • N:N 关系，通过 asset_tag 关联表
  • 有 category 枚举约束（color|angle|style|fabric|size|role|scene|season|custom）

Collection = 资产被用于什么目的（当前已有，需扩展）

  • 描述资产"用来干什么"：上贴、Campaign、画册
  • type 枚举定义目的类型
  • context JSON 定义具体目标
  • N:N 引用（通过 AssetCollectionItem）

用户担心的问题：Collection 的 context 太灵活 = 像 tag 一样随意？

这个担心是对的，但 AEM 和 ERPNext File 给出了答案：

AEM 的做法

用 type 枚举 + 每种 type 有固定 context schema 来约束灵活度。

type="listing" → context={skus, channel, marketplace}
type="campaign" → context={campaign, season, platforms}
type="catalog" → context={season, product_line}
ERPNext 的做法

用 (doctype, docname) 作为通用 FK 对 — 灵活但有结构。

attached_to_doctype = "Item"
attached_to_name = "KS0001"

不是自由文本，是引用真实存在的单据。

4. 建议：Collection 的 type/context 设计

参考 AEM type 枚举 + ERPNext (doctype, docname) 引用模式：

type 含义 context 包含 Phase
listing 平台 Listing 上贴批次 skus: [str], channel: str, marketplace: str Phase 3b 先做
campaign 营销 Campaign 图片组 campaign_name: str, season: str, platforms: [str] Phase 5+
catalog 产品画册/目录 product_line: str, season: str Phase 5+
custom 自由用途 description: str 已有

每个 type 有固定 context schema → 不会像 tag 一样随意。如果以后要关联 ERPNext 单据，可以在 context 里加 erpnext_doctype + erpnext_docname。

关于 Private Collection

搜索确认：AEM 的 Private Collection = 仅创建者+管理员可见。这是一种访问控制机制，不是"关联到某个人"的语义。

对我们：

  • Phase 3b 默认 Public，不需要 Private 的复杂度
  • 如果以后需要"按销售渠道/账号负责人隔离"，可以借助 Collection 的 context（如 context.channel = "Amazon-US"）过滤，而不是靠 Private 标记
  • ERPNext 的 tabFile.is_private 模式是一个参考，但现在不需要
