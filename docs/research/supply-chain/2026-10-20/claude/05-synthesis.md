# 05 — 综合结论与推荐架构

> 输入：`01-existing-assets.md`、`02-industry-practices.md`、`03-ai-agent-sota.md`、
> `04-open-source.md`、`experiments/e1–e3`。
> 本文只写推荐方案；未选方案在 §3 说明理由。证据编号沿用各文件（S1/S2/S3/S4）。

## 1. 结论先行

1. **V1 不是「建平台」，而是「一条可复跑的决策链 + 一页纸」**：
   只读快照 → 指标语义层 → 组合预测 → 补货建议 → 审批记录 → 例外队列。
2. **推荐「轻量栈 + 薄 Agent」**：cron/uv/Python → DuckDB（计算）→ SQLite（服务）→
   Metabase/静态一页纸 → StatsForecast + OR-Tools → ERPNext Workflow 审批 → MCP 只读工具。
   Agent 只做取数、解释、归因和草拟，**不碰最终数字、不执行写操作**。
3. **预测用组合法或 TSB，不选单一模型**：E1 修正后 held-out 测试期 TSB 0.511、ens5 0.520、naive 0.602
   （ens5 −13.6%）；验证期收紧切分后选 Croston（测试 0.530），**不能声称选择规则可外推**；
   保留 naive 守门 + 月度回测。
4. **补货优化的空间被决策结构锁死**：E2 证明**件数预算**下总缺货与分配无关；
   真正的杠杆是**服务水平/预算/滚动频率**，不是求解器。件数预算不能外推为金额预算。
5. **AI 的价值在「解释与编排」，不在「算数」**：E3 的确定性路由 + 语义层通过 15 题评估，
   0 次越权写；但**未验证生产鉴权、并发与独立回读**；LLM 直接报数有明确反证 [S3-002]。
6. **最大风险仍是口径与数据新鲜度**，不是技术选型。指标权威矩阵必须先由业务确认（§2）。

## 2. 指标权威矩阵（V1 提案）

| 指标 | 事实源（V1） | 粒度 | 新鲜度 | 已知偏差 / 禁用口径 |
|---|---|---|---|---|
| 销量（数量） | 通途订单月表（发货口径） | SKU × 仓 × 渠道 × 日 | 月表，滞后 1 月；202610 缺失 | 发货量 ≠ 真实需求；断货月是删失值 |
| 销售额 / 毛利 | 平台结算 / 赛狐结算 | 订单 / 交易 | 日更或月结 | 金额不要用通途订单表凑 |
| 可用库存 | 通途分仓库存 | SKU × 仓 | 准实时 | **EN Bin 不扣减通途，不能当可用库存** [S1-014] |
| 采购在途 | 通途采购单 | PO × SKU × 仓 | 准实时 | EN PO/请购链基本空白；SO 未交量不是在途 |
| 生产进度（WIP） | EN Job Card（首道 required 工序） | 工单 / 工序 | 实时 | 首道报工不跨工序求和；`WO.status`/`produced_qty` 不可信 |
| 生产产出（已入库） | EN 已提交 Manufacture Stock Entry（成品行） | 工单 / 批次 | 实时 | `produced_qty` 只是展示代理，不等于已入库 |
| 工厂出库 | EN 已提交 Delivery Note（签名数量，退货负向） | 单据 / 行 | 实时 | 草稿 DN 不计入；部分出库/退货需净额 |
| 头程在途 | 钉钉 `2026年下单表` + `发货信息总表` | 批次 / 包裹 | 人工维护，无时间戳 | **无结构化 ETA**；批次只写首行需下填；join key 是 EN SO 号 |
| 成本 | EN BOM 成本 + 成本引擎口径 | SKU / BOM | 变更时 | 赛狐 FIFO 批次成本不可反推；引用 #295 时以 20 号更正页为准 |
| 客户 / 渠道 | EN Channel Account | 客户 × 国家站 | 人工维护 | Amazon 按国家站；渠道别名需映射 |
| 需求预测 | 派生（模型版本 + 回测） | SKU × 月 | 月跑 | 不是事实；必须附方法、区间、断货删失标记 |
| 覆盖月数 | 派生（可用 + 在途）/ 需求率 | SKU × 仓 | 随快照 | 在途 ETA 不可靠时只能给区间 |
| 服务水平 / 预算 | **老板/财务决策输入** | 品类 / 月 | 人工 | 不是数据；不要让算法替老板定 |

> 这张表是 V1 的**唯一口径来源**。任何报表、Agent 回答、Excel 都必须引用同一指标名与定义。
> 生产数量的四分法（首道 / 末道 / 已提交入库 / 已出库）与守恒式见 [08-fact-contract.md](08-fact-contract.md) §1–§2；
> 不要把首道报工直接当产出。
> 落地方式：`metrics.yaml`（名称、公式、单位、权威源、刷新频率、禁用口径、owner）。
>
> **库存质量说明（用户 2026-10-20 补充）**：目前**只有通途库存**可作为可用库存来源；
> 通途库存本身不一定准确，但暂时没有更好的替代。所有库存快照必须带 `fetched_at`、
> 来源与质量标记（负数、异常波动、未映射 SKU），预测/补货输出要显式标注「库存置信度」，
> 不能把通途库存当成精确账。

## 3. 三个候选架构

### 架构 A：轻量决策链（推荐 V1）

```text
cron / Windows 任务计划
  → uv + Python（只读连接器：通途 MCP / EN REST / 赛狐 / 钉钉 / GSheet）
  → DuckDB 快照（原始层 + 口径层）
  → StatsForecast ens5 + 断货删失 + 偏差校正
  → 补货建议（DDMRP-lite / 6 个月覆盖 + MOQ + 预算）
  → SQLite 服务层 → Metabase / 静态一页纸 / 钉钉推送
  → ERPNext Workflow 审批记录（只生成草稿）
  → 例外队列（每条有 owner、时限、升级路径）
```

- **适合**：5 人团队、月度/周度批处理、先跑通一个品类。
- **成本**：约 ¥3.0–3.2 万/年（04 的轻量自建口径，含服务器与维护人力区间）。
- **周期**：4–6 周出 V1；90 天跑完一个试点周期。
- **风险**：自助分析弱；报表需求多了会回到「人肉 Excel」。
- **不选它的条件**：任务数 >10、需要 2 名以上运营自助、或多写并发/行级权限。

### 架构 B：标准数据平台（毕业路径）

```text
Prefect（Windows 原生）→ Postgres / DuckDB + dbt（可选）
  → Metabase / Superset
  → StatsForecast + HierarchicalForecast + OR-Tools
  → ERPNext 审批 + 权限
```

- **适合**：A 的触发条件满足后；有多人协作、数据契约稳定、需要资产血缘。
- **成本**：约 ¥6.4–9.8 万/年（04）。
- **周期**：3–6 个月。
- **风险**：dbt/Prefect/BI 服务栈带来运维负担；小团队容易「平台建好了、业务没用起来」。
- **明确不选**：Airflow（Windows 非原生、依赖 251）、Dagster（三常驻服务）、K8s [S4-001/003]。

### 架构 C：Agent 控制塔（只做薄层）

```text
语义层（metrics.yaml + 指标 API）
  → MCP 只读工具（订单/库存/在途/生产/头程）
  → Agent（Claude Agent SDK 或确定性路由）
  → prepare → 人工确认 → 只读执行 → 独立回读
  → 一页纸 + 证据链
```

- **适合**：A 的语义层稳定后，作为老板/计划员的「问数 + 解释」入口。
- **成本**：token 成本很低（Sonnet 级 $2/$10 per MTok [S4-051]），主要成本是集成与治理。
- **周期**：2–4 周薄层；不要先做多 Agent 编排。
- **风险**：LLM 非确定性、口径漂移、自动化偏差、过度授权 [S3-014/015/018/030]。
- **明确不选**：让 Agent 直接算补货量/下单；多 Agent planner-executor-critic 上生产；
  无白名单的 Text-to-SQL [S3-013/020]。

### 候选 D：成熟计划引擎（保留比较入口，不提前锁定）

> 回应评审：不提前决定「全部自组」。以下均为公开文档主张（V），未做 PoC；工期/成本是假设。

| 路线 | 需求冲减 | 有限产能 | 多级 BOM/中间库存 | 与现有系统集成 | 主要风险 |
|---|---|---|---|---|---|
| A 轻量自组（当前推荐） | 自建 | 需外接/自建 | 需自建 | 最高（Python/EN/通途） | 重复造 MRP；工期最长 |
| B ERPNext 原生（Production Plan + Reorder + Subcontracting） | 按 SO/MR 拉需求、扣预计库存 | 文档未提供有限排产 | 中间层有库存时计划不准（已知问题） | 最高（同库事实源） | MRP-I 口径；需外挂产能/证据层 |
| C1 FrePPLe（开源 APS） | 按优先级/交期排序 | 资源级有限产能 | 递归 BOM + 缓冲 | 需 ETL 接 EN/通途 | 运维与数据质量；企业版求解器另计 |
| C2 Odoo MRP/MPS | MPS 手工预测；补货含安全库存/提前期 | 标准版无真正有限排程 | 支持 | 需另建主数据 | MPS 与再订货规则不可混用；实施面大 |

**翻转条件**（满足任一才重新评估，不现在锁定）：

- **对照不必等 V1 完成**：同一事实快照准备好后，先跑轻量组件与 EN 原生可表达的部分；
  若自组需要重造 MRP，或已存在资源/BOM 约束，触发成熟引擎的最小影子例（G3b）。
- EN 原生 `projected_qty` 缺运营库存时不得直接对比；用测试输入显式注入，或判定该路径不适用。
- 单一品类、瓶颈靠人工排 → 先用轻量组件 + ERPNext 原生对照。
- 出现共享资源、换型、工序排序等有限产能约束 → 评估 FrePPLe（3–4 周 PoC）。
- 公司已在别处用 Odoo 且团队熟悉 → 优先 Odoo，避免双主数据。
- 头程/采购证据链是主矛盾、计划算术简单 → 自组薄层，旁挂 FrePPLe。
- 厂商/引擎无法导出原始记录与审计字段 → 一票否决。

**假设（非承诺）**：V1 单品类切片约 6–10 周；ERPNext 原生配置 1–2 周；FrePPLe PoC 3–4 周；
自组内核 8–12 周。均不含数据治理与头程接入，需 PoC 后重估。

## 4. 推荐：A + 薄 C，B 作为毕业路径

### 4.1 分层设计

| 层 | V1 选择 | 理由 |
|---|---|---|
| 接入 | 现有客户端只读；每日/每周快照 | 不重造连接器；失败可重跑 |
| 存储/计算 | DuckDB 单文件 + SQLite 服务层 | 单人可运维；Metabase 官方支持 SQLite 但**不支持 DuckDB** [S4-018] |
| 语义层 | `metrics.yaml` + 指标 API；禁止裸 SQL | E3 证明语义层能兜住歧义；Text-to-SQL 企业场景仍弱 [S3-013] |
| 预测 | TSB 或 `ens5` + 断货删失 + 偏差校正；naive 守门 | E1 测试期 TSB 0.511 / ens5 0.520 vs naive 0.602；验证选 Croston 测试 0.530，选择规则不可外推 |
| 补货 | DDMRP-lite + 6 个月覆盖 + MOQ + **件数预算**；输出「预算-服务水平前沿」 | E2：固定件数预算下分配不改变总缺货；金额预算未验证 |
| 排产 | 先做粗能力/交期倒排检查；不上 APS；保留 ERPNext 原生/FrePPLe 比较入口 | APS 依赖高数据质量 [S2-007]；产能是否瓶颈未证 |
| 计划引擎 | 不锁定；按 §3 候选 D 的翻转条件评估 | 未做 PoC；工期/成本是假设 |
| 审批 | ERPNext Workflow 记录 + 钉钉通知；只生成草稿 | 已有 Workflow 机制；不自动提交 |
| 交互 | 静态一页纸 + Metabase + 只读 Agent | 老板要结论，不要原始明细 |
| 治理 | 运行日志、数据新鲜度、未匹配报告、WAPE/Bias、采纳率 | 「把湖煮干」的可追溯性 |

### 4.2 为什么不是「先建大平台」

- 现有资产已覆盖连接器、履约阶段机、成本口径、库存预警；
  缺的是**上半段决策链**，不是又一套 ERP。
- 小团队的主要成本是维护，不是许可证（04 结论）。
- 先用 8 个 SKU 跑通，才能发现真正的数据缺口（E1/E2 已经暴露了断货标签与 MOQ 冲突）。

### 4.3 与现有资产的复用关系

| 现有资产 | 在 V1 中的角色 | 注意 |
|---|---|---|
| #291 `EN_API/fulfillment/` | 订单→生产→出库的阶段与数量事实 | 未合并；只覆盖阶段 0–3；头程未接 |
| #294 `order_side_input.py` | 销量/件数/拆包/补发口径 | 与 #295 分叉；不要假设可机械合并 |
| #295 `cost-engine-spec` + `group_split_rows` | 成本口径与「不重不漏」断言 | 引用以 20 号更正页为准 |

### 4.4 库存数据架构：通途 → 查询层（2026-10-20 补充）

**现状（用户确认）**：

- 目前只有**通途库存**可作为可用库存来源；它不一定准确，但暂时没有更好的替代。
- **EN 没有与通途库存同步**；EN Bin 不能当可用库存（已知差 351 件）。
- 通途 SKU ↔ EN 物料映射复杂；**拆包裹/合并订单**在 #294/#295 已有记录。

**结论：不要把通途库存写进 EN 的 Bin/Stock Ledger；建「只读快照 + 查询层」。**

> 术语：**DuckDB** 是嵌入式分析数据库（单文件、无独立服务，像「分析版 SQLite」）；
> **mart** 是面向某个主题的小型数据集市。**DuckDB mart** = 用 DuckDB 文件承载的
> 供应链数据集市（快照表 + 维度/事实表），不是一个新产品，也不是数据仓库。

| 方案 | 做法 | 优点 | 风险 | 结论 |
|---|---|---|---|---|
| A. 写入 EN Bin/Stock Ledger | 把通途库存同步成 EN 库存 | EN 内可直接查 | **污染账务/制造语义；双计；不可逆；违背 EN 不扣减通途的事实** | **不采用** |
| B. EN 只读快照 DocType | 自定义 DocType 存快照，不碰 Bin | EN UI/REST 可直接查；权限沿用 EN | 生产库增长；需测试环境；仍需映射 | 可选（EN 是硬性 UI 要求时） |
| C. 独立数据 mart | DuckDB/Postgres 存快照，供所有工具查询 | 无 EN 写入；可按 as-of 重建；迭代快 | 多一个存储/ETL；需权限 | **V1 推荐** |
| D. 手工导出/CSV 直查 | 继续用 CSV 当数据源 | 零改造 | 无历史一致性、并发/权限差、易错 | 不采用 |

**推荐落地（V1）**：

```text
Tongtool API（只读、分页）
  → 每日不可变快照（Parquet + manifest，含 fetched_at / run_id / 质量标记）
  → DuckDB mart：raw_snapshot / dim_sku / dim_warehouse / fact_inventory_snapshot
  → 语义层（metrics.yaml + 小 API / Metabase）
  → 预测、补货、BI、Agent 共用同一份数据
```

- **快照**：保留 13 个月，支持 as-of 回测；每个快照带 `source`、`fetched_at`、行数、未映射数。
- **质量标记**：负数、零、异常波动、未映射 SKU 单独记录，不静默丢弃。
- **SKU 映射**：独立 `sku_map` 表（`tongtool_sku`、`en_item`、`customer_item_code`、
  `split_group`、`effective_from/to`、`source`、`confidence`）；拆包/合并按 #294/#295 的行级规则，
  歧义 fail-closed；库存粒度（SKU×仓）与订单粒度（行/包裹）分开建模。
- **历史库存备份（如有）**：只作一次性回填源；校验后转 Parquet。
  新链路用 API 或受控导出，不把 CSV/手工文件当查询层。
- **EN 的角色**：事实源（SO/PP/WO/DN/BOM），不是库存快照的存放地。
  如果非技术同事必须在 EN 里看，再加只读 Snapshot DocType，仍然**不写 Bin**。

**测试策略（遵守「先别碰 EN 生产」）**：

| 阶段 | 环境 | 允许动作 |
|---|---|---|
| 1 | 本地 / 测试机 | Tongtool 只读 + 历史 CSV；不碰 EN |
| 2 | EN 测试环境 `ensh.vilavi.cn` | 建只读 Snapshot DocType/报表；FAC MCP + REST |
| 3 | EN 生产 | 仅只读同步，评审 + 开关 + 对账后上线；**不写库存账** |

**为什么不是「同步进 EN」**：

- EN 库存是会计/制造语义，通途是运营库存；所有权、仓、批次口径不同。
- 写进 EN 会让 EN 误以为拥有这些库存，导致 MRP、成本、对账错误；
  也会破坏「EN 不扣减通途」这条已经确认的事实。
- 只读快照能拿到大部分分析价值，不承担账务风险。

E1/E2 的 PB 楔形枕只作**方法试点**，不是 G1 业务切片。

| 周 | 交付 | 验收 |
|---|---|---|
| 1–2 | 指标注册表、只读快照、断货标签、SKU/仓/渠道映射 | 每个数字能回到源；未匹配单列 |
| 3–4 | `ens5` 回测 + naive 守门 + 偏差校正；月度运行 | 聚合 WAPE、Bias、覆盖率报告 |
| 5–6 | 补货建议（覆盖 + MOQ + 预算）；预算-服务水平前沿；一页纸 | 与 10-16 决策包对拍，差异可解释 |
| 7–8 | ERPNext Workflow 审批记录 + 钉钉推送 + 只读 Agent | 老板试用；0 越权写 |
| 9–12 | 例外队列、准确率复盘、采纳率 | 下一周期半天内复跑 |

**前置验证**：第 1–2 周必须先完成 [08-fact-contract.md](08-fact-contract.md) §8 的 V1–V16
（生产数量口径与退货/草稿/虚拟工序），否则“生产进度/产出”不可信。
**工期与成本均为假设**，需 PoC 后重估，不作为对外承诺。

**停止/回退条件**：

- 组合法连续 3 个月不优于 naive 10% → 回退 M1 + 安全库存。
- 断货标签无法覆盖历史 → 不做跨期回测，只做「当期 + 情景」。
- 预算/服务水平未定 → 输出前沿，不输出单一建议。
- 头程 ETA 仍无结构 → 到货日只给区间，明确标「估算」。
- 审批采纳率 <50% 连续两期 → 重做一页纸与信任机制，而不是加功能。

## 7. 风险与反证

| # | 风险 | 证据/反证 | 对策 |
|---|---|---|---|
| 1 | 口径不统一 | 三系统同指标定义不同 [S1-014] | `metrics.yaml` 先定权威源，再写代码 |
| 2 | 断货删失标签缺失 | E1 只能对 2026 年已知窗口删失 | 先补 2024–2025 标签；否则不做跨期回测 |
| 3 | 头程 ETA 不可靠 | 钉钉表只有人工日期 [S1-013] | 到货日给区间；等 Jack/PJ 数据 |
| 4 | 预测系统性低估 | E1 ens5 bias −11.2% | 偏差校正 / 安全库存补偿 |
| 5 | 固定预算下优化无效 | E2 总缺货不变 | 先定服务水平/预算；输出前沿 |
| 6 | 单一模型不稳定 | E1 最好单一方法仅 26% 原点第一 | 组合法 + 月度回测 |
| 7 | Agent 过度自主 | τ-bench / 多 Agent 失败模式 [S3-014/015] | 只读 + 语义层 + 人工确认 + 回读 |
| 8 | 未合并 PR 冲突 | #294/#295 分叉；多个 PR 冲突 | 引用思想与断言，不依赖可合并性 |
| 9 | 自动化偏差/采纳率低 | 自动化偏差综述 [S3-030]；E3 只在小切片通过 | 先影子运行，再逐步扩大 |
| 10 | 数据新鲜度 | 人工表无时间戳；202610 月表缺失 | 每次输出标「数据截止日」；超期告警 |
| 11 | 生产数量口径冲突 | #291 文档与代码矛盾；`produced_qty` vs 已提交 SE | 按 08 §1 四分法；先做 V1–V16 |
| 12 | 计划引擎路线未锁定 | 轻量自组 vs ERPNext 原生 vs FrePPLe | 保留比较入口；按 §3 候选 D 翻转条件 |
| 13 | 件数预算不能当金额预算 | E2 单位成本=1 是假设 | 用真实 EN BOM 成本重跑后再谈资金 |

**本项目最强的反证**：如果业务只想要「每月一份能看的 Excel」，那么 A 的复杂度仍然偏高，
应该退回「脚本 + 模板 + 人审」；本方案的价值只有在「要反复跑、要审计、要解释」时才成立。

## 8. 与三家对比会话的关系

本文件是 Claude 这一路的结论。Codex / Cursor 的独立调研完成后，应在对比会话中：

1. 只保留三方来源都能支撑的共识；
2. 分歧回到一手来源裁决；
3. 特别核对：指标权威矩阵、预测方法结论、开源栈选择、Agent 边界；
4. 输出 `00-comparison.md`，再决定最终架构。

**本文件不声称是最终答案**；它是可被三方对比修正的候选方案。
