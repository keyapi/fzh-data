# G1 三角靠枕匹配过程（按公司架构）

> **更正**：G1a v1 用“品类/产品名含三角”做主筛选，口径不对；`EN Tongtool Cost Review` 只借代码逻辑，不用其数据。
> 本文件按 `docs/company-context.md` / `CONCEPTS.md` 的公司架构重写。

## 0. 公司架构（先对齐）

`docs/company-context.md:14-29`：

```text
绍兴工厂
 ├─ 生产皮壳、内胆、半成品
 ├─ 部分成品直接生产 → FBA / 直接发货
 └─ → 海外分公司仓库：
      ├── USNJ (美东, NJ) → CENTRADE：填充/压缩/包装/仓储/发货(2C+2B)
      ├── USTX (美中, TX) → DANEEY：同上
      └── POLAND (波兰)   → 同上
```

- 三角靠枕类：绍兴只发**皮壳**给分公司；分公司填充 PP 棉、压缩、包装，最终卖给顾客的**多数是成品**。
- 个别订单只卖皮壳 → 发皮壳；这是例外，不是主需求。
- 因此：**终端成品出库 1:1 消耗皮壳**；补货需求应由分公司的**出库消耗**驱动（正常销售 + 补发/换货都消耗库存），皮壳仓是库存/缓冲节点，不是需求本身。

## 1. 匹配步骤（可复核）

1. 从 `EN产品BOM成本列表20261016.xlsx` 取 `产品编号` 前缀 `KS0001`/`KS0248` 的行：**1,739 行**。
2. 取 `客户物料号` 建精确索引；**不用品类文本做纳入**。
3. 每月 `订单_order_cost` 的 `通途SKU` 精确匹配客户码。
4. 按公司架构解释结果：
   - base 码订单 = 分公司出库（多数为成品销售，也包含补发/换货等），1:1 对应皮壳消耗；
   - `-Cover` 码订单 = 只卖皮壳的例外，也计入皮壳需求；
   - `绍兴发货方式=皮壳` 说明绍兴发的是皮壳，不代表订单行卖的是皮壳。
5. 皮壳仓（如 `FZH-DANEEY-皮壳仓库`）是分公司仓，不是“皮壳产品”；其销售行产品名也是「三角有扣…靠枕」。
6. **EN SO 行可能用包装码 `PK#`/`ND#`**：BOM `产品编号` 是 `KS0001-...`，
   订单行实际物料可能是 `PK#KS0001-...`（皮壳/成品包装码）。G1b 查 SO 必须用
   `--customer-code` 或先做 `KS → PK#` 映射；只按 `KS...` 精确查会漏单（试点已复现）。

> 补货看的是**库存消耗**，不是会计口径的“销量”：正常销售、补发/换货都是出库消耗，**都应计入**；

### 3.1 补发（M 后缀）核对

M 后缀是项目里常见的补发线索，但**不是唯一判据**。2026-04..09 快速核对（行/件）：

| 口径 | 行 | 件 | `是否补发货=是` | `是否补发货=否` |
|---|---:|---:|---:|---:|
| 全量 Mxxx | 286 | 333 | 172 | 114 |
| family Mxxx | 115 | 124 | 64 | 51 |

- family 里 `是否补发货=是` 共 66 行/72 件，其中 64 行带 M 后缀；
  另外 51 行带 M 后缀但 `是否补发货=否`，不能只凭后缀判定。
- family Mxxx 渠道（行）：Amazon 52、manomano 47、Wayfair 7、Cdiscount 3、PotteryBarn 2、
  HOME24 1、Mirakl 1、allegro 1、Shopify 1。
- 上述 Mxxx 是**快速聚合**（按订单号后缀），未逐单核；用于判断量级，
  逐行事实以 #294 补发口径与原始订单为准。
- **处理**：补发是出库消耗，已包含在 33,719 中；补货按毛量计，不另加、不净扣。
  若原单也在窗口内，原单与补发是两个独立出库事件，不能因为“同一客户”合并掉。
- 项目已有补发口径（#294 `order_side_input.py`）；M 后缀需结合 `是否补发货`、渠道/订单规则判断，
  不能单独当事实。

### 3.2 退货（反向流，不在订单文件）

- 订单文件没有退货/贷项/负数行；退货必须来自退货单、贷项通知或平台退货事件，不能靠订单文件净扣。
- **库存净算不冲减退货**：如果退货已经回库，它已经在 `available` 里；再从需求扣一次就是**双扣**。
  未回库/报废也不冲减（毛出库已经发生）。所以 33,719 直接作为对照当前库存的需求基线。
- **三角退货率暂按 5% 只作未来需求情景**（业务 2026-10-20 口径；`confidence=low`，是假设不是事实）；
  本期参考量约 `33,719 × 5% ≈ 1,682 件`。它**不用于当前库存净算**，也不能与已回库库存重复抵扣。
  其他品类/新品可能更高，不能外推；未来可从 Amazon 结算 V2 / 退货报表取实际值并配置化。
- 若退货尚未回库但预计会回库再售，应作为**未来供给**（in-transit/receipt）单列，而不是减需求。
- 若退货后又补发，补发已在出库毛量中；退货回库已在库存中，同样不再重复冲减。

### 4.1 WayfairCG / 其他 3PL 的结论（按数据 + 架构）

- **WayfairCG-Cranbury 是下游 3PL**：通常从美国两个分公司拿**成品**再发货。
  - 它的 **1,162 件 family 销售是终端需求**，应计入总需求；
  - **分公司 → WayfairCG 的转移不是新增需求**；补货净算时要把 WayfairCG 的成品/皮壳库存与在途算进去，避免重复。
- **供货归属不是固定的 USNJ 或 USTX**：可能按 SKU 分流，也可能随时期变化；必须看通途/赛狐的**调拨单**，
  不能从 Wayfair 销售渠道反推。
- **其他 3PL**：2026-04..09 的 family 销售里，非分公司仓**只有 WayfairCG**；
  没有证据表明其他 3PL 直接卖三角 family。其他 3PL 的海绵（`-Foam`）是另一条组件流，
  不是皮壳需求；其他产品也不在三角 family 内。
- **退货仓 165 件**是正数出库销售，照常计入出库消耗，不是新增需求也不是退货。

#### 4.1.1 `3pl_supply_allocation`（供货归属）

用途：把 WayfairCG 的**终端需求/库存/在途**挂到实际供货的分公司，供分公司级净算；不改变 family 总需求。

| 字段 | 说明 |
|---|---|
| `sku` / `family` | Sellfox/通途 SKU；映射到 EN leaf group |
| `3pl_warehouse` | 例如 WayfairCG-Cranbury |
| `source_branch` | USNJ/CENTRADE、USTX/DANEEY、PL、`unknown` |
| `period_start` / `period_end` | 调拨发生区间 |
| `transfer_qty` | 实际调拨量（已完成状态） |
| `in_transit_qty` | 在途/待入库量（未完成状态） |
| `transfer_no` / `source` | 调拨单号与来源（通途/赛狐） |
| `confidence` | `fact`（有调拨单）/ `estimate`（分摊）/ `unknown` |

数据来源：
- **赛狐调拨单列表**：`POST /api/warehouseTransfer/pageList.json`；
  `warehouseId`=发货仓、`targetWarehouseId`=收货仓、`items[].commoditySku`、`items[].goods`、
  `status`（0草稿/1待审核/2待调拨/3待入库/4已完成/5已驳回/6已作废）、`createTime`；
  可按 `targetWarehouseIds` 过滤 WayfairCG、按 `start/end` 取区间。见
  `SELLFOX_API/docs/api-reference/仓库/调拨单/调拨单列表.md`。
- **通途调拨单**（如有 API/导出）：作为一手来源或交叉校验；本项目暂未找到通途调拨 API 文档，
  不能假设一定可得。
- 需先把 Sellfox/通途仓库 ID 与分公司仓名做映射；映射表进 `sku_map/warehouse_map`。

分配规则：
1. 有已完成调拨：按 `source_branch × sku × period` 的实际调拨量分配；同一 SKU 多来源就按量拆。
2. 只有在途/计划：标 `in_transit`，不当作在手；到货丢件进 `discrepancy`。
3. 完全没有调拨数据：`source_branch=unknown`，用情景（按分公司 family 销售占比或 50/50）并标 `estimate`；
   **不得断言**“固定 USNJ”或“固定 USTX”。
4. 分公司级净算只扣该分公司实际供货的部分；WayfairCG 总需求只计一次。

### 4.2 WayfairCG 库存缺口（重要）

- **Tongtool 的 WayfairCG 库存可能不准**：YTQ 一般会在通途做调拨，但 Wayfair 实际收货可能丢件。
- YTQ 需要补 WayfairCG 时，是**下载 Wayfair 后台库存**；赛狐平台仓 API 只有 Temu/Mercado/Walmart WFS，
  **没有 Wayfair**；暂时不能 API 抓取。
- G1 处理：
  - `WayfairCG on_hand` 标 `source=wayfair_backend_manual`、`as_of`、`confidence=medium`；
  - 调拨单（通途/赛狐）只算**发出量/在途**，不能当实际在手；同时用于 §4.1.1 的供货归属；
  - `transfer vs Wayfair receipt` 对账，差额进 `discrepancy`，不静默修正；
  - 无后台数据时标 `unknown`，加安全缓冲，不补 0。
- 影响量级：WayfairCG family 销售 1,162 / 33,719 = **3.4%**；
  若丢件率 r%，总需求偏差约 3.4%×r（很小），但 WayfairCG 渠道库存偏差是 r%（对该渠道不小）。

## 5. 需要确认的剩余问题（只问业务，不问常识）

1. **WayfairCG 的供货归属**：不假设固定 USNJ/USTX；需确认通途/赛狐调拨单能否按 SKU、按区间导出。
   - 赛狐 `POST /api/warehouseTransfer/pageList.json` 已有发货仓/收货仓/SKU/数量/状态字段；
   - 需确认 WayfairCG 对应的仓库 ID、来源仓 ID，以及是否按 SKU 分流；
   - 无调拨数据时标 `unknown` + 情景，不阻塞 G1b。
2. **WayfairCG 库存导出**：由 YTQ 手工下载，频率？能否给一份当前后台库存 + 对应调拨记录？
   - 用来算丢件率/差异，不然后台库存只能标 unknown。
3. **补发口径**：补发已按出库消耗计入，不再等“是否算新增需求”。
   - 需确认 M 后缀规则与 `是否补发货` 字段是否覆盖全部补发；
   - 特别是有 51 行 family Mxxx 但 `是否补发货=否`，是渠道/订单类型差异还是字段漏标？
4. **退货反向流**：三角靠枕暂按 5% 情境；需确认退货是否都在通途操作并重新入库、
   可再售比例大概多少；其他品类/新品退货率另定，不能复用 5%。
5. **`-out` / `-Foam` 排除**：建议排除；本次订单 0 命中。
