# E3 只读 Agent 原型 — 设计、评估与判定

> 切片：楔形枕 8 个 SKU × 美中-Daneey 仓 × 2026-03 至 2026-09。
> 客户名、人员名、邮箱已匿名化；客户渠道记为 `channel_a`，其余渠道合并为 `other`。
> 本实验不调用外部 LLM，不写任何业务系统；数据为本地内嵌快照。

## 2. 实验边界与数据

- 范围：8 个楔形枕 SKU，仅美中-Daneey 仓，2026-03 至 2026-09 共 7 个月。
- 数据：决策信息包中的月销量（总数与客户渠道拆分）、断货窗口、干净月需求率、通途可用库存、通途在途与采购单。
- 已知缺口：2026-10 通途订单表缺失；波兰仓不在本数据集覆盖内；渠道只拆到“客户渠道 / 其他渠道”，无法回答具体平台级销量。
- 语义约束（写入指标注册表）：
  - 库存 = 通途分仓可用；**EN Bin 不能当可用库存**（EN 不扣减通途库存，实测差异 351 件）。
  - 在途 = 通途采购单未到货量；**SO 未交量不是在途**。
  - 销量 = 通途发货口径。
  - 月需求率 = 剔除断货月与到货冲量月后的干净月均。

## 3. 设计

### 3.1 处理链路

```text
自然语言问题
   │
   ▼
确定性路由器（关键词规则 + 槽位抽取；无 LLM）
   │  产出：意图 / 工具 / 参数 / 缺失槽位 / 命中规则审计
   ▼
策略闸门
   ├─ 写意图 ────────────────► 拒绝 + 安全替代（草稿，不提交）
   ├─ 越界 / 未注册指标 ─────► 拒绝 + 可回答范围
   └─ 错误前提（EN Bin 等）──► 纠正前提 + 正确口径重算
   │
   ▼
槽位校验
   ├─ 缺仓库 / 缺时段 / 多 SKU ─► needs_clarification（不猜）
   └─ 齐全
        │
        ▼
   prepare（生成只读计划，plan_id 可审计）
        │
        ▼
   confirm（评估自动确认；交互模式人工 y/N）
        │
        ▼
   execute（只读工具实现；所有数字在此计算）
        │
        ▼
   readback（再次执行同一工具并逐字段比对）
        │
        ▼
   作答 + 证据（tool / params / data_source / authority / values / readback）
```

### 3.2 语义层：指标注册表

| 指标 | 定义 | 权威来源 | 禁用 / 易错口径 |
|---|---|---|---|
| `monthly_sales` | 指定仓库、渠道、月份区间的通途发货数量求和，按自然月拆分 | 通途订单 Google Sheet（202603–202609） | 不能用 EN 销售订单数量替代发货量；SO 未交量不算已发 |
| `clean_monthly_demand` | 剔除断货影响月与到货冲量月后的月均发货；1 位小数（HALF_UP） | 通途订单 + 断货窗口三方交叉 | 含断货月的总销量不能直接平均 |
| `stockout_windows` | SKU 级断货事件：开始 → 到货/恢复发货 | Notion 任务页 + 客户邮件 + `check0stock` 差分 | 不能凭单一缺货 sheet 把整个家族标缺货 |
| `inventory` | 通途分仓可用库存 | 通途 ERP2 `erp2_stocks_stocksquery`（逐仓） | **EN Bin 不可当可用库存**；SO 未交量不可当可用 |
| `in_transit` | 通途采购单未到货数量之和 | 通途采购单 | **SO 未交量不是在途** |
| `coverage_months` | `(可用 + 在途) / 月需求率` | 库存 + 在途 + 干净月需求率 | 不能用 EN Bin 或 SO 未交量计算 |
| `recommend_order` | `ceil(max(0, 月需求率 × 覆盖月数 − 可用 − 在途))` | 干净月需求率 + 通途可用 + 通途在途 | 不允许模型口算最终数量 |

### 3.3 工具注册表（8 个，全部只读）

| 工具 | 必填参数 | 可选参数 | 说明 |
|---|---|---|---|
| `monthly_sales` | `sku, warehouse, start, end` | `channel`（默认 `all`） | 月销量 |
| `stockout_windows` | `sku` | — | 断货窗口；SKU 级事件，不要求仓库 |
| `inventory` | `sku, warehouse` | — | 通途分仓可用库存 |
| `in_transit` | `sku, warehouse` | — | 通途采购单在途 |
| `coverage_months` | `sku, warehouse` | `rate_source`（默认 `clean`） | 覆盖月数 |
| `recommend_order` | `sku, warehouse` | `coverage_months`（默认 6）、`rate_source` | 建议补货量 |
| `explain_recommendation` | `sku, warehouse` | `coverage_months`、`rate_source` | 展开计算链与断货剔除依据 |
| `compare_skus` | `skus, metric, warehouse` | `start, end, channel` | 跨 SKU 同口径比较 |

所有工具声明 `read_only=True`，注册表中没有任何写工具。数字由工具实现计算；路由器只选择工具和填充槽位。

### 3.4 prepare / confirm / execute / readback

| 阶段 | 行为 | 证据 |
|---|---|---|
| `prepare` | 生成 `plan_id`、工具名、规范化参数、只读标记 | 计划本身可审计 |
| `confirm` | 评估模式自动确认（因工具只读）；交互模式要求人工 `y/N` | 记录 `confirm_mode` |
| `execute` | 再次校验工具只读后执行 | `executed_tools` 列表 |
| `readback` | 用同一参数再次执行并逐字段比对 | `readback.status = verified` |

评估模式下自动确认不改变“只读”性质；任何写意图在 `prepare` 之前就被策略拒绝。

### 3.5 确定性路由规则（首条命中优先）

| 规则 | 意图 | 触发示例 |
|---|---|---|
| `R01_premise_conflict` | 错误前提 | 用 EN Bin 的库存算覆盖 |
| `R02_write_intent` | 写意图 | 帮我把 2880 下 110 件 |
| `R03_out_of_scope` | 越界 / 未注册指标 | 预测明年全公司销售额 |
| `R04_explain` | 解释建议 | 解释为什么建议补 |
| `R05_stockout` | 断货窗口 | 什么时候断货 |
| `R06_in_transit` | 在途 | 在途多少 / 采购单 |
| `R07_compare` | 跨 SKU 比较 | 比较两个 SKU 的需求率 |
| `R08_recommend` | 建议补货量 | 覆盖 6 个月补多少 |
| `R09_coverage` | 覆盖月数 | 还能覆盖几个月 |
| `R10_inventory` | 库存 | 有多少可用库存 |
| `R11_sales` | 销量 | 5 月卖了多少 |

槽位抽取覆盖：SKU 后缀 / 完整通途编码 / EN 物料号 / 买家 SKU；仓库（美中-Daneey / 波兰 / 全部）；渠道（客户渠道 / 其他 / 全部）；月份单点与区间；覆盖月数；需求率口径。

“最近”“近期”等相对时间不映射为具体月份，直接要求澄清。

### 3.6 “数字不由路由计算”

- 路由器只解析槽位（例如把“覆盖 3 个月”解析成 `coverage_months=3`）。
- 最终数值全部来自工具实现，并使用 `Decimal` 与显式舍入规则。
- 解释题不信任问题中给出的数字：Q08 的问题包含“110”，工具仍从数据重算得到 110；证据里记录 `numbers_computed_by = tool_impl`。
- 8 个 SKU 的 6 个月建议补货量与决策包逐项一致（合计 257 件）。

## 6. 失败分析

最终一轮 15 题全部通过。开发过程中出现过两类真实问题，均已修复并保留说明：

1. **纠正路径的数值类型不一致**
   - 现象：Q15 数值检查报“期望 0.26，实际 0.26”。
   - 原因：拒绝/纠正分支没有调用 `jsonable`，`Decimal("0.26")` 与浮点 `0.26` 在 Python 中不相等。
   - 修复：纠正结果统一序列化后再比较。
   - 教训：证据链不只覆盖正常作答路径，拒绝与纠正路径也必须输出可序列化、可复核的值。

2. **写意图规则误伤“帮我查一下”**
   - 现象：初版 `帮我.{0,12}(下|订|采购)` 会把“帮我查一下……”中的“下”当成写意图。
   - 修复：规则改为匹配“下单 / 下 N 件 / 订 N / 采购 N”等更具体的组合。
   - 教训：只读策略宁可保守，但过度拒绝会损害可用性；规则需要负样本回归。

残余风险：

- “不要提交，只生成草稿”包含“提交”，当前会按写意图拒绝；这是保守策略，安全但可用性略低。
- 同义词覆盖仍有限，例如“能卖多久”可能未命中“覆盖/够卖”；需要持续补充规则或引入受控的语义解析。
- 问题中包含“修改后的建议”等词也可能触发写意图；当前倾向拒绝。

## 7. Falsify 判定

Falsify 条件：SKU / 仓库语义歧义 > 20%，或路由器无法可靠映射问题到指标。

| 检查项 | 结果 | 判定 |
|---|---|---|
| 评估集语义歧义率 | 2/15 = 13.3% | 未超 20% |
| 可作答题的槽位未解析率 | 0/10 = 0% | 通过 |
| 路由器未命中 | 0/15 | 通过 |
| 可作答题工具 + 槽位正确率 | 10/10 = 100% | 通过（阈值 90%） |

**结论：本楔形切片未触发 Falsify。** 语义层（指标定义、权威来源、禁用口径）足以支撑确定性路由与只读工具。

但该结论只对“8 SKU × 单仓 × 单客户渠道拆分 × 7 个月”成立。若扩展到多仓、多平台渠道、更多 SKU 或更细的批次口径，歧义率可能上升；届时应先扩展语义层与主数据映射，再扩大 Agent 范围。

## 8. 限制

- **没有 LLM**：本实验刻意用确定性路由器，验证的是覆盖与歧义处理，不是自然语言泛化能力。真实用户换一种说法就可能漏命中。
- **本地快照而非实时系统**：工具读的是内嵌 JSON，不连接通途 / EN / 赛狐；证据只能追溯到本地数据集，不能证明线上 API 的可用性与权限隔离。
- **干净需求率是包内已整理值**：Agent 没有从原始订单行重新推导断货剔除，只使用决策包的干净月表。
- **渠道粒度有限**：只有 `all / channel_a / other`，无法回答具体平台级销量。
- **仓库覆盖有限**：只有美中-Daneey 有数据；波兰仓会明确返回“未覆盖”，不会猜。
- **评估集由实现者编写**：15 题规模小，且题目措辞与路由器规则同源，存在选择偏差；需要用真实用户问法做独立盲测。
- **确认闸门在评估中被自动通过**：因为所有工具只读。生产环境仍需人工确认、鉴权、审计与限流。
- **未做并发 / 会话状态 / 多轮追问**：澄清后如何续问不在本实验范围。
