## 3. 三条事实（附边界）

1. **覆盖率**（交期前存在任一非取消 PO/WO 的行 / 交期已知的行）：外部 **293/294（99.7%）**，内部 **2231/2310（96.6%）**；交期未知而行未计入分母：外部 0 行、内部 0 行。该覆盖率是**存在性**口径，接近饱和，不能读成“按单及时供给”。
2. **滞后**：SO 创建日 → 最早供给单，外部中位数 **-360.0 天**（293 行有供给单，其中早于 SO 的 **276** 行），内部中位数 **-478.0 天**（2237 行，早于 SO 的 **2149** 行）；若只看 SO 当日或之后创建的首张供给单，外部中位数 **1.0 天**（282 行）、内部 **1.0 天**（2199 行）。负滞后只说明物料此前已被采购/生产过，不代表为本单下单。
3. **无动作与最差月份**：交期前没有任何 PO/WO 的行 外部 **1**、内部 **79**（其中完全查不到供给单的 外部 1 / 内部 73，供给单创建晚于交期的 外部 0 / 内部 6）；按月看，外部最差 2026-03（98.5%，64/65）；内部最差 2026-01（90.8%，158/174）。无动作 ≠ 漏单（可能备货/调拨）；有动作 ≠ 及时足够（数量与到货未验证）。

## 4. 方法要点

- 覆盖判定只看**存在性**与**创建日**：`min(creation) <= delivery_date`。不读库存、不读到货、不比数量（按任务设定“只用单据日期”）。
- 月份与半年按 `transaction_date` 归属，保证与筛选范围自洽；`lag_days` 按 `creation` 起算（SO 草稿创建 → 首张供给单创建）。
- PO 明细行按子表行 id 去重，WO 按 (单据名, 创建日) 去重；SO 行按子表行 id 去重。父表/子表 join 分页在 `name asc` 上不稳定（会重复并漏行），因此统一按 `name asc, idx asc` 排序，子表行 id 再兜底去重。
- 不做任何写操作；CSV 只含哈希化 SO 标识与物料编码，不含客户名、不含 PO/WO 单号。
