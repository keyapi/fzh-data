# 自动补货：整体交付计划

## 目标与唯一入口

**从最新可得的逐仓库存出发，结合未来需求、未履约订单、已下单、在产、已出库和在途，形成可解释、可复算、可人工执行确认的补货建议；在目标服务水平下尽量减少库存资金与积压风险。**

本文件固定方向、任务与验收；[项目看板](PROJECT_BOARD.md)记录实时完成情况；[老板简报](BOSS_BRIEF.md)说人话汇报；[评估理论与指标](INVENTORY_EVALUATION.md)规定选模与补货比较标准。不再另造平行总计划。

本计划是跨角色项目计划，不是生产部署授权。2026-10-23 用户已要求继续推进 Shipment、长短史预测、PB 需求恢复、全 SKU 补货与持续优化。局部证据不足不等于全项目停工。

## 不可偏离的交付要求

| 要求 | 交付含义 |
|---|---|
| R1 当前起算 | 以有时间戳的快照起算，覆盖剩余本月和未来保护期；不先还原历史月初；旧快照必须披露陈旧度 |
| R2 全去向 | 首批冻结 1,328 SKU / 2,309 SKU×仓旧母集的去向；后续核在售、库存及近期无销售商品目录，不能永远把近期销售母集称公司全 SKU |
| R3 供应闭环 | 未结 PO、WO、DN、Shipment、接收/上架是同一批供应的不同阶段，关联去重，按实际可售时间进入供给 |
| R4 多种需求 | 长史、短史/间歇、PB 长史且有断货线索分别验证；模型实验必须接回统一补货评估，不能只产一张 WAPE 表 |
| R5 业务效果 | 优先看需求满足与库存占用的权衡；WAPE/MASE/Bias 是诊断，不是终极 KPI；不用 1−WAPE 命名准确率 |
| R6 可解释 | 每行显示模型/政策版本、库存时间、未来需求、已承诺需求处理、供应剩余量/时间/去重、建议及假设和风险 |
| R7 可监督 | 更新看板、提交与测试凭证、独立审核、下一动作；终端存活不算进展，worker 自报完成不等于验收 |
| R8 安全执行 | 允许项目内离线研发和既有授权范围内最小生产只读；不写生产、不下单、不合并、不公开推送业务数据 |

## 交付分层：不是一个“已完成”就全部通过

1. **技术状态**：待开始 → 执行中 → 待审 → 返修 → 已验收；仅就固定版本与声明范围判断。
2. **使用等级**：研究附件 / 条件建议 / 业务确认后可执行建议 / 已获采购执行批准。与技术状态分开。
3. **情景编号**：在手基准、仅证实及时到货、假设到货、延误压力等；不得再用 A/B 同时表示验收等级与计算情景。

没有签认不阻塞条件建议、模拟和研发；签字也不能把缺失事实变成已知事实。执行采购仍须用户/业务授权。条件建议应有数值、假设、需要时间及可能改变决策的条件，不用“非采购量”四字代替所有成果。

## 里程碑与退出条件

| 里程碑 | 给甲方的成果 | 必须满足的退出条件 |
|---|---|---|
| M0 方向和看板可监督 | 本计划、实时看板、老板简报 | 当前产物与待办均有证据入口；角色收到并确认，不把文档创建当产品完成 |
| M1 广覆盖条件建议，可供业务试用 | 全母集行动清单、逐桶供需账、模型/到货/服务情景、代表算例 | 全去向对账、核心域逻辑测试、独立审核；有数与无数的原因都保留；高风险行隔离，不要求所有行都可执行 |
| M2 完整目录与补货政策验证 | 扩展商品目录、概率预测、服务—库存前沿、可确认的建议 | 长/短/PB 分组对照、运输与提前期接入、政策参数版本化；模型切换有业务收益与退化边界证据 |
| M3 持续生产使用（先人审） | 可重复刷新、可回滚产物、异常清单及复盘 | 数据新鲜度/运行失败不静默、建议审批记录、MOQ/装箱/预算落实；前向观察验证；不自动写单 |

今天优先完成 M1；不承诺未经验证的完成时刻。任务完成即流转，时间仅是告警上限。M2 的独立实验与 M1 并行，不等全目录完美或“最优模型”才交付 M1。

## 核心验收例（任务书必须细化，不靠报告措辞过关）

| 域 | 必测情况 |
|---|---|
| SO/预测冲减 | F=100、未履约SO=20、物理库存80：若SO属于同窗预测，总需求仍100，不能扣成80再扣库存；若SO不在预测内需另加。用available时查占用是否已扣，不能重复扣 |
| 时间账 | 快照在月中、跨月、迟到供应、分批接收、已知未来取消/退货；时点前后不重复需求/到货；最早缺口不能靠期末盈余掩盖 |
| 供应数量 | 一个DN五个号、一个号多DN、部分已签收/部分在途、父已提交子表docstatus0；取消与退货处理；未知分配不均摊 |
| 未知与SKU×仓 | 缺库存/单位/物料/ETA、不同仓同SKU、共享料、Cover替代未证、零销售与源缺失；缺值不自动0 |
| 预测评估 | 同窗口/同SKU/同训练可知信息；群体偏差和重点SKU退化；追加未来证据不改变过去预测；不拿自身插补需求评分 |
| 概率与政策 | 合成已知需求下Fill rate/CSL可手算；累计分位数不等于逐月分位数相加；提前期/复核周期/MOQ/预算变动；服务目标未知先输出情景前沿 |

建议沿用现有 `experiments/business_phase/forward_net.py`、`forecast_eval/`、`dn_bridge/` 与 `experiments/pb_stockout/`；测试文件随任务建立 `test_forward_net.py`、`test_dn_bridge.py`、`test_inventory_policy.py`，先搜同类测试再增补。不因这份计划重写已有已验收适配器。

## 推进与监督规则

1. 工头收完成事件 → 看真实产物/测试 → 提交固定版本 → 送必要审核 → 返修或下一项；不能发完总结就把无人值守等同于待用户催。
2. 同难点三次无新证据：先搜项目资产/经验 → 官方/成熟开源 → 固定输入最小对照；能突破则继续，否则隔离该项并推进独立工作，不机械停全项目。
3. 每卡记录：负责人、Task/Dispatch、最近证据时间、产物/commit/hash、测试、审核范围、下一动作。没有证据不写执行中/已验收。
4. 同一卡投入超过2轮仅文案返修，工头须解释为什么影响交付；下一动作应是实际修复/验证/集成，不再扩大报告层级。
5. Codex读实际额度/重置；低额度合并窄审、先做Claude离线工作，保存队列；不擅换模型、购买或密集重试。
6. 上下文接近60%保存短交接，约70%准备压缩；只带当前目标、版本、未结卡及证据入口，不再灌满历史终端。
7. 工头/Codex2可按证据更新看板；稳定目标、服务政策和范围变更必须留变更原因。外部Codex/Claude Desktop只读看板及报告提出监督意见，不形成第二指挥链。
8. 本地文件不会自动唤醒Agent；需验证Orca完成事件/等待循环真实运行。若会话退出且无人接收，必须显示“调度未运行”，不能宣称持续监督。
