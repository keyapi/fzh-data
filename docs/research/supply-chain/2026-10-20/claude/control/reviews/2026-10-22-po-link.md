# SO 与采购/生产的真实关联路径

> **只读**：37 GET / 60，7.3 s，单线程 200 ms；无写入、不下单、不改配置、不改既有产物。
> `po_no` 只输出前缀与掩码格式（字母→A、数字→9、其他→?），不输出原值；单号一律哈希化。

## 1. 做了什么

- 新增 `experiments/auto_order/check_po_link.py`，回答 T40 留下的问题：`po_no` 解析到 Purchase Order 命中 0，是
  「PO 不存在」还是「字段语义不同」，以及 SO→供给到底有哪些**显式**路径。
- 读 `Sales Order` 的 DocType meta 取 `po_no` 的 fieldtype；取 2026-01-01..09-30 已提交 SO 前 30 张，统计
  `po_no` 的前缀分布与掩码格式；用这 30 个值对 `Purchase Order.name` 做精确匹配。
- 逐个读 6 个候选 doctype 的 meta（Work Order / Material Request Item / Production Plan Sales Order /
  Delivery Plan Item / Delivery Note Item / Purchase Order Item），确认 `sales_order` / `so_detail` /
  `against_sales_order` 字段是否存在；再用 4 张样本 SO（前 2 外部 + 前 2 内部）过滤，记录**样本命中行数**。
- 对 Purchase Order 加了一个全局对照：`Purchase Order Item.sales_order is set`（不限样本）；
  用同样形状在 Delivery Plan 上做阳性对照，排除「查询写法导致 0」的可能。

## 2. `po_no` 是什么

- `Sales Order.po_no` 的 **fieldtype = `Data`**，label = `Customer's Purchase Order`；
  **不是 Link→Purchase Order**，所以它不可能承载内部采购单号。
- 30 张样本 SO 的 `po_no` **全部非空**；前缀分布：`TXHY`×8、`PLHY`×5、`NJHY`×4、`BNUSFBA`×2、`DAUSFBA`×2、
  `TXKY`×2、`PL`×1、`LEFBAUK`×1、`LEUSFBA`×1、`STFBADE`×1、`RSUSFBA`×1、无字母前缀×2。
- 掩码格式以 `AAAA99999999`（13 条）、`AAAAAAA99999999`（8 条）为主，其余为带后缀的变体——
  典型「字母客户/渠道前缀 + 日期数字」的客户单号形态。
- 用这 30 个值对 `Purchase Order.name` 精确匹配：**0 行**。

## 3. 六条候选路径

| 路径 | 字段是否在 schema 中 | fieldtype | 4 张样本 SO 命中 |
|---|---|---|---:|
| Work Order | 是 | Link→Sales Order | **20**（单次上限） |
| Material Request | 是（`Material Request Item`） | Link→Sales Order | **10** |
| Production Plan | 是（`Production Plan Sales Order`） | Link→Sales Order | **7** |
| Delivery Plan | 是（`Delivery Plan Item`） | Link→Sales Order（+`so_detail` Data） | **68** |
| Delivery Note | 是（`Delivery Note Item.against_sales_order`） | Link→Sales Order（+`so_detail` Data） | **68** |
| Purchase Order | 是（`Purchase Order Item.sales_order`） | Link→Sales Order | **0** |

- 逐 SO 明细见 `out/auto_order/po_link_findings.md` 第 3 节；20 表示触到单次查询上限，不是精确值。
- **PO 全局对照**：`Purchase Order Item.sales_order is set`（不限样本）返回 **0 行**；
  同一形状在 `Delivery Plan Item.sales_order is set` 上返回 5 行 → 「is set」过滤本身可用，
  PO 的 0 不是查询写法造成的。

## 4. 结论

1. **SO→供给的显式路径有五条**：Work Order、Material Request、Production Plan、Delivery Plan、Delivery Note。
   字段都是 `Link → Sales Order`；`Delivery Plan Item` / `Delivery Note Item` 另有 `so_detail`（Data，存 SO 明细行 name），
   可以精确到行。样本里这五条都能查到记录。
2. **Purchase Order 这条路不通**：`Purchase Order Item.sales_order` 虽然是 Link，但**全库没有任何一条 PO 设置它**
   （样本 0、全局 is set 0）。也就是说 schema 允许，业务上没用。
3. **T40 的「po_no 未解析」是两个独立原因叠加**：
   ① `po_no` 是 **Data 客户采购单号**（label「Customer's Purchase Order」），本就不指向 EN 的 Purchase Order；
   ② 即便改走 PO→SO 的 Link，也没有任何 PO 建立了这种连接。
   所以「SO 有 po_no 却没有对应 PO」是**预期现象**，不是漏单，也不是 PO 单据缺失。

## 5. 顺带发现：一个会让查询静默返回 0 的陷阱（影响上一轮产物）

- 在 `Delivery Plan` 上，字段清单**同时包含表头 `status` 与子表字段**时，接口**静默返回 0 行**（HTTP 200，不报错）；
  去掉 `status` 后同一过滤返回 **20** 行。脚本里做了对照复现（`dp_quirk={'with_status': 0, 'without_status': 20}`）。
- 因此上一轮**数量守恒核查**（`qty_conservation`，commit `82ecae9a`）里的「Delivery Plan 关联 0 行 / DP 行 0」
  是**假阴性**，不是 DP 真的没有关联。
- 影响范围：DP 只被当作「关联证据」，不参与数量计算，所以守恒恒等式与供给/需求比值**不受影响**；
  受影响的只有「显式关联 / 未观测」的分母（当时外部 68、内部 481 行未观测，可能偏高）。
- 未修改上一轮产物（本任务只允许新增文件）；如需更正，应由协调方另派任务重跑 `check_qty_conservation.py`
  （去掉 DP 查询里的 `status` 字段）。

## 6. 边界与复现

- 只读：schema 读 `/api/resource/DocType/<name>.fields`，数据读 `/api/resource/<doctype>`；无写操作。
- 样本只有 4 张 SO、命中上限 20 行：结论是「**有没有**这条路径」，不是「有多少」。
  要规模化的关联率，需要另一次全量（有预算约束的）核查。
