# B 包：SO 关联修复与分阶段审计

> **只读**：171 GET / 200，34.5 s，单线程 200 ms；无写入、不下单、不改配置、不改既有产物。
> **边界**：只用显式关联，不按同物料推断，不读库存；「需求 − 净交付 = 余额」只是算术结果，**不是**独立验证。

## 1. 修了 DP 假阴性，并重算关联率

| 口径 | 命中 SO | 关联率 |
|---|---:|---:|
| 修正前（表头 `status` + 子表字段） | 0 | 0.0% |
| 修正后（去掉 `status`） | **236** | **70.4%** |

- 同一批 SO（335 张已审计）下重取：修正前后差 236 张 SO，全部来自查询字段组合，不是数据缺失。
- 复现方式：同一过滤、同一分页，只改字段清单；修正前恒为 0 行（HTTP 200，无报错）。
- 这一坑不影响数量/比值类结论，只影响「显式关联率 / 未观测」的分母。

## 6. 过程中发现并修掉的问题

1. **EN 的分页排序会超时**：`order_by=name asc, idx asc` 在宽子表扫描上稳定返回 HTTP 500；改 `name asc` 后正常。
   但纯 `name asc` 的 OFFSET 分页会重复/漏行（早期一次重跑同一 SO 的 DN 汇总得到 236 与 117 两个值）。
   最终改为 **keyset（`name >= last`）+ 子表行 id 去重**，既不依赖 idx 也不丢行。
2. **早停会丢行**：只要「该批 SO 都出现过」就停止翻页，会漏掉同一批 SO 后续页的 DN 明细。
   去掉早停后 DN 关联行从 10,862 升到 11,211、DP 从 14,479 到 14,718。修好后连续两次运行 CSV 哈希一致
   （`c8c4a502695deee8`）。
3. **PP 查询整体不可用**：任何带子表字段的 PP 查询 500，连 `limit 5` 也不行；因此 PP 记「不可观测」，
   而不是「关联率 0%」。
4. **关联必须可解析**：`po_no` 之类只有字段值、解析不到具体单据的，不算关联（上一任务已验证 `po_no` 是客户单号）。

## 7. 边界与复现

- 只读；单号全部哈希化，CSV 不含客户名、不含单据号。
- 恒等式只作算术余额，超交付/重复 DN 等异常独立计数；不推断库存是否真实超补/缺补。
- 连续两次运行 CSV 哈希一致（`c8c4a502695deee8`）；单次运行 171 GET / 34.5 s，均在预算内。
- PP 路径因 EN 500 不可用，是本次唯一的不可观测项。
