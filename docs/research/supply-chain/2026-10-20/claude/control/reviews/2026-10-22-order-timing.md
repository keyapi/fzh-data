# 下单时点回测（只用单据日期）

> **只读**：65 GET / 200，13.0 s，单线程、间隔 200 ms；无写入、不下单、不改配置、不改既有产物。
> 结论只写观测事实：**有 PO/WO ≠ 及时足够**（只证明存在一张更早创建的非取消供给单，数量/到货/是否为本单下单都未验证，
> 甚至可能早于 SO）；**无 PO/WO ≠ 漏单**（可能备货、预生产或调拨）。

## 1. 做了什么

- 新增 `experiments/auto_order/order_timing_backtest.py`，读取 EN 生产只读 API。
- 范围：`transaction_date` ∈ 2026-01-01..2026-09-30 的**已提交** SO 行（docstatus=1、status≠Cancelled），
  **不排除已关闭/已完成**（问的是下单当时发生了什么）；按 `is_internal_customer` 分外部 / 内部。
- 每条 SO 行取：SO 创建日、单据日期、交期（行级 `items.delivery_date`，缺失回退表头）、物料、数量、内外部。
- 对同物料查 EN 的 **Purchase Order** 与 **Work Order**（创建日、数量、状态、docstatus；**排除 docstatus=2 已取消**，含草稿），计算：
  - **覆盖**：交期前是否存在任一 PO/WO（`min(创建日) <= 交期`）；交期未知才记 null；
  - **滞后**：SO 创建日 → 首张 PO/WO（可为负 = 供给单早于 SO）；
    另给 **SO 后滞后**：只取 SO 创建当日或之后创建的首张供给单，更接近“本单触发的动作”；
  - **无动作行**：交期前没有任何 PO/WO（含“完全无供给单”和“供给单晚于交期”两种）。
- 数据量：SO 行 **2604**（外部 294 / 内部 2310）、**111** 张 SO、**657** 个物料；
  PO 明细 283 行（全部已提交），WO 7087 行（草稿 801 / 已提交 6286）。2026-02 无已提交 SO 行，按月表因此断档。

## 4. 三条事实（带边界）

1. **覆盖率接近饱和**：外部 293/294（99.7%）、内部 2231/2310（96.6%）的交期前都能找到一张更早创建的非取消 PO/WO。
   这是**存在性**口径：不读库存、不读到货、不比数量，不能读成“按单及时供给”。
2. **首张供给单大多早于 SO**：外部 276/293、内部 2149/2237 行的最早供给单创建日在 SO 之前，故中位数为负
   （外部 -360.0 天、内部 -478.0 天）。这说明该物料此前已被采购/生产过，不说明为本单下单；
   只看 SO 当日或之后创建的首张供给单，中位数外部 1.0 天、内部 1.0 天。
3. **无动作很少但分布不均**：交期前没有任何 PO/WO 的行 外部 1、内部 79（其中 73 行完全查不到供给单、6 行供给单晚于交期）；
   按内外部分别看，最差月份为外部 2026-03（98.5%，64/65）、内部 2026-01（90.8%，158/174）。
   无动作可能是备货或调拨，不等于漏单；有动作也不等于及时足够。

## 5. 实现中发现并修正的问题

1. **`无供给单` 被误记为 unknown**：原写法只在“有交期且有首张供给单”时判定覆盖，导致完全无 PO/WO 的行落到“交期未知”，
   虚高覆盖率分母。现改为：交期已知 + 无任何供给单 → **覆盖=否**；只有交期本身未知才记 null。
2. **表头与行级 `delivery_date` 同名**：两者同时选取会互相覆盖。现把表头字段别名成 `hdr_dd`，行级保持 `delivery_date`；
   实测 2604 行全部有行级交期，回退逻辑仅作保险。
3. **父子表 join 分页不稳定**：按 `name asc` 翻页会重复并漏行（子表行序号不在排序键里）。
   现统一 `name asc, idx asc` 排序，并用子表行 id 兜底去重；实测同一 SO 内确实存在多行同物料同数量同交期（是源单据真实重复行，不是翻页重复）。
4. **CSV 需字节级可复现**：排序加子表行 id 作为最终 tiebreaker 后，连续两次运行 CSV 哈希一致
   （`sha256 前 16 位 = 1e9a7aa511e253a9`）。
5. **负滞后会误导**：单看“滞后中位数 -360 天”容易被读成管道故障，因此并列给出 `SO 后滞后`，并把“早于 SO 的行数”写进表格。
