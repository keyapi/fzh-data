## 0. 一句话

M01 的真实原因不是“输入被换过”，而是**用 Windows 工作区的 CRLF 字节算 hash**：同一文件
LF 表示是 `15d52072…`（287,307 bytes，git 里就是这个），CRLF 表示是 `7eea7c6f…`
（297,288 bytes）。现在按 canonical LF 字节硬绑定、失配即拒，并把两套 hash 与 blob/commit 写进产物。
M02 按 end 动态生成 6 个月到 2027-03-21、断言桶日数等于请求天数，并把窗口 P90 改为
**同形历史日历窗口残差**；重算后 seasonal naive 的 120 天窗口覆盖只有 **75%**。
M03 只是标签错 30 天（数值本来就是 60/90/120），改标签后重算稳定性 9 稳 1 不稳。
M04 把 `start_condition` 换成结构化三态闸门：旧版 10 行里 8 行写着“转 always”，新版 0 行，
always 层仍为 0。

## 1. M01 — 冻结输入不能从固定提交复现

**决策**：按 `evidence.json` 实际字节 hash `15d52072…` 重跑绑定；生成入口加断言，失配即失败退出；
产物写 commit/blob/hash。

**修复前**

| 项 | 值 |
|---|---|
| `model_race.json` `inputs.evidence_sha256` | `7eea7c6f41d444bb69728646fb8cb90a174bbc71f5124c3876f5bd13508175b1` |
| 字节数 | 297,288 |
| 从 `98e1c664 / 3a19cd05 / f9df4357 / 8641bf87` 读出的 blob | `15d52072…`，287,307 bytes |
| 生成入口 | 只 `sha256_file()` 记录现场，无期望值、无断言 |

**根因（本轮实测）**：`b.replace(b"\r\n", b"\n")` 后长度 287,307、sha `15d52072…`；
`b.count(b"\r\n") == 9,981`，差值 9,981 = 行数。即 V1 首版把 **Windows CRLF 工作区字节**
当成输入 hash —— 内容与 git 完全一致，只是表示不同，所以任何固定提交都无法复现那个值。

**修复后**

| 项 | 值 |
|---|---|
| 绑定常量 | `EXPECTED_EVIDENCE_SHA256 = 15d52072…`，`EXPECTED_EVIDENCE_BYTES = 287307` |
| 校验对象 | **canonical（LF）字节**；raw 字节同时记录 |
| 失配行为 | `SystemExit("evidence content mismatch…")`，退出码 1，不写产物 |
| 产物字段 | `evidence_sha256`（canonical）、`evidence_sha256_raw`、`evidence_raw_bytes`、`evidence_crlf_count=9981`、`evidence_line_ending_normalization="crlf_to_lf"`、`evidence_blob_sha1=04c30f791c1e627aaa7d12a327202b0f70e9eb52`、`code_commit`（运行时的 HEAD）、`hash_binding_verified=true` |
| 覆盖范围 | `model_race.py` 与 `build_actions.py` 两个入口都做了同一绑定 |

**可见证据**：把 evidence 复制到临时目录、只把 `"report_version": "V0.1"` 改成 `"V0.2"`，
再跑 `model_race.py --evidence <副本>`：

```
exit=1
evidence content mismatch: expected canonical sha256 15d52072… (287307 bytes LF),
got 188b61dd… (287307 bytes LF; raw e84d755f…, 297288 bytes). Refusing to run…
output written? False
```

## 2. M02 — 动作窗口漏月 + 完整月残差冒充部分月窗口（决策 2A）
