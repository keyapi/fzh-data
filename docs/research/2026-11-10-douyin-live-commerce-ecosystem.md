# 抖音直播电商生态调研

> 2026-11-10。适用前提：**自营品牌直播 + 自有工厂生产发货**（不是给第三方代发）。
> 阅读顺序建议：先看 §1 结论，再看 §5（备注传产线，本次最具体的病）与 §7（EN 能干什么），其余按需。
> 面向管理层的精简版见 [管理层版](2026-11-10-douyin-live-commerce-management-brief.md)。

---

## 1. 结论摘要（TL;DR）

1. **能自建，但有一道 1–3 个月的硬门槛：软著。** 抖店官方 FAQ 明确「调用接口必须先申请资质，创建完应用才可以调用接口」，且软著**必须**由国家版权局颁发、著作权人须与店铺主体一致、须在 `ccopyright.com.cn` 可查，**没有替代材料**；软著常规审核 30–60 个工作日。ERPNext 本体是 GPLv3、著作权属 Frappe，**不能**拿来登记；要登记的是我们自研的 app。自研应用审核本身只要 1–3 个工作日，卡点在软著。
2. **订单、售后、电子面单、客服机器人、投流都有官方接口。** 但「直播间弹幕」没有面向商家的官方接口 —— 官方那套属于「直播小玩法」，要抖音云 + 内网专线，不是运营口径。
3. **"买家备注传不到一线生产"是误读。** 平台限制的是**收件人明文个人信息**的流转，不是业务指令本身。备注里的定制要求（刻字、改尺寸、指定包装）可以传；要做的是把备注里的手机号/地址先脱敏。
4. **订单接入优先做成 EN 的独立 app（与 `tongtool_integration` 同构），不要另起服务。** 但「电商作业台」（波次拣货、面单池、售后审核台、客服会话）应该用现成的——不是做不到，是不划算且会波及生产。
5. **真正的风险不是技术，是履约处罚。** 2026 年发货三红线（超时 1–5%、虚假发货 25%、欺诈发货 30% + 冻货款）＋ 隐私违规累计 12 分清退。合规动作比接 API 更优先。

## 2. 生态全景：一条直播链路拆成 6 层

| 层 | 干什么 | 平台官方 | 服务市场 ISV | 自建 |
|---|---|---|---|---|
| ① 流量内容 | 短视频/直播引流、素材生产 | 千川·乘方（千策/千意/千寻）、即创/即梦 | 代运营、素材工厂 | AI 批量出素材（见 §8） |
| ② 交易订单 | 下单、订单同步、改价/改址 | 抖店订单 API、消息推送 | 聚水潭/万里牛/旺店通/我打 | 自研应用 + 中间层 |
| ③ 履约发货 | 打单、取号、回传、拦截 | **抖音官方电子面单（强制）**、物流 API | 同上 + 风火递/抖掌柜类 | 不建议自研面单链路 |
| ④ 客服 | 售前咨询、催付、售后沟通 | 飞鸽客户端 + 官方机器人（仅"智能辅助"） | 晓多/探域等认证 ISV | 客服消息权限包 + 自建 LLM |
| ⑤ 售后 | 退款/退货/换货审核、拦截 | 售后 API（`/afterSale/*`） | OMS 内置 | 可自建但价值低 |
| ⑥ 数据复盘 | GPM、UV 价值、停留、转化 | 罗盘/百应后台 | 飞瓜、蝉妈妈 | 待核实是否有官方接口 |

**判断**：②③④ 是必须打通的；① 是运营活，⑤⑥ 可以先用现成后台。

## 3. 平台接口盘点（抖店开放平台）

### 3.0 申请门槛：软著是硬门槛，且不能先开发后补

官方 FAQ 原文（[应用创建常见问题](https://op.jinritemai.com/docs/question-docs/103/3226)，2025-02-14）：

> 很抱歉，调用接口必须先申请资质，创建完应用才可以调用接口。
> 软著的要求：**必须提供由国家版权局颁发的软件著作权证书扫描件或照片**，著作权人需与您店铺 & 开发者实名认证一致，且能够在中国版权保护中心官网（http://www.ccopyright.com.cn/）**查询到有效信息。其他软著认证平台均不符合要求。**

推论（三条，都影响排期）：

1. **顺序不可绕过**：资质 → 软著 → 创建应用 → 才能调接口。想"先开发测试完再补软著"的路径**不通**。
2. **ERPNext 本体不能用于登记**：它是 GPLv3，著作权属 Frappe Technologies，不是我们的主体。能登记的是**我们自己写的 app**（如 `key_test`、`tongtool_integration` 这一类）。2026-03 中国版权保护中心新规还明确打击"拿开源项目改名套壳"，审核会做代码相似度比对。
3. **软著周期 30–60 个工作日**（常规），加急可压到几个工作日但费用高。这是 P1 的**关键路径**，比写代码慢得多。

> ⚠️ 2026-03 新规的两个摩擦点（来源为行业解读，需以版权中心最新公告为准）：申请表新增**手抄承诺「本软件为独立开发，未使用 AI 编写代码、撰写文档或生成申请材料」**；审核引入 **AI 代码相似度比对**。若我们的代码大量由 AI 生成，这一段存在如实声明与通过率之间的张力 —— 申请前应先按实际情况评估，**不要抱着"先交了再说"的心态**，失实会被列入版权登记失信名单。

**若没有软著、又不想等 3 个月**：走服务市场现成 ISV/OMS（它们早已具备资质），或先用人工/导出过渡。这正是 §7.3 架构选项 B 的触发条件之一。

### 3.1 应用与认证

| 项 | 内容 |
|---|---|
| 端点 | `https://openapi-fxg.jinritemai.com/{method}` |
| 公共参数 | `app_key`、`access_token`、`param_json`（业务参数按名排序的 JSON）、`timestamp`（GMT+8）、`v=2`、`sign`、`sign_method` |
| 签名 | `hmac-sha256`（官方推荐，`md5` 将下线） |
| token | OAuth2 授权码模式，商家在后台确认授权后换 `access_token` |
| 网络 | **必须配置 IP 白名单** |
| 频控 | 逐接口声明（例：`/rights/getProductPrivileges` 接口总限流 5000 次/秒） |
| 收费 | **自用型应用同样收费**（2023-06-01 起「商家后台系统」类目纳入） |

### 3.1.1 API 收费与「云内 / 云外」（官方规则 V1.3，2026-06-16）

《抖店开放平台技术服务费规则》原文表：

| API 类型 | 抖店云内调用 | 抖店云外调用 |
|---|---|---|
| 基础 API | 0.018 元/百次/AppKey | **0.18 元/百次/AppKey（×10）** |
| 增值 API | 0.05 元/百次/AppKey | 0.5 元/百次/AppKey，**未经允许禁止云外调用** |

**已核实：`/order/batchDecrypt`（批量解密）在官方《收费接口列表》里属「基础 API」**，与 `/order/searchList`、`/order/orderDetail`、`/afterSale/List`、`/afterSale/Detail` 同类。也就是说**云外可以调用，只是单价 ×10**。

> 有一条流传的说法是「2023-08-31 起自研涉及订单解密的必须部署抖店云、云外解密权限关闭」。该说法我在官方收费规则与收费接口列表里**没有找到对应条款**，暂按「待工单确认」处理。**但它不影响主方案** —— 我们推荐的是**密文打单**（官方电子面单组件在本地解密），本来就不调用 `batchDecrypt`。

**换算成钱**：按日 500 单、每单 2 次调用、售后翻倍估算 ≈ 6 万次/月 → 云外约 **108 元/月**。量级可忽略，**不构成"必须上抖店云"的理由**。

> 另有独立产品「数据推送」（抖店云 → RDS）与「消息推送」，与 API 收费是两套机制；欠费时数据推送会**停止推送**，这点比 API 限流更致命。

### 3.2 订单与售后（已核实字段）

| method | 用途 | 备注 |
|---|---|---|
| `/order/list` | 订单列表，支持按下单/更新时间排序 | 可做增量拉取 |
| `/order/detail` | 订单详情 | 含下面这些关键字段 |
| `buyer_words` | **买家留言** | 客户特殊要求的原始来源 |
| `seller_words` | 商家备注 | 内部用，不会给买家看 |
| `encrypt_post_receiver` / `encrypt_post_tel` / `encrypt_detail` | 密文姓名 / 电话 / 详细地址 | 默认拿到的就是密文 |
| `/order/batchDecrypt` | 批量解密 | **受每日/每月额度管控**，未付款/已退款/待支付严禁解密 |
| `/order/addOrderRemark` | 商家给订单加备注 | 反过来：我们写回平台 |
| `/order/addressModify` | 卖家主动改收货信息 | 需与买家沟通过 |
| `/afterSale/List` `/afterSale/Detail` `/afterSale/Operate` | 售后列表 / 详情 / 审核 | 售后状态要能秒级感知并冻结订单 |

> 另有 `/order/batchEncrypt`、`/order/batchSensitive`（脱敏）等安全辅助接口。

### 3.3 风控安全 API

`/antispam/orderSend`、`/antispam/orderQuery` —— ISV 系统在展示/下载订单时须向平台风控上报事件。我们是商家自研自用，**是否同样强制上报需以官方最新文档为准**（列入 §9 待核实）。

### 3.4 物流与电子面单

- **强制使用抖音官方电子面单**：第三方/跨平台面单回填会被判「虚假发货」。
- 链路：取号 → 官方打印组件出带防伪水印的面单（解密在本地组件内完成，"可用而不可见"）→ 单号回传平台。
- 这是整个方案里**唯一没有替代路径**的一环，必须先具备。

### 3.5 飞鸽 / 三方客服 API（客服机器人的入口）

已核实存在的接口：

| method | 用途 |
|---|---|
| `/pigeon/updatePushUser` | 飞鸽消息推送店铺设置 |
| `/pigeon/workOrderNotify` | 更新或存储客服工单 |
| `/pigeon/ISVExecuteTool` | 执行 ISV 客服工具 |
| `/pigeon/GetPigeonToolList` | 获取飞鸽客服工具列表 |
| `/pigeon/ISVToolEventPreCheck` | ISV 工具可用性预检（含频控） |
| `/rights/getProductPrivileges` | 查商品服务权益（运费险/极速退款） |

`/rights/getProductPrivileges` 的文档明确列出属 **「三方客服 + 客服机器人」权限包** → **平台确实开放了"客服机器人"这一类目**。

> ⚠️ 当前公开列表里看到的多是**工具/工单类**接口，**没有**一个叫「接收/发送买家消息」的服务端 method。

**那自研客服到底怎么接？** 官方给了另一条路：**「飞鸽插件」**。

- 抖店开放平台 → **抖店应用** 下分四块：`开发基础` / `微应用` / `店铺装修` / **`飞鸽插件`**。飞鸽插件是嵌在飞鸽客服工作台里的前端应用。
- 官方 FAQ 里存在「关于飞鸽插件开发，**没有开发者模式权限**」「静态打包检测不通过」「onShow 首次进入插件时」等条目 → 说明**插件是官方支持的扩展点，但开发者模式权限需要单独开通**。
- 字节开源的 `mona` 运行时 README 提到前端可监听会话切换（「切换飞鸽左侧的用户时触发回调」），并注明**没申请 `user_id` 权限包就监听不到** → 能力存在，按权限包分级。

**结论（修正此前的假设）**：自研客服的现实路径是 **飞鸽插件（嵌在工作台内）**，**不是**服务端消息 API。能否做到全自动收发，要看开通插件权限后能拿到哪些 JS API —— 这一点必须在拿到开发者模式权限后实测（见 §9-2）。

### 3.6 消息推送

- 开放平台有独立「消息文档」分区，并存在《消息推送服务多地址使用指南》——可为不同店铺配置不同回调地址 → **HTTP 回调机制存在**。
- 与「抖店云」的关系已经清楚：**抖店云不是消息推送的前置条件**，它是另一套计费与部署选项（见 §3.1.1）。官方另有独立的**「数据推送」**产品（订单/售后推 RDS），走抖店云，**欠费即停止推送**。
- 仍待确认的只剩一件事：外网**长期**接收消息的稳定性（官方未承诺 SLA）。**这不影响方案**——按 §10 P1 的做法（增量拉取 + 5 分钟兜底），消息推送是加速项而非依赖项。

### 3.7 代发 API（本次不用，留作扩展）

`/iop/sellerDistribute`（商家分配代发）、`/iop/sellerOrderList` `/iop/sellerOrderInfo`（商家查看代发单）、`/iop/orderInfo`（厂商查看订单）、`/iop/sellerSupplierList`、`/iop/sellerCancleDistribute`。

> 若将来要接「给别的商家代发」，架构改动集中在这里 + 密文代发通道 + 工厂独立电子面单账户。

### 3.8 巨量千川 M-API（投流）

- 端点与文档：`open.oceanengine.com`，OAuth2 授权码模式。
- 能力覆盖：账户/余额、广告计划创建与调整、一键起量、人群包、**评论管理**（`/tools/comment/reply`、`/tools/comment/hide`、`/tools/comment/terms_banned/add` 等）、素材预审、即创 AIGC 元素管理。
- **2025-05 起全面「全域推广」**；2026 上线「千川·乘方」。

## 4. 客服机器人：三条路线

| | ① 官方飞鸽机器人 | ② 服务市场认证 ISV | ③ 自研（飞鸽插件） |
|---|---|---|---|
| 门槛 | 零 | 按月付费 | 开放平台自研应用（**含软著**）+ 飞鸽插件**开发者模式权限** |
| 能力 | 仅「智能辅助」，界面提示"请回到飞鸽客户端正常接待"；**不支持无人值守/云端值守** | 多轮对话、情感识别、催付跟单、聚合接待 | 按插件开放的 JS API 决定，**需开通权限后实测** |
| 数据 | 留在平台 | 留在第三方 | 留在自己手里 |
| 成本 | 0 | 数百~数千元/月/店 | 开发 + 模型 token |
| 风险 | 低 | 中（供应商资质/数据出境） | 中（权限审核、责任在己） |

**建议**：
- 起步阶段用 **①**，把高频 FAQ 沉淀成话术库；
- 一旦出现「3 分钟回复率」不达标、或夜间无人值守丢咨询 → 上 **②**；
- **③ 不要按"服务端收发消息"去设计**（公开 API 里没有这样的 method）。若要做，走 **飞鸽插件**，先申请开发者模式权限、摸清插件能拿到哪些能力再评估。
- 走 ③ 时，LLM 可复用本仓库既有网关 `api.vilavi.cn`（DeepSeek），仓库里已有 5 处调用范式（`EN_API/customs_export.py`、`dam-prototype/ai_pipeline.py`、`pb_reconciliation/visual_check.py`、`pdf_to_md/qwen_vl_md.py`、`amazon_pairing/judge.py`）。`intent_router/` 不适合直接用（TypeSafe Jev 决策模型、目录写死、只出标签不出话术），但它的「三态置信度闸门（ok/low_confidence/none）」可以直接借成「不确定就转人工」的判据。

## 5. 订单备注 → 一线生产（本次最具体的病）

### 5.1 先纠正误读

传闻「买家的特殊备注不能传到一线生产」，实际上平台限制的是：

- **收件人明文个人信息**（姓名/手机/详细地址）不得导出、复制、传给非必要人员；
- 手动解密 + 复制地址到外部系统 = **一级隐私违规**（单次扣 2–4 分，累计 12 分清退）；
- 未付款/已退款/待支付订单**严禁解密**，且解密有每日额度。

**业务指令本身（刻字内容、改尺寸、指定赠品、包装要求）没有禁止传递。** 要做的只是：**脱敏**（去掉夹带的手机号/地址）+ **最小必要**（车间只看与自己工序相关的那一条）。

### 5.2 备注分两类，处理方式不同

| 类型 | 例子 | 建议做法 |
|---|---|---|
| **结构化定制** | 刻字内容、尺码、颜色、包装方式、赠品选项 | **做成商品规格/参数**，下单时就是结构化字段 → 直接进 SO 行，零歧义 |
| **自由文本** | "麻烦发顺丰"、"不要放发票"、"周五前一定到" | 需判定：可执行的进工单；纯沟通类只给客服，不进车间 |

> 最有效的改进不是在备注上加 AI，而是**把能结构化的需求从备注里搬到商品规格**。备注越长，误判率越高。

### 5.3 推荐链路

```
抖店 /order/detail (buyer_words + 密文字段)
        │
        ▼
轻中间层（FastAPI）
  ├─ 幂等落库（order_id 唯一键）
  ├─ 备注脱敏（正则剥离手机号/地址片段）+ 类型判定（结构化 / 可执行 / 仅沟通）
  └─ 映射到 EN
        │
        ▼
EN（ERPNext）
  ├─ SO Item.description / custom_*  → 备注进入订单行
  ├─ Job Card → 车间工单看得到本工序要求
  └─ 打印格式（需新建）→ 随工单/拣货单一起出纸
```

### 5.4 EN 侧现有可复用字段（本仓库已核实）

| 载体 | 位置 | 说明 |
|---|---|---|
| `special_mark` | `Item Customer Detail` | 客户级永久特殊标记（如"该客户所有单不贴吊牌"） |
| `description` / `custom_tongtool_item_name` | Sales Order Item | 现有做法靠前缀拼接传递，可承载"本单"要求 |
| `custom_process_file_customer_item_code` / `custom_attach_file_customer_item_code` | SO 表头 | 已存在，可用于附加工艺文件 |
| `tracking_number`、`custom_is_subcontracting` 等 | Job Card | 工单层已有自定义字段先例 |

**缺什么**：**一个把备注打出来的打印格式**。目前 EN 只有批量二维码/标签，没有备注打印。

### 5.5 反例（不要这么做）

- ❌ 把备注塞进收件地址/电话字段 → 扩散明文，直接踩隐私红线；
- ❌ 让车间直接登抖店后台看订单 → 明文扩散到非必要人员；
- ❌ 中间层不落库、每次现查 → 抖店改单/退款后车间拿到旧数据。

## 6. 风控与合规红线（2026）

### 6.1 履约三红线

| 级别 | 判定 | 处罚 |
|---|---|---|
| 发货超时 | 现货 48h / 预售承诺时效内**无真实揽收** | 赔付实付 1%–5%；批量超时降体验分、限流 |
| 虚假发货 | 无效/重复单号、跨平台面单回填、打单无真实揽收、轨迹中断 | 赔付 25%；单日超标可冻结货款 |
| 欺诈发货 | 空包、小样抵货、货不对板、缺货拖延、无实物代发 | 赔付 30%；首次冻货款 30 天；年度 4 次 → 180 天 + 停业整顿 |

### 6.2 隐私与工具

- 一级隐私违规单次扣 **2–4 分**，累计 **12 分清退**、冻结保证金；
- 每日订单解密**有额度**；
- 平台要求用**服务市场认证工具**；浏览器插件/爬虫类工具被处罚的概率高（第三方文章称 68%，**标为第三方说法**）。

### 6.3 AI 直播（2026-02-01《直播电商监督管理办法》生效）

- AIGC/数字人直播必须**显著标识**并持续提示（业内口径：画面 1/10 以上区域标注"AI 生成"）；
- 虚拟人须平台注册，使用者实名认证，**必须真人驱动实时互动**；
- **禁止纯 AI 无人直播**；抖音另禁"录播循环伪装实时直播"；
- **运营者对 AI 生成内容造成的后果负全责**。

### 6.4 数据合规

- 个人信息最小必要：车间只需要「本工序要求」，不需要买家身份；
- 解密后的明文**不落盘、不进日志、不进群聊**；
- 中间层要有操作审计（谁在什么时候查了哪个单）。

## 7. EN 能承担什么 / 不能承担什么

### 7.1 现状（本仓库已核实）

| 能力 | 现状 |
|---|---|
| 外部系统推订单进 EN | **无**入站 webhook、无接收端；SO 来源是手工上传 Excel（`EN_API/so_item_special_mark/`） |
| 认证 | 仅 `Authorization: token <key>:<secret>`；**无 OAuth2**；未实现入站签名校验 |
| 客服/工单 | **未使用** Issue / HD Ticket / Helpdesk |
| 抖音相关 | 仓库内**零**代码 |
| 打印 | 仅批量二维码/标签，**无备注打印** |

### 7.2 先纠正一个说法：不是「EN 不能做」，而是「哪些该买、哪些该造」

用户的质疑是对的：EN 可以随便定制，`tongtool_integration` 就是"单向拉取 + 写单"的先例；轻中间层同样要写代码，只是放在别处。所以「EN 不适合当 OMS」这种说法**不准确**，应改为：

- **该自己造的**：订单接入（拉单、幂等、备注判定、写 SO）。这件事我们有先例、有掌控权、量不大 → **直接做成 EN 的独立 app，和 `tongtool_integration` 同构**，不必多养一个 FastAPI 服务。
- **该买/用平台的**：面单取号与打印（官方组件）、售后审核界面、波次拣货、客服工作台。这些是商品化的东西，自己造要几个月，且要跟着平台规则一直改。
- **不要做的**：把"电商作业台"（拣货波次、面单池、售后审核台、客服会话）塞进 ERPNext。不是因为做不到，而是**投入产出不划算 + 改坏会波及生产**。

**因此原方案修正为**：优先 `douyin_integration`（EN app）而非外挂中间层；中间层仅在「不想动 EN 服务器」或「需要独立扩缩容」时才成立。

### 7.3 分工建议

| 环节 | 谁做 | 理由 |
|---|---|---|
| 拉单、幂等、改单/退款感知 | **EN 独立 app**（或外挂中间层） | 与 `tongtool_integration` 同构 |
| 备注脱敏 + 三类判定 | **EN 独立 app** | 判定逻辑要跟着业务改 |
| 面单取号与打印 | 抖店官方电子面单 + 打印组件 | **唯一不能自研的一环** |
| 售后审核 | 前期抖店后台人工；量大再评估 | 审核规则常变 |
| BOM、生产工单、Job Card、工序派工 | **EN** | 现有强项 |
| 物料/库存/采购/出货 | **EN** | 现有强项 |
| 客户备注 → 工序要求 | app 判定 → **EN**（需新建打印格式） | 缺一个打印格式，约 1 人天 |
| 客服会话 | 官方机器人 / ISV / 飞鸽插件 | 见 §4 |

### 7.4 三个架构选项

**A. `douyin_integration`（EN 独立 app，推荐）**
- 和 `tongtool_integration` 同一形态：Frappe app、定时拉取、写 SO、回传单号。
- 优点：不新增服务、复用现有部署链路（测试建分支 → migrate → 合并 → 生产 pull + migrate + restart）、权限与审计复用 Frappe。
- 代价：改 EN 服务器，需要用「生产只读查询也会压垮站点」的纪律（见本仓库既有教训）约束拉单频率与索引。
- 适用：单量中等、SKU 以自制为主。

**B. 外挂轻中间层（FastAPI）+ EN 只做生产**
- 复用 `sellfox-api-proxy/`（Bearer key + 限流 + token 缓存 + 声明式多账号）与 `web_automation/scripts/dispatch.py`（状态字面量 + 写操作强制确认）。
- 适用：需要独立扩缩容、或不想让平台调用打到生产 EN。

**C. 买成熟 OMS（聚水潭/万里牛/旺店通）+ EN 只做生产**
- 现成的波次、面单、售后、对账。
- **额外优势**：它已有软著与平台资质，**不受 §3.0 的 1–3 个月软著门槛限制**。
- 适用：想尽快开卖、或日单量上千、或一店变多店。

## 8. 直播策划与投流：标准做法 + SOTA

### 8.1 标准 SOP（业界通用）

1. **对标**：找 10+ 个同赛道直播间，拆人货场；
2. **人货场**：主播人设 / 货盘结构 / 场景与贴片；
3. **排品**：引流款（低价高频）+ 主推款（利润）+ 福利款（回馈），首场不超过 3 款；
4. **脚本**：开场钩子 → 产品讲解 → 逼单 → 循环；
5. **中控**：弹窗、改价、发券、口播配合；
6. **复盘指标**：GPM（千次观看成交）、UV 价值、平均停留、互动率、转化率、退货率。

### 8.2 投流现状（2026）

- **全域推广**成为默认：短视频 + 直播 + 商品卡/搜索打通，付费与自然流不再严格区分；
- **AI 接管定向**：多数字商家不能再手动设年龄/性别/地域/兴趣/达人相似 → **竞争点从"投手技巧"转向"内容向量化"**（标题关键词、画面场景物、主播妆造、话术、评论都会被算法解析成标签）；
- 成本：CPM 约 80 元（2023）→ 120 元（2026）；有品牌 ROI 从 1:3 降到 1:1.5；
- **千川·乘方**（千策 / 千意 / 千寻）：一个总预算 + 一个综合 ROI 目标 → 系统自动分配预算、出价、选品；AI 动态创意与"智投星"诊断；多模态需求预判。

### 8.3 AI 能用的地方（按风险从低到高）

| 用途 | 风险 | 说明 |
|---|---|---|
| 脚本/话术生成、卖点提炼 | 低 | 用 LLM 批量产出，人工定稿 |
| 短视频素材批量生成（即创/即梦） | 低-中 | 需注意素材同质化与平台查重 |
| 评论区/私信回复 | 中 | 属客服机器人范畴，见 §4 |
| 直播切片、二创 | 中 | 注意肖像权与音乐授权 |
| **数字人直播** | **高** | 必须标识 + 注册 + 真人驱动；纯无人直播被禁 |
