# 抖音直播电商生态调研

> 2026-11-10。适用前提：**自营品牌直播 + 自有工厂生产发货**（不是给第三方代发）。
> 阅读顺序建议：先看 §1 结论，再看 §5（备注传产线，本次最具体的病）与 §7（EN 能干什么），其余按需。
> 面向管理层的精简版见 [管理层版](2026-11-10-douyin-live-commerce-management-brief.md)。

---

## 1. 结论摘要（TL;DR）

1. **能自建，但有一道 1–3 个月的硬门槛：软著。** 抖店官方 FAQ 明确「调用接口必须先申请资质，创建完应用才可以调用接口」，且软著**必须**由国家版权局颁发、著作权人须与店铺主体一致、须在 `ccopyright.com.cn` 可查，**没有替代材料**；软著常规审核 30–60 个工作日。ERPNext 本体是 GPLv3、著作权属 Frappe，**不能**拿来登记；要登记的是我们自研的 app。自研应用审核本身只要 1–3 个工作日，卡点在软著。
2. **订单、售后、电子面单、客服机器人、投流都有官方接口。** 但「直播间弹幕」没有面向商家的官方接口 —— 官方那套属于「直播小玩法」，要抖音云 + 内网专线，不是运营口径。
3. **"买家备注传不到一线生产"是误读。** 平台限制的是**收件人明文个人信息**的流转，不是业务指令本身。备注里的定制要求（刻字、改尺寸、指定包装）可以传；要做的是把备注里的手机号/地址先脱敏。
4. **订单接入优先做成 EN 的独立 app（与 `tongtool_integration` 同构），不要另起服务。** 但「电商作业台」（波次拣货、面单池、售后审核台、客服会话）应该用现成的——不是做不到，是不划算且会波及生产。
5. **真正的风险不是技术，是履约处罚。** 2026 年发货三红线（超时 1–5%、虚假发货 25%、欺诈发货 30% + 冻货款）＋ 隐私违规累计 12 分清退。合规动作比接 API 更优先。
6. **自研有大量真实先例**（见 §11）：开源全套 OMS（启航电商）、Java/PHP/Python/Go/Spring 多语言 SDK、生产踩坑文都能点开验证。技术上确实不是问题，成本在**资质（软著 1–3 个月）**与**平台规则长期维护**。

## 2. 生态全景：一条直播链路拆成 6 层

| 层 | 干什么 | 平台官方 | 服务市场 ISV | 自建 |
|---|---|---|---|---|
| ① 流量内容 | 短视频/直播引流、素材生产 | 千川·乘方（千策/千意/千寻）、即创/即梦 | 代运营、素材工厂 | AI 批量出素材（见 §8） |
| ② 交易订单 | 下单、订单同步、改价/改址 | 抖店订单 API、消息推送 | 聚水潭/万里牛/旺店通/我打 | 自研应用 + 中间层 |
| ③ 履约发货 | 打单、取号、回传、拦截 | **抖音官方电子面单（强制）**、物流 API | 同上 + 风火递/抖掌柜类 | 不建议自研面单链路 |
| ④ 客服 | 售前咨询、催付、售后沟通 | 飞鸽客户端 + 官方机器人（仅"智能辅助"） | 晓多/探域等认证 ISV | 客服消息权限包 + 自建 LLM |
| ⑤ 售后 | 退款/退货/换货审核、拦截 | 售后 API（`/afterSale/*`） | OMS 内置 | 可自建但价值低 |
| ⑥ 数据复盘 | GPM、UV 价值、停留、转化 | 罗盘/百应后台 | 飞瓜、蝉妈妈 | 待核实是否有官方接口 |

**判断**：②③④ 是必须打通的；① 是运营活，⑤⑥ 可以先用现成后台。

## 3. 平台接口盘点（抖店开放平台）

### 3.0 申请门槛：软著是硬门槛，且不能先开发后补

官方 FAQ 原文（[应用创建常见问题](https://op.jinritemai.com/docs/question-docs/103/3226)，2025-02-14）：

> 很抱歉，调用接口必须先申请资质，创建完应用才可以调用接口。
> 软著的要求：**必须提供由国家版权局颁发的软件著作权证书扫描件或照片**，著作权人需与您店铺 & 开发者实名认证一致，且能够在中国版权保护中心官网（http://www.ccopyright.com.cn/）**查询到有效信息。其他软著认证平台均不符合要求。**

**为什么开个 API 还要软著？**（这是最容易被当成"刁难"的一条，值得说透）

软著**不是考你的技术**，是给平台一个**能把责任落地的锚点**。平台作为"平台经营者"，在《电子商务法》《个人信息保护法》《数据安全法》下对第三方接入的数据访问负监管责任。它需要证明三件事：

1. **这套系统是谁的** —— 软著著作权人 = 店铺主体 = 开发者实名，三者一致，出事能找到人；
2. **不是批量空壳** —— 软著登记有实质审查，挡掉大量注册即用的账号；
3. **不是套壳转卖** —— 主体一致约束住了"借别人资质接进来"（这也正是 §3.0 后面说的"挂靠 ISV 违规"同一条线）。

所以本质是：**平台把法律上的监管责任，转成了一道可执行的行政闸门**。这不是中国特有——Shopify 用 "protected customer data 审核 + app review"，亚马逊用 SP-API 开发者注册，**目的完全一样，只是形式不同**；中国选了"软著"这个成本最低、最容易被验证的形式。

推论：**它不会因为你是小商家就免**，也不会因为你只是想"客服机器人 + 订单处理"就免。好消息是软著本身不难办（材料就是源码+说明书），难的是**等 1–3 个月**——这段时间用 §7.5 的 Excel 桥跑业务。

推论（三条，都影响排期）：

1. **顺序不可绕过**：资质 → 软著 → 创建应用 → 才能调接口。想"先开发测试完再补软著"的路径**不通**。
2. **ERPNext 本体不能用于登记**：它是 GPLv3，著作权属 Frappe Technologies，不是我们的主体。能登记的是**我们自己写的 app**（如 `key_test`、`tongtool_integration` 这一类）。2026-03 中国版权保护中心新规还明确打击"拿开源项目改名套壳"，审核会做代码相似度比对。
3. **软著周期 30–60 个工作日**（常规），加急可压到几个工作日但费用高。这是 P1 的**关键路径**，比写代码慢得多。

> ⚠️ 2026-03 新规的两个摩擦点（来源为行业解读，需以版权中心最新公告为准）：申请表新增**手抄承诺「本软件为独立开发，未使用 AI 编写代码、撰写文档或生成申请材料」**；审核引入 **AI 代码相似度比对**。若我们的代码大量由 AI 生成，这一段存在如实声明与通过率之间的张力 —— 申请前应先按实际情况评估，**不要抱着"先交了再说"的心态**，失实会被列入版权登记失信名单。

**若没有软著、又不想等 1–3 个月**：只有两条合规路径 —— ① **订购**服务市场现成 ISV 工具（我们是买家）；② **委托** ISV 定制开发（交付主体是服务商）。或先用人工/导出过渡（见 §7.5）。

> ⚠️ **"挂靠 ISV 资质"是违规的，不要走这条路。** 《服务商违规处罚及退出机制》把「未经平台授权，将所涉服务**转委托**给第三方」「滥用、售卖平台提供的产品服务接口」「将账号擅自借给其他第三方使用」列为一**级违规**，处罚含公示警告、扣除全额保证金、**清退**。所以不存在"借别人的软著/应用来调我们自己的系统"这种合规形态。另注意：**「AI 智能客服」是「客服工具」一级类目下的二级类目，面向服务商开放**，不是商家自研类目。

### 3.0.1 委托代理办软著：正常操作，但"贴假代码"这条别听

> 背景：2026-11 有同行建议「给钱找代理就行，粘一点假代码进去都行」。**前半句对，后半句在 2026-03 之后已经变成高风险动作。**

**先说对的**：找代理办软著是**完全正常、合法**的行业实践。代理帮你整理源码（前后各 30 页）、写说明书、规范命名，收费几百到两千，这是正经服务，没人觉得有问题。

**再说变了的**：2026-03-15 中国版权保护中心发布《关于共同维护计算机软件版权登记良好生态的通知》，新版申请表当日起施行，直接针对"贴假代码"这类做法：

| 变化（多家媒体与地方软件行业协会一致报道） | 对我们的影响 |
|---|---|
| 功能描述从 200 字提到 **500–1300 字**，要求写清研发背景/架构/模块/技术实现 | 模板话术会被退回 |
| 签章页要求**经办人黑色中性笔手抄承诺 + 签名 + 身份证号** | **责任落到具体个人**，不是公司抽象承担 |
| 承诺原文含「本软件确系**人的独立开发，未使用 AI 开发**编写代码、撰写文档或生成登记申请材料」 | 我们代码有 AI 参与 → 如实评估，别签假承诺（见下方） |
| 承诺含「如有失实或欺骗，**自愿承担列入版权登记失信名单及个人征信记录**」 | 这是个人征信，不是罚款了事 |
| 明确**整治代理的"虚假承诺、模板化申报、批量代写"** | 那句"假代码也行"正是被点名的对象 |

**三条法律事实**（比传言可靠）：

1. **登记证书只是"初步证明"**——《计算机软件保护条例》第 7 条原文。真打官司，法院看的是实际开发证据（git 记录、需求文档、部署记录），假代码撑不住。
2. **撤销需要生效文书**——《计算机软件著作权登记办法》第 23 条：国家版权局依据**最终司法判决**或**著作权行政管理部门行政处罚决定**撤销登记。所以不是"一举报就撤"，但一旦走到那一步就是确定性的。
3. **把他人软件作为自己的软件登记，本身构成侵权**——《计算机软件保护条例》第 23 条。用开源代码或别人的代码冒充，法律上是侵权，不只是"材料不实"。

**给我们的具体做法**：

| 该做 | 不该做 |
|---|---|
| 找代理可以，但**指定用我们的真实源码、真实界面截图、真实功能描述** | 让代理代写代码、PS 截图、套模板 |
| 合同里写明：**材料真实性由我方提供，代理方不得代生成代码或伪造截图** | 接受"包过""不用你管材料"的承诺 |
| 代码量不足 60 页：**合并多个真实 app 申报一套系统**，或按法规"不足 60 页全部提交" | 为凑页数粘贴无关代码 |
| 留存证据链：git 提交记录、需求文档、部署截图、服务器日志 | 只留一张证书 |

**关于 AI 生成代码这条**（最现实的摩擦点）：新规承诺要求"未使用 AI 开发"。我们代码确实有 AI 参与。稳妥做法是**先按实际情况评估、必要时向版权中心或专业代理确认是否需要补充说明**，而不是签了承诺再说。行业解读里有"提交《AI 使用说明》"的说法，但我**未在官方通知中核实到该要求**，暂不作为依据。

> **一句话**：这条捷径对我们**没有任何收益**——我们本来就有真代码（`key_test`、`tongtool_integration`、本仓库脚本）。花同样的钱用真代码，风险为零；贴假代码，风险全落在签承诺书的那个人身上。

### 3.0.2 自办还是找代理：渠道、费用、周期、代码保护

**结论先行**：软著**可以自己线上办，不必经中介**；担心源码外泄，法规里有**例外交存**和**封存**两种机制。找代理买的是"省事+补正响应"，不是"必需的通道"。

#### 一、官方渠道（北京，唯一登记机构）

- **中国版权保护中心**是国家版权局认定的**唯一**软件著作权登记机构，官网线上提交即可，2023-06 无纸化后只发电子证书。
- 流程：注册/实名认证（1–2 工作日）→ 在线填表上传 → 受理（3–5 工作日）→ 审查（**60 自然日**）→ 公告 + 下载电子证书。
- 北京设有登记大厅，但常规申请不需要跑现场。

#### 二、费用：分清"官费"和"服务费"（这是最大的坑）

| 项 | 事实 |
|---|---|
| **官方登记费** | **2017-04-01 起已停征**。中国版权保护中心《关于停征软件著作权登记缴费有关事项的通告》原文："自 2017 年 4 月 1 日起停止执收软件著作权登记费。"（新华社同日报导） |
| **代理服务费（2026 市场区间）** | 基础代提交 **500–800**；标准（含预审/材料整理/补正）**800–1500**；加急 **1500–3000**；高端定制 3000+。大厂平台：阿里云 399（自助）～2200（安心）、华为云市场 300–598 起 |
| **加急** | 各来源说法矛盾：2022 年有"加急官费 1000 元/件、档期 21–30 工作日"的说法；2026 年有"官方无加急通道、加急属第三方增值服务"的说法。**以版权中心官网当期公示为准** |
| **例外交存/封存** | 属附加事项，可能单独收费（有报价 320 元/件次），以官方为准 |

> ⚠️ **警惕**：不少代理把"服务费"包装成"官费"报给你（如"官费 300 元"），与 2017 年停征通告冲突。**要求分项报价：官费多少、服务费多少、加急费是否单独算。**

#### 三、审查要求（2026，材料层面）

| 材料 | 硬要求 |
|---|---|
| 申请表 | 线上填；签章页打印→签字/盖章→扫描回传；**功能描述 500–1300 字**（2026 新规） |
| 源程序 | **前后各连续 30 页（共 60 页）**；每页 **≥50 行**；不足 60 页**全部提交**；页眉标软件名+版本号；页码 1–60；**第 60 页须是完整模块结尾** |
| 文档 | 用户手册/设计说明书任选一；前后各 30 页；每页 **≥30 行**（有图除外）；截图要**含标题栏/菜单栏的完整界面**；实操上 13–15 页较稳 |
| 身份证明 | 营业执照副本盖章、法人身份证、授权委托书（如代办） |
| 权属 | 合作/委托开发需合同 |
| 一致性 | **软件名称、版本号、开发完成日期在申请表/代码/文档三处必须完全一致**；开发完成日期晚于公司成立日期 |
| 补正 | 收到通知 **30 日内**补正，逾期视为撤回 |

> 行业文章还提到：同一主体**每日申请不超过 3 份**（否则触发批量预警）、开源组件需附协议与自有代码边界说明（2026 新增）。这两条我未在官方通知中核实，**按"宁可遵守"处理**。

#### 四、真代码怕外泄？法规给了两条路

《计算机软件著作权登记办法》**第十二条**（例外交存，三选一）：

1. **前后各 30 页，机密部分用黑色宽斜线覆盖**，覆盖面积**不得超过**交存源程序的 **50%**；
2. 源程序**连续前 10 页 + 任意部分连续 50 页**（避开核心算法段）；
3. **目标程序**前后各 30 页 + 源程序任意连续 20 页（泄露风险最低）。

**第十三条**（封存）：登记时可申请将源程序、文档或样品**封存**，"除申请人或者司法机关外，任何人不得启封"。

**落到操作上，三层保护**：

| 做法 | 效果 |
|---|---|
| **自己线上提交，不经中介** | 源码根本不离开公司 |
| 必须找代理时：**只给已排好版的前后 30 页 PDF**（含页眉页码），**不给整个仓库** | 中介拿到的是可提交的成品，不是可编译的代码 |
| 核心算法敏感：**用第 2 或第 3 种例外交存** + 签 NDA | 避开核心段，法律上也站得住 |

> 注意：**例外交存不是"造假"**，它是法规明写的保密方式，代价只是"交存的证据少一些"，将来维权的举证会弱一点。这跟"贴假代码"是两回事。

#### 五、"AI 写的代码"怎么办（如实处理，别签假承诺）

- 新规承诺原文要求"**未使用 AI 开发**编写代码、撰写文档或生成登记申请材料"。
- 行业文章建议：确有 AI 辅助的，提交《AI 使用说明》，说明人类主导、人工贡献比例、开源来源。**该要求我未在官方通知核实**。
- 稳妥做法：**先向版权中心或正规代理确认口径**，再填承诺；不要把"AI 生成"写成"独立开发"。

#### 六、选代理的筛选标准（北京本地同理）

| 该看 | 红旗 |
|---|---|
| 营业执照 + 知识产权服务经营范围（国家企业信用信息公示系统可查） | 只说"包过""不用你管材料" |

### 3.1.1 API 收费与「云内 / 云外」（官方规则 V1.3，2026-06-16）

《抖店开放平台技术服务费规则》原文表：

| API 类型 | 抖店云内调用 | 抖店云外调用 |
|---|---|---|
| 基础 API | 0.018 元/百次/AppKey | **0.18 元/百次/AppKey（×10）** |
| 增值 API | 0.05 元/百次/AppKey | 0.5 元/百次/AppKey，**未经允许禁止云外调用** |

**已核实：`/order/batchDecrypt`（批量解密）在官方《收费接口列表》里属「基础 API」**，与 `/order/searchList`、`/order/orderDetail`、`/afterSale/List`、`/afterSale/Detail` 同类。也就是说**云外可以调用，只是单价 ×10**。

> 有一条流传的说法是「2023-08-31 起自研涉及订单解密的必须部署抖店云、云外解密权限关闭」。该说法我在官方收费规则与收费接口列表里**没有找到对应条款**，暂按「待工单确认」处理。**但它不影响主方案** —— 我们推荐的是**密文打单**（官方电子面单组件在本地解密），本来就不调用 `batchDecrypt`。

**换算成钱**：按日 500 单、每单 2 次调用、售后翻倍估算 ≈ 6 万次/月 → 云外约 **108 元/月**。量级可忽略，**不构成"必须上抖店云"的理由**。

> 另有独立产品「数据推送」（抖店云 → RDS）与「消息推送」，与 API 收费是两套机制；欠费时数据推送会**停止推送**，这点比 API 限流更致命。

### 3.4 物流与电子面单

- **强制使用抖音官方电子面单**：第三方/跨平台面单回填会被判「虚假发货」。
- 链路：取号 → 官方打印组件出带防伪水印的面单（解密在本地组件内完成，"可用而不可见"）→ 单号回传平台。
- 这是整个方案里**唯一没有替代路径**的一环，必须先具备。

**发货之后会发生什么（闭环）**：

```
取号 → 打印官方面单 → 点"发货" → 单号与轨迹由平台闭环同步
                                    ↓
                    买家侧自动看到物流；平台按真实揽收时间考核 48h/承诺时效
                                    ↓
                    售后拦截/改址 通过 /afterSale/* 与 /order/addressModify
```

- **单号不需要我们"回传"到别处**——用官方组件发货时，平台自己就记录了；我们要做的是把**订单号 ↔ 包裹**的关系写进 EN，方便车间和售后查。
- **考核看的是"真实揽收时间"**，不是"我们点发货的时间"。所以"提前点发货、后补单号"这类操作会踩虚假发货。

**和跨境 TikTok 的差别**（你提到"差不多"，形态像、约束不同）：

| | 抖店（国内） | 跨境 TikTok Shop |
|---|---|---|
| 面单 | **强制官方电子面单** | 视渠道：部分用平台面单，多数自发货自填 tracking |
| 单号 | 平台闭环，人看不到明文地址 | 通常手动/接口上传运单号 |
| 考核 | 真实揽收时间、虚假发货重罚 | 有发货时效要求，但判罚口径不同 |
| 结论 | 你不能"自己找快递打单"，必须走官方组件 | 自由度更高，但要自己保证轨迹 |

所以抖店这边**比跨境更"锁死"**：打单这一环没有自研空间，只能对接官方组件。

**那自研客服到底怎么接？** 官方给了另一条路：**「飞鸽插件」**。

**结论（修正此前的假设）**：自研客服的现实路径是 **飞鸽插件（嵌在工作台内）**，**不是**服务端消息 API。能否做到全自动收发，要看开通插件权限后能拿到哪些 JS API —— 这一点必须在拿到开发者模式权限后实测（见 §9-2）。

### 3.6 消息推送

## 4. 客服机器人：三条路线

| | ① 官方飞鸽机器人 | ② 服务市场认证 ISV | ③ 自研（飞鸽插件） |
|---|---|---|---|
| 门槛 | 零 | 按月付费 | 开放平台自研应用（**含软著**）+ 飞鸽插件**开发者模式权限** |
| 能力 | 仅「智能辅助」，界面提示"请回到飞鸽客户端正常接待"；**不支持无人值守/云端值守** | 多轮对话、情感识别、催付跟单、聚合接待 | 按插件开放的 JS API 决定，**需开通权限后实测** |
| 数据 | 留在平台 | 留在第三方 | 留在自己手里 |
| 成本 | 0 | 数百~数千元/月/店 | 开发 + 模型 token |
| 风险 | 低 | 中（供应商资质/数据出境） | 中（权限审核、责任在己） |

**建议**：
- 起步阶段用 **①**，把高频 FAQ 沉淀成话术库；
- 一旦出现「3 分钟回复率」不达标、或夜间无人值守丢咨询 → 上 **②**；
- **③ 不要按"服务端收发消息"去设计**（公开 API 里没有这样的 method）。若要做，走 **飞鸽插件**，先申请开发者模式权限、摸清插件能拿到哪些能力再评估。
- 走 ③ 时，LLM 可复用本仓库既有网关 `api.vilavi.cn`（DeepSeek），仓库里已有 5 处调用范式（`EN_API/customs_export.py`、`dam-prototype/ai_pipeline.py`、`pb_reconciliation/visual_check.py`、`pdf_to_md/qwen_vl_md.py`、`amazon_pairing/judge.py`）。`intent_router/` 不适合直接用（TypeSafe Jev 决策模型、目录写死、只出标签不出话术），但它的「三态置信度闸门（ok/low_confidence/none）」可以直接借成「不确定就转人工」的判据。

### 4.1 官方机器人：免费，但没有 token 费也不等于"能自己长脑子"

官方学习中心原文：**「飞鸽机器人推出了『智能辅助模式』，抖店商家直接使用，无任何收费项」**（[抖音电商学习中心](https://school.jinritemai.com/doudian/wap/article/aHKFgnqDGxVs)）。

| 项 | 事实 |
|---|---|
| 费用 | **免费，无坐席费、无 token 费** |
| 模型 | 字节自有，不可替换 |
| 知识/话术 | 后台配置（话术模板库、关键词、知识库）—— **需要人工录入**；是否支持 Excel/文档批量导入，公开文档未写清（见 §9-8） |
| 模式 | **只能"辅助"**，界面提示"请回到飞鸽客户端正常接待"；不做无人值守 |
| 备案 | 模型已由平台备案，商家无额外备案负担 |

**所以你的判断成立**：官方机器人省的是钱，不省人力——话术还是得人往里填。想让它"自己长脑子"，官方给不了。

### 4.2 先分清：客服机器人 ≠ 直播弹幕（这一步最容易搞错）

老板娘说的"客服机器人"，**大概率是飞鸽私信，不是直播间公屏**。两者是两套系统：

| | **飞鸽客服**（买家咨询） | **直播间弹幕 / 公屏评论** |
|---|---|---|
| 入口 | 商品页 / 订单页 / 直播间点"联系客服" → **私聊** | 直播画面下方公屏，**所有人可见** |
| 谁能看到 | 只有客服和该买家 | 所有观众 + 主播 |
| 核心 KPI | **3 分钟回复率**、体验分、询单转化 | 互动率、平均停留、直播间氛围 |
| 官方 API | **无收发消息接口**；只有工具/工单类 + 飞鸽插件 | 无商家侧接口；只有"直播小玩法"专用通道 |
| 自研可行路线 | 飞鸽插件（需开发者权限）/ 插件模拟 | 中控台 Playwright（只读或只发） |
| 代表性开源件 | `ChatGPT-On-CS`（Electron 客户端） | `oba-live-tool`（Electron + Playwright） |

**结论**：如果第一步是"客服机器人"，`oba-live-tool` 那类**基本不相关**（它做的是直播中控台：弹幕、商品弹窗、自动发言）；相关的是官方飞鸽机器人、ISV，或 `ChatGPT-On-CS` 这类飞鸽客户端。

**第一步的正确顺序**：
1. 抖店后台开官方「智能辅助」+ 填 50 条高频话术（今天，0 元）；
2. 观察 3 分钟回复率是否稳定 ≥ 平台线；
3. 不够 → 买 ISV（有资质、当天可用）；
4. 要完全自主 → 等软著 + 飞鸽插件权限（季度级）。

> 直播弹幕那边，只做"只读看板/消息提醒"风险可控；**自动发言、刷互动属平台打击的"虚假人气"，不要做**。

### 4.3 一个常被忽略的事实：平台不是"技术做不到"，是"选择性开放"

业内普遍的看法（如《为什么淘宝、抖音都不能接入第三方AI客服机器人？》一文）是：**接口是有的，只是不对商家自研开放**，客服能力被收拢到服务市场 ISV。

官方口径是"数据安全与责任可追溯"，业内解读是"客服行业话语权与商业生态"。两者可能同时成立。**对我们最重要的推论只有一条**：这是**商业决策**，不是技术限制，因此**不存在"技术方案绕过它"的合法路径**——要么走官方通道，要么走灰区（模拟），没有第三条。

### 4.4 自研 / 接外部模型的真实边界（三条，都来自一手或开发者实测）

1. **飞鸽没有"发送消息"的服务端接口。** 一位长期做该场景的开发者（唯一客服系统作者）原话：「抖音官方店铺对接大模型，抖音官方有没有接口？那肯定是没有接口了」「飞鸽客服是没有发送消息的接口的，**只能通过模拟的形式**（浏览器插件）在输入框里输入再点发送」。市面上所有"抖店 AI 客服接大模型"（含开源 ChatGPT-On-CS、gofly 等）本质都是**浏览器/Electron 模拟**。
2. **官方给自研的口子是飞鸽插件**（嵌在工作台内），需要 `开发者模式权限`，能力边界未公开。
3. **⚠️ 算法备案是容易被忽略的合规门槛。** 按《互联网信息服务算法推荐管理规定》第 24 条与《生成式人工智能服务管理暂行办法》第 17 条，面向公众提供生成式 AI 服务需备案；其中「调用第三方已备案模型 API、未做实质训练」需 **算法备案 + 大模型登记**（行业解读称约 3–5 个月），「自研或深度微调」需 **算法备案 + 大模型备案**（约 6–9 个月）。责任主体按「用自己账号对外提供服务」认定 —— **商家自建 AI 客服同样可能被认定为服务提供者**。
   > 该段的法律依据是真实法规，但"电商客服是否必然触发、适用哪一档"属行业解读，**需法务或网信部门确认**，本文不写成定论。

**结论**：接外部/自研模型技术上能做（插件模拟），但要走完 **软著 + 飞鸽插件权限 + 可能的算法备案** 三关，周期以季度计；而官方机器人为零成本、零备案。所以"先用官方顶住、同时把知识库沉淀成结构化数据（这条路以后接自研也能直接复用）"是更稳的顺序。

## 5. 订单备注 → 一线生产（本次最具体的病）

### 5.1 先纠正误读

传闻「买家的特殊备注不能传到一线生产」，实际上平台限制的是：

- **收件人明文个人信息**（姓名/手机/详细地址）不得导出、复制、传给非必要人员；
- 手动解密 + 复制地址到外部系统 = **一级隐私违规**（单次扣 2–4 分，累计 12 分清退）；
- 未付款/已退款/待支付订单**严禁解密**，且解密有每日额度。

**业务指令本身（刻字内容、改尺寸、指定赠品、包装要求）没有禁止传递。** 要做的只是：**脱敏**（去掉夹带的手机号/地址）+ **最小必要**（车间只看与自己工序相关的那一条）。

### 5.2 备注分两类，处理方式不同

| 类型 | 例子 | 建议做法 |
|---|---|---|
| **结构化定制** | 刻字内容、尺码、颜色、包装方式、赠品选项 | **做成商品规格/参数**，下单时就是结构化字段 → 直接进 SO 行，零歧义 |
| **自由文本** | "麻烦发顺丰"、"不要放发票"、"周五前一定到" | 需判定：可执行的进工单；纯沟通类只给客服，不进车间 |

> 最有效的改进不是在备注上加 AI，而是**把能结构化的需求从备注里搬到商品规格**。备注越长，误判率越高。

### 5.3 推荐链路

```
抖店 /order/detail (buyer_words + 密文字段)
        │
        ▼
轻中间层（FastAPI）
  ├─ 幂等落库（order_id 唯一键）
  ├─ 备注脱敏（正则剥离手机号/地址片段）+ 类型判定（结构化 / 可执行 / 仅沟通）
  └─ 映射到 EN
        │
        ▼
EN（ERPNext）
  ├─ SO Item.description / custom_*  → 备注进入订单行
  ├─ Job Card → 车间工单看得到本工序要求
  └─ 打印格式（需新建）→ 随工单/拣货单一起出纸
```

### 5.4 EN 侧现有可复用字段（本仓库已核实）

| 载体 | 位置 | 说明 |
|---|---|---|
| `special_mark` | `Item Customer Detail` | 客户级永久特殊标记（如"该客户所有单不贴吊牌"） |
| `description` / `custom_tongtool_item_name` | Sales Order Item | 现有做法靠前缀拼接传递，可承载"本单"要求 |
| `custom_process_file_customer_item_code` / `custom_attach_file_customer_item_code` | SO 表头 | 已存在，可用于附加工艺文件 |
| `tracking_number`、`custom_is_subcontracting` 等 | Job Card | 工单层已有自定义字段先例 |

**缺什么**：**一个把备注打出来的打印格式**。目前 EN 只有批量二维码/标签，没有备注打印。

### 5.5 反例（不要这么做）

- ❌ 把备注塞进收件地址/电话字段 → 扩散明文，直接踩隐私红线；
- ❌ 让车间直接登抖店后台看订单 → 明文扩散到非必要人员；
- ❌ 中间层不落库、每次现查 → 抖店改单/退款后车间拿到旧数据。

## 6. 风控与合规红线（2026）

### 6.1 履约三红线

| 级别 | 判定 | 处罚 |
|---|---|---|
| 发货超时 | 现货 48h / 预售承诺时效内**无真实揽收** | 赔付实付 1%–5%；批量超时降体验分、限流 |
| 虚假发货 | 无效/重复单号、跨平台面单回填、打单无真实揽收、轨迹中断 | 赔付 25%；单日超标可冻结货款 |
| 欺诈发货 | 空包、小样抵货、货不对板、缺货拖延、无实物代发 | 赔付 30%；首次冻货款 30 天；年度 4 次 → 180 天 + 停业整顿 |

### 6.2 隐私与工具

- 一级隐私违规单次扣 **2–4 分**，累计 **12 分清退**、冻结保证金；
- 每日订单解密**有额度**；
- 平台要求用**服务市场认证工具**；浏览器插件/爬虫类工具被处罚的概率高（第三方文章称 68%，**标为第三方说法**）。

### 6.3 AI 直播（2026-02-01《直播电商监督管理办法》生效）

- AIGC/数字人直播必须**显著标识**并持续提示（业内口径：画面 1/10 以上区域标注"AI 生成"）；
- 虚拟人须平台注册，使用者实名认证，**必须真人驱动实时互动**；
- **禁止纯 AI 无人直播**；抖音另禁"录播循环伪装实时直播"；
- **运营者对 AI 生成内容造成的后果负全责**。

### 6.4 数据合规

- 个人信息最小必要：车间只需要「本工序要求」，不需要买家身份；
- 解密后的明文**不落盘、不进日志、不进群聊**；
- 中间层要有操作审计（谁在什么时候查了哪个单）。

### 6.5 AI 客服的算法备案（自研/接外部模型时才触发）

- 法律依据：《互联网信息服务算法推荐管理规定》第 24 条、《生成式人工智能服务管理暂行办法》第 17 条。
- 行业解读的三档：纯规则/FAQ 检索 → 仅算法备案；调用已备案第三方模型 API（未实质训练）→ 算法备案 + 大模型登记；自研或深度微调 → 算法备案 + 大模型备案。
- **责任主体按"用自己账号对外提供服务"认定**，商家自建同样可能被视为服务提供者。
- 用抖音官方机器人 → 模型由平台备案，商家无此负担。
- ⚠️ 该段适用性属行业解读，**需法务/网信确认**，不写成定论（见 §9-9）。

## 7. EN 能承担什么 / 不能承担什么

### 7.1 现状（本仓库已核实）

| 能力 | 现状 |
|---|---|
| 外部系统推订单进 EN | **无**入站 webhook、无接收端；SO 来源是手工上传 Excel（`EN_API/so_item_special_mark/`） |
| 认证 | 仅 `Authorization: token <key>:<secret>`；**无 OAuth2**；未实现入站签名校验 |
| 客服/工单 | **未使用** Issue / HD Ticket / Helpdesk |
| 抖音相关 | 仓库内**零**代码 |
| 打印 | 仅批量二维码/标签，**无备注打印** |

### 7.2 先纠正一个说法：不是「EN 不能做」，而是「哪些该买、哪些该造」

用户的质疑是对的：EN 可以随便定制，`tongtool_integration` 就是"单向拉取 + 写单"的先例；轻中间层同样要写代码，只是放在别处。所以「EN 不适合当 OMS」这种说法**不准确**，应改为：

- **该自己造的**：订单接入（拉单、幂等、备注判定、写 SO）。这件事我们有先例、有掌控权、量不大 → **直接做成 EN 的独立 app，和 `tongtool_integration` 同构**，不必多养一个 FastAPI 服务。
- **该买/用平台的**：面单取号与打印（官方组件）、售后审核界面、波次拣货、客服工作台。这些是商品化的东西，自己造要几个月，且要跟着平台规则一直改。
- **不要做的**：把"电商作业台"（拣货波次、面单池、售后审核台、客服会话）塞进 ERPNext。不是因为做不到，而是**投入产出不划算 + 改坏会波及生产**。

**因此原方案修正为**：优先 `douyin_integration`（EN app）而非外挂中间层；中间层仅在「不想动 EN 服务器」或「需要独立扩缩容」时才成立。

### 7.3 分工建议

| 环节 | 谁做 | 理由 |
|---|---|---|
| 拉单、幂等、改单/退款感知 | **EN 独立 app**（或外挂中间层） | 与 `tongtool_integration` 同构 |
| 备注脱敏 + 三类判定 | **EN 独立 app** | 判定逻辑要跟着业务改 |
| 面单取号与打印 | 抖店官方电子面单 + 打印组件 | **唯一不能自研的一环** |
| 售后审核 | 前期抖店后台人工；量大再评估 | 审核规则常变 |
| BOM、生产工单、Job Card、工序派工 | **EN** | 现有强项 |
| 物料/库存/采购/出货 | **EN** | 现有强项 |
| 客户备注 → 工序要求 | app 判定 → **EN**（需新建打印格式） | 缺一个打印格式，约 1 人天 |
| 客服会话 | 官方机器人 / ISV / 飞鸽插件 | 见 §4 |

### 7.4 三个架构选项

**A. `douyin_integration`（EN 独立 app，推荐）**
- 和 `tongtool_integration` 同一形态：Frappe app、定时拉取、写 SO、回传单号。
- 优点：不新增服务、复用现有部署链路（测试建分支 → migrate → 合并 → 生产 pull + migrate + restart）、权限与审计复用 Frappe。
- 代价：改 EN 服务器，需要用「生产只读查询也会压垮站点」的纪律（见本仓库既有教训）约束拉单频率与索引。
- 适用：单量中等、SKU 以自制为主。

**B. 外挂轻中间层（FastAPI）+ EN 只做生产**
- 复用 `sellfox-api-proxy/`（Bearer key + 限流 + token 缓存 + 声明式多账号）与 `web_automation/scripts/dispatch.py`（状态字面量 + 写操作强制确认）。
- 适用：需要独立扩缩容、或不想让平台调用打到生产 EN。

**C. 买成熟 OMS（聚水潭/万里牛/旺店通）+ EN 只做生产**
- 现成的波次、面单、售后、对账；**且已有软著与平台资质，不受 §3.0 的 1–3 个月门槛限制**。
- **但本方案已被业务方排除**：我们在跨境侧用的通途与赛狐都是 SaaS，**不能定制、且体验不好**（2026-11-10 业务方明确表态）。国内 OMS 大概率同类问题，且数据与流程要迁就厂商。
- 保留此条仅作对照，不推荐。

### 7.5 不等软著的最短路径：Excel 桥（推荐先做这个）

软著要 1–3 个月，但「简单的订单处理」**今天就能开工**，因为你们现有的 SO 来源本来就是 Excel 导入（`EN_API/so_item_special_mark/` → `key_test.item_utils.read_excel_file`）。

```
抖店后台 → 导出订单（只勾白名单列）→ 导入 EN → 生成 SO / 工单 → 备注打到工单
                                            ↓
                              发货仍在抖店后台用官方电子面单完成
```

**关键：导出列只留「订单号 / SKU / 数量 / 买家留言 / 下单时间」，不导出收件人姓名电话地址。** 这样：

- 不调用解密接口 → 不碰隐私红线；
- 不需要 API → **不需要软著**；
- 不需要抖店云 → 无额外费用；
- 与你们现有「通途导出 → 本地处理 → 建 EN 单据」的作业习惯一致。

**成本**：复用现有 Excel 导入范式，首版约 2–3 人天（含 SKU 映射表 + 工单打印格式）。

> 待核实：抖店后台导出是否支持自选字段、默认模板是否含明文收件人。若不可裁剪，导出后**立即丢弃隐私列、不落盘**（见 §9-7）。

## 8. 直播策划与投流：标准做法 + SOTA

### 8.1 标准 SOP（业界通用）

1. **对标**：找 10+ 个同赛道直播间，拆人货场；
2. **人货场**：主播人设 / 货盘结构 / 场景与贴片；
3. **排品**：引流款（低价高频）+ 主推款（利润）+ 福利款（回馈），首场不超过 3 款；
4. **脚本**：开场钩子 → 产品讲解 → 逼单 → 循环；
5. **中控**：弹窗、改价、发券、口播配合；
6. **复盘指标**：GPM（千次观看成交）、UV 价值、平均停留、互动率、转化率、退货率。

### 8.2 投流现状（2026）

- **全域推广**成为默认：短视频 + 直播 + 商品卡/搜索打通，付费与自然流不再严格区分；
- **AI 接管定向**：多数字商家不能再手动设年龄/性别/地域/兴趣/达人相似 → **竞争点从"投手技巧"转向"内容向量化"**（标题关键词、画面场景物、主播妆造、话术、评论都会被算法解析成标签）；
- 成本：CPM 约 80 元（2023）→ 120 元（2026）；有品牌 ROI 从 1:3 降到 1:1.5；
- **千川·乘方**（千策 / 千意 / 千寻）：一个总预算 + 一个综合 ROI 目标 → 系统自动分配预算、出价、选品；AI 动态创意与"智投星"诊断；多模态需求预判。

### 8.3 AI 能用的地方（按风险从低到高）

| 用途 | 风险 | 说明 |
|---|---|---|
| 脚本/话术生成、卖点提炼 | 低 | 用 LLM 批量产出，人工定稿 |
| 短视频素材批量生成（即创/即梦） | 低-中 | 需注意素材同质化与平台查重 |
| 评论区/私信回复 | 中 | 属客服机器人范畴，见 §4 |
| 直播切片、二创 | 中 | 注意肖像权与音乐授权 |
| **数字人直播** | **高** | 必须标识 + 注册 + 真人驱动；纯无人直播被禁 |

## 11. 有没有公司真的自己写系统接抖店？（案例核查）

**结论先说**：**订单侧有大量真实先例，是行业常规路径；客服侧也有人做，但只能"插件模拟"，没有官方 API。** 所以"技术不是问题"这个判断成立 —— 真正的成本在**资质**和**长期维护**，不在写代码。

### 11.1 证据分四类（都可点开验证）

| 类型 | 实例 | 说明了什么 |
|---|---|---|
| **开源全栈 OMS** | `zeasin/qihang-oms`（启航电商 OMS，SpringBoot3）：商品库 / 店铺订单拉取 / 售后 / **电子面单打印** / 发货 / 多租户，支持抖店；明确"可用接口对接内部 ERP、WMS、财务" | 有人把整套抖店订单链路**写完并开源**，不是纸上谈兵 |
| **多语言 SDK** | Java `cnJun/sdk4-jinritemai`、PHP `iMactool/jinritemai`（订单/售后/物流/商品/库存/账单全覆盖）、Python `minibear2021/doudian`（显式支持**自用型应用** + 消息推送 + 沙箱）、Go `zsmhub/doudian-sdk`、Spring Boot `chrisis58/doudian2-spring-boot-starter`、PHP `whalesky-labs/doudian-sdk`（710+ 接口） | 开发者生态成熟，轮子基本都有 |
| **实战踩坑记录** | 阿里云社区《抖店订单API对接实战：自研系统如何绕开资质门槛》给出可操作细节：增量窗口取 `当前时间-60秒` 防漏单、`order_id` 唯一键做幂等、状态映射留未知分支 | 这些细节只可能来自**真跑过生产**的人 |
| **资质流程已常规化** | 51CTO《自研型商家如何与抖音电商平台进行API对接》列出完整清单：营业执照 + 法人身份证 + **软著** + 系统说明（架构/API 列表/截图/代码片段）；类目「电商商家自研 - 商家后台系统」；官方 FAQ 里就有「申请商家后台系统需要提供软著/系统代码，无法提供如何解决」 | 说明这是平台**设计好的常规入口**，不是特例 |

旁证：点三这类电商中台把自己的客户明确列为「**中大型企业构建自研 OMS / ERP 系统**」—— 如果没人自研，这个客群不存在。

### 11.2 客服侧：真有人做，但只有"模拟"这一条路

- 开源 `cs-lazy-tools/ChatGPT-On-CS`（AGPL-3.0）：多平台 AI 客服，支持抖店/飞鸽，可接 DeepSeek / 通义千问，支持自有知识库。
- 商业实现（gofly 唯一客服等）同理：**插件运行在飞鸽网页版上，抓消息 → 交给大模型 → 模拟输入框输入并点发送**。
- 原因见 §4.2：飞鸽**没有发送消息的服务端接口**，官方只给"飞鸽插件"这一条路。

⇒ 能做，但形态是浏览器/Electron 注入，**不是官方 API**；可维护性和合规确定性都低一档。

### 11.3 两个必须知道的"坑产业"

1. **聚合 API（绕过资质）**：点三、小于科技等提供"只给 appId/appSecret/shopId 就能拉单"的中间层。**确实能绕开软著门槛**，但代价是：字段被裁剪/归一化、稳定性依赖中间商、数据链路多一跳、长期迁移有改造成本。**架构上必须封在独立适配层**（业务只依赖 `OrderSyncService`），否则将来切回官方要重写。
2. **ISV 的说法要打折**：万里牛等厂商公开写「部分大型品牌会考虑自研，但面临极高的开发与维护成本，接口规范不断迭代（加密面单算法、预售、阶梯发货）」——**风险描述是真的，结论是为卖 SaaS 服务的**。对已经有开发团队、且讨厌 SaaS 的团队，这笔账要自己算。

### 11.4 对你们的判断

| 环节 | 自研可行性 | 依据 |
|---|---|---|
| 订单拉取 / 写 SO / 售后同步 | **高，且被验证** | 开源 OMS + 多语言 SDK + 生产踩坑文 |
| 电子面单打印 | **高**（调官方组件，别自己造） | 启航 OMS 已开源实现 |
| 备注 → 工单 | **高**（你们已有 Excel 导入与 Job Card） | 本仓库既有能力 |
| 库存同步回抖店 | 中高 | 有 SDK 方法，但要注意并发与超卖 |
| **AI 客服** | **中**（只能插件模拟） | 无官方收发消息 API |

**真正的三笔成本**（都不在写代码上）：① 软著 + 资质，1–3 个月；② 平台规则变更的长期跟进（面单算法、预售、阶梯发货都会改）；③ 客服侧的"无 API"结构性缺陷。

> 所以：**订单侧自研是合理选择**，前面几轮的谨慎主要卡在"资质 + 你已排除 SaaS"，而不是技术。真要把风险压到最低，建议顺序是 **Excel 桥先跑通闭环 → 软著并行办 → 换 API 只替换取数层**。

**三条判断**：

1. **`doudian-sdk` 最"干净"**：MIT、有测试、签名/token 实现可直接对照。虽然语言不同，但签名算法、token 缓存、重试退避这些是跨语言的，**读它就等于省掉最容易出错的一块**。
2. **`oba-live-tool` 技术参考价值最高，合规风险也最高**。可以借它的 Playwright 接中控台方案，但**只做"只读看板/消息提醒"**，不要做自动发言和自动互动——这两件事在平台规则里是"制造虚假人气"，处罚不是限流就是封禁。
3. **`ChatGPT-On-CS` 功能最贴，许可证最麻烦**。AGPL-3.0 下最稳妥的用法是**只读代码、重写实现**，或做成独立进程 + HTTP 边界隔离，不要把它当私有代码库的一部分。

**低成本验证建议（各半天，风险可控）**：

| 项目 | 怎么测 | 规避什么 |
|---|---|---|
| doudian-sdk | 只读 `src/` 的签名与 token 刷新，和官方文档逐条对 | 不需要真实店铺 |
| oba-live-tool | 用**小号/测试店**连中控台，**只读评论、关闭一切自动发送** | 不要用主店铺号；不要开自动发言/自动弹窗 |
| ChatGPT-On-CS | 本地跑通一个测试会话，重点看 adapter 怎么抽象 | 不要接生产飞鸽账号 |

### 11.7 深挖 `mcp-cn-commerce`：它不能绕开软著，但能省掉"给 Agent 接数据"的活

| 项 | 事实 |
|---|---|
| 许可 / 语言 | **MIT** / Python 3.11+ / MCP Server（stdio） |
| 活跃度 | 97★ / 18 fork，最后推送 **2026-11-09** |
| 抖店已核范围 | **订单列表/详情、售后列表/详情**（只读）；通用店铺信息**不支持** |
| 写操作 | **无。所有工具默认只读**，Agent 无法修改任何内容 |
| 验收状态 | **全部平台 `live_verified = false`** —— 合同已读、代码已写、CI 已过，但**未在任何真实店铺验收** |

**三条判断**：

1. **它绕不开软著。** 走的仍是官方开放平台，仍需 AppKey 与店铺授权。它做的是"把读接口封装成 Agent 工具"，不是"替代资质"。
2. **它是目前看到最诚实的实现**：每个工具带 `contract_status` / `supported` / `live_verified` 三态，`supported=false` 的会在发请求前直接拒绝。这种"把不知道的标成不知道"的做法，比 star 数更值得信任。
3. **它的价值在工程件**：共享连接池、限流、重试、脱敏、统一金额与时间处理、分页缺失显式标记。这些正是自研最容易漏的部分。

**它独立佐证了我方 §3.0 的结论**（双来源一致）：该仓库 `docs/official-access-status.md` 明确写——

> 抖店自用指南要求：**商家后台系统类目资质、系统材料、软著、关联店铺**；主体相同或证明强关联。
> 一个应用可授权多个关联店铺；获取 token **必须带目标 `shop_id`**，遗漏时可能返回**最早授权店铺的 token**。
> token 默认有效期 **7 天**，支持创建/刷新，**不应每次业务请求前重新获取**。
> **自用应用不能在服务市场发布服务**；对外服务应按工具型/服务商类目办理。

> ⚠️ 那个 `shop_id` 细节值得记：多店铺时漏传 `shop_id` 会静默拿到**别的店**的 token —— 对"一店一应用"或"多店共应用"的架构选择有直接影响。
