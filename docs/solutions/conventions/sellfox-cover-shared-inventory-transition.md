# 三角类皮壳在通途与赛狐并行期的共享库存代理

## 决策摘要

当前通途与赛狐并行期，三角类分公司普通仓继续以通途 `TT123` 一类成品码记录实际皮壳库存；赛狐以对应 EN `KS...` 普通商品承接这一个库存池，并把在售皮壳 SKU `PK#KS...` 建成 **组合商品**，子商品为 `KS... x 1`。

```text
通途库存事实源：TT123（必要时再确认是否合并 TT123-Cover）
                    |
                    v 定期只校准底层商品
赛狐 KS...：普通商品、有库存
   ^                         ^
   | 成品 Listing            | PK# 组合商品下单时扣子商品
   |                         |
成品订单                 PK#KS...：组合商品、无独立库存
                           ^
                           |
                       皮壳 Listing
```

这里的 `PK# -> KS x1` 是 **销售库存代理关系**，不是物理组成、生产 BOM、EN Product Bundle，也不能反向同步为 EN 套件。EN 不新增 Product Bundle。

加工商品暂不采用。它有独立库存，必须通过加工单消耗子商品、增加加工商品库存；取消“开启加工过程”只缩短加工单状态流，不会取消加工单和库存转换。这会重新引入北京或海外仓人工操作，不能解决当前共享库存需求。

本结论是阶段性架构决定。数量共享可以按「一个 SKU、一个已确认皮壳仓、一条皮壳 Listing」沙盒验证；**利润不能按同一套验收放行**（见「成本与利润风险」）。[#191](https://github.com/keyapi/fzh-data/pull/191) 未合并前，本文与只读审计脚本的波兰 covers **语义**视为 pending；通途 `FZHPoland-covers` → 赛狐 `POLAND` 的期初/备货单仓库映射本身已在主线。

## 为什么三个系统不能共用同一套物料语义

### EN：生产身份与流程事实源

- `KS...` 是产品成品，`PK#KS...` 是皮壳半成品；两者生产流程、BOM、工单语义必须严格区分。
- 销售订单 Excel 用通途完整 SKU 找 EN 产品物料，再由“皮壳/成品/半成品”列决定实际交付物料。
- 即使通途码带 `-Cover`，也统一登记在 EN `KS` 产品的 `customer_items`，不能改登记到 `PK#` 来替代。
- 三角靠枕 `KS0001`、三角靠枕无扣 `KS0248` 的 `PK#` 变体在 EN 内仍须按后缀 1:1 配对；这与赛狐销售库存代理是两层不同关系。

### 通途：当前仓库作业与库存事实源

- 历史上销售只卖成品，通途只有 `TT123`；分公司收到的实物虽是皮壳，出入库和普通仓库存仍长期使用 `TT123`。
- 后来新增 `TT123-Cover` 供皮壳订单发货，但其无库存时需要人工从 `TT123` 调拨，形成重复、易错的操作。
- 接下来仍用通途做出入库和订单标记发货，因此不能要求现场马上改用 `PK#` 或另一套新编号。

### 赛狐：销售、利润与运营可见性

- 当前重点是 Amazon 订单、销量、成本、账期费用及运营库存可见性，不是替代 EN 的生产主数据。
- 运营需要独立的皮壳商品与皮壳 Listing 配对，但不代表皮壳必须在赛狐拥有独立物理库存。
- 赛狐可以用组合商品把两个销售身份映射到同一个可扣减库存池。

## 仓库边界

只把 **用户确认的三角类分公司仓** 纳入共享池：绍兴发给该仓的实物须是可售皮壳，而通途/赛狐目前可能仍按 `TT123`/`KS...` 记账。

`warehouse_name` 填 **赛狐仓库名**（2026-08-20 回读仍为 `CENTRADE` / `DANEEY` / `POLAND` 等，与通途 `美东-CENTRADE` 前缀不是同一套字符串）。

以下库存不得直接并入：

| 仓库/库存 | 实物判断 | 本阶段处理 |
| --- | --- | --- |
| 美东主仓（赛狐名如 `CENTRADE`） | 三角类通常是皮壳 | 用户确认实物后可进入共享池 |
| 美中主仓 / 成品仓（名称含 `DANEEY` 且不含皮壳/cover） | 可能是成品或混放 | **不默认**当皮壳共享池；只读审计会 `cautions` |
| 美中皮壳仓（通途 `FZH-DANEEY-皮壳仓库` / `美中-FZH-DANEEY-皮壳仓库`） | 皮壳 | 若赛狐有对应仓且用户确认，优先于主仓 |
| 波兰赛狐仓 `POLAND` | 对应通途皮壳仓 `FZHPoland-covers` / `波兰-FZHPoland-covers` | 可作为三角皮壳共享池（2026-08-20 用户确认） |
| 波兰成品仓（通途 `FZHPoland-finished`，名称含 finished/成品） | 成品 | 不是皮壳共享池；只读审计会 `cautions` |
| FBA | 绍兴发出的成品 | 保持成品库存，不与皮壳共享；审计 `type=2` 会 blocked |
| 退货仓 | 可能是成品、皮壳或混合 | 名称含「退货」会 blocked |
| 不良品仓 | 不可售或待处理 | 名称含「不良」会 blocked |

2026-08-20 赛狐只读回读确认 `CENTRADE`、`DANEEY`、`POLAND` 普通仓及三地退货仓/不良品仓均已存在。新增退货和不良品仓当时库存字段为空。该快照只证明仓库对象存在。同日用户确认：赛狐 `POLAND` 对应通途 covers 仓，不对应 `FZHPoland-finished`。

## 组合商品与加工商品的实际差异

| 维度 | 组合商品 `isGroup=1` | 加工商品 `isGroup=2` | 对当前需求的影响 |
| --- | --- | --- | --- |
| 自身库存 | 无 | 有 | 当前希望共享一个库存池，组合更合适 |
| 订单扣减 | 扣子商品 | 扣加工商品自身 | 加工商品会形成第二个库存池 |
| 库存转换 | 不需要加工单 | 加工单消耗子项并增加成品 | 当前无人承担加工单操作 |
| 关闭加工过程 | 不适用 | 仅缩短为待配货到已完成 | 不等于免加工单、免分配库存 |
| 适用场景 | 虚拟套装、销售别名、共享库存 | 真实组装/加工后形成可独立存货 | 当前是销售身份差异，不是仓内加工 |

调研来源：赛狐帮助中心“商品列表”“加工单”“采购单”及本项目 OpenAPI 镜像。当前账号查询 `isGroup=2` 返回 0，说明团队没有现成加工商品操作经验。公开资料也没有证明客户订单能自动创建并完成加工单；本地 OpenAPI 镜像尚未验证出创建、分配、完成加工单的完整写链，因此不能把自动加工当成已具备能力。

## 冻结的数据模型

以一个 EN 变体为例：

```text
底层库存商品
SKU: KS0001-DM-194-GREY
类型: 普通商品
库存: 定期从通途目标池校准

皮壳销售商品
SKU: PK#KS0001-DM-194-GREY
类型: 组合商品
子商品: KS0001-DM-194-GREY x 1
库存: 无独立库存

在线配对
成品 Listing -> KS0001-DM-194-GREY
皮壳 Listing -> PK#KS0001-DM-194-GREY
```

### 不可破坏的规则

1. 通途仍是并行期库存事实源；赛狐调整只写底层 `KS`，不调整 `PK#` 组合商品。
2. 同一个普通仓内，卖成品或皮壳都从同一个 `KS` 池扣一件。
3. 不把 `PK#` 组合关系同步成 EN Product Bundle，也不交给 `sellfox-combo-create` 的 TJ# 同步流程。
4. 不改变 EN 客户物料号登记规则和销售订单“交付形态”识别逻辑。
5. FBA、退货仓、不良品仓单独分类，不因 SKU 相同就合池。
6. 同步目标池是否采用 `TT123 可用库存 + TT123-Cover 可用库存`，必须先核实通途“可用”是否已经扣除占用/待发货；未核实前不写公式。
7. 避免时间反馈：赛狐订单已扣库存、通途尚未标记发货时，不能用旧通途快照立刻把赛狐库存加回去。需要约定同步时点、订单排除或水位容差。

## 成本与利润风险

2026-08-21 补记（[#191](https://github.com/keyapi/fzh-data/pull/191) 在波兰 covers 确认之后的会话）：共享数量不代表共享成本。组合商品复选框和「子件 `KS` 仓批次被订单吃到」都**不能**当成皮壳利润通过。EN Tongtool Cost Review 按通途后缀与交付形态切 BOM 局部成本；赛狐没有对等定制。

### 三层赛狐「采购成本」不得混用

界面和导入模板多处都叫采购成本，本仓库三条管道写入的对象不同：

| 层 | 管道 | 粒度 | 实际写入 |
| --- | --- | --- | --- |
| 商品主数据 | `item-cost` | 只有 SKU，不分仓 | **绍兴发货成本**（皮壳成本 / 皮壳+包装 / 绍兴总成本）。备注前缀 `EN绍兴发货成本-`，避免当成完整采购成本 |
| 期初库存 | `stock-init` | **仓库 + SKU** | 按发货方式选黄列：皮壳/半成品 → `发皮壳尾程前成本`；成品 → `发成品尾程前成本`。通途 `FZHPoland-covers` 映射赛狐 `POLAND` |
| 海外仓备货单 | `warehouse-restock` 默认格式 2 | **收货仓库 + SKU** | 赛狐只有两格：`指定采购单价` = 绍兴发货 + 国外加工；`单个头程费用` = 头程。销售负责人要求头程单独看 |

黄列拆解见 [BOM 成本读取说明](../../bom_cost_explanation.md)。该文**不解释**通途尾缀（`-Cover`/`-Foam`/`-1` 等）造成的成本拆分。

期初曾按仓写入约 1000 件安全冗余数量（不追求与通途数量一致）。备货单后来把格式 1 的三格费用收成格式 2 的两格，因为赛狐海外仓备货单界面只有这两个可维护位。

用户寄希望于：订单从某仓扣 `KS`，利润取**该仓这批库存**（期初或备货单），而不是商品列表上的绍兴发货成本。对组合商品，扣的正是子件 `KS` 的仓批次。**即便这一希望成立，对皮壳 Listing 仍然不够**（下一小节）。

### 组合复选框只改 `PK#` 主数据采购成本

赛狐帮助中心 [商品列表 §2.2 添加组合商品](https://www.sellfox.com/help/features/product-list)：采购信息**默认勾选**「关联子商品采购成本」时，组合采购成本 = 子商品采购成本 × 数量，子商品变更会连带修改；取消勾选后手工编辑，不再联动。OpenAPI `purchaseCostLock`：`1` = 不锁定、允许自动关联；`0` = 锁定、只允许手动改（`SELLFOX_API/docs/api-reference/商品/商品列表/创建SKU.md`）。这与「自动计算重量」`autoCalcWeight` 不是一回事。

取消勾选 / `purchaseCostLock=0` 仍是主数据卫生（避免默认加总成品 `KS` 的商品采购成本），**不会**按仓生成皮壳成本，**不会**按 `-Cover` 切片，也**不会**改写 `KS` 的期初/备货单批次。

### 子件 FIFO 批次对皮壳销售仍然是错的

组合商品自身无库存，出库扣子商品。赛狐同一仓库 + SKU 按 FIFO 消耗批次（`docs/company-context.md`）。皮壳 Listing 配到 `PK#` 后，订单吃到的是该仓 `KS` 现存批次——通常是成品口径，或「发皮壳尾程前成本」整段黄列（含该仓加工），而不是 EN 的皮壳部分成本。

EN 测试/生产上的 **Tongtool Cost Review**（用户确认；本仓库没有公式源文件，不得杜撰加项）按通途完整 SKU 后缀（至少 `-Cover`、`-Foam`、`-1`、`-2`）和销售订单「皮壳/成品/半成品」交付形态，从 BOM 取**局部**成本。赛狐没有后缀规则，也没有交付形态列去改同一仓同一 `KS` 批次的取值。

因此：库存扣减可以通过（`PK#` 无独立库存、指定仓 `KS` 恰扣 1），同时利润验收预期失败。不要把「成功吃到子件仓成本」写成通过。

### 结构不兼容与实务分工

一个普通仓里，同一 `KS` 只有一套 FIFO 队列。共享库存要求成品单和皮壳单都从这套队列扣数量；Cost Review 要求皮壳单读另一套金额。vanilla 赛狐不能同时满足。不要在赛狐里发明一套没有定制入口的「部分成本」。

- **赛狐**：库存可见性与 Listing 配对（数量代理）。
- **EN / 通途**：利润与订单成本（Cost Review / 特殊规则）。

并行期「赛狐只用来获取订单成本」不能理解成「FIFO 批次已经等于 EN 皮壳切片」。若利润对不上，即使扣减通过也不能扩大上线；可暂时只用于库存配对。

## 已讨论并排除的方案

### 再发明一个成品编号

否决。通途 SKU 含义和人工流程已经固定，再增加编号会扩大现场培训、映射和对账成本。

### 当前就用 `PK#` 普通商品 + `KS` 加工商品

暂缓到赛狐成为唯一仓储系统之后。当前会要求把通途以 `TT123` 入库的库存转换成 `PK#`，再执行加工单得到 `KS`；这与现有现场操作相冲突。

### 让加工商品取消“开启加工过程”以实现自动共享

否决。该选项只缩短加工单状态，不会让加工商品变成无库存别名，也没有证据显示订单会自动完成库存转换。

### 在 EN 创建 Product Bundle

明确否决。这里没有组合销售物理组成，EN 已能通过产品客户码和交付形态严格区分成品/皮壳流程。

## 单 SKU 沙盒计划

范围必须由用户点名。不要从示例仓名或「赛狐里已有某个 `KS0001`」自动扩大。`POLAND` 已确认为通途 covers 仓。生产写入前先跑 `sellfox_cover_inventory/audit_sandbox.py`。

### 阶段（写操作必须另批）

| 阶段 | 做什么 | 现在是否执行 |
| --- | --- | --- |
| 0 点名 | 赛狐仓 + 通途基码 + 底层 `KS` + 皮壳 `PK#`。店铺/MSKU 对当前 `--live` **不是必填**（脚本不查 Listing） | 等用户点名 |
| 1 只读 | 无 `--live` 只校验配置；`--live` 查仓库和两个商品 SKU。`PK#` missing 记缺口，不创建。已是有库存普通商品则 blocked | 可跑；不创建、不配对 |
| 2 创建组合 | `PK#` = `KS x1`，`isGroup=1`。不走 `sync-combos` | 须再确认 |
| 3 配对 | 皮壳 Listing → `PK#`，不是 → `KS` | 须再确认 |
| 4 测试单 | 只验证扣减与页面展示。利润项预期失败 | **现在不要请井下单** |

找到已有三角 `KS` 只覆盖阶段 1 的「底层存在」，不是成本接受，也不能跳到阶段 4。

### 前置证据

1. 选定通途基码、可选 `-Cover` 码、赛狐底层 `KS`、上层 `PK#`、已确认皮壳仓。店铺和皮壳 MSKU 是阶段 3–4 才必须。
2. 确认普通仓实物是可售皮壳；排除 FBA、退货和不良品。波兰不要填 `FZHPoland-finished`。
3. 回读赛狐底层商品存在且为普通商品。
4. 若 `PK#` 已存在，断言它为组合商品且只有 `KS x1`；不一致则阻断，不自动修改。
5. 记录通途同步前水位、赛狐底层水位和在途/待发订单（阶段 4 之前）。

### 三项核心验收

| 验收 | 操作 | 通过标准 |
| --- | --- | --- |
| 订单扣减 | 皮壳 Listing 测试单（阶段 4，另批） | `PK#` 无独立库存，指定仓 `KS` 可用恰好扣 1，无需人工调拨 |
| 库存展示 | 运营查看皮壳/成品商品和仓库库存 | 能理解两条 Listing 共享一个池，页面不显示两份可售库存 |
| 利润成本 | 对照 EN Tongtool Cost Review 对该仓该 SKU 的 `-Cover` 切片 | **不是**「已锁定 `PK#` 采购成本」，**不是**「`KS` 仓批次已出现」。vanilla 赛狐**预期失败** |

### 同步回归

测试定期校准时，必须证明不会把刚由赛狐订单扣掉但尚未在通途反映的 1 件加回。至少跨过一次“订单产生 -> 通途标记 -> 下一次校准”完整周期并保存各时点快照。

### 停手条件

- `PK#` 已是普通/加工商品或子项不是唯一 `KS x1`。
- 普通仓实物分类不确定，或美中误用主仓/成品仓而未确认皮壳仓，或波兰误用 `FZHPoland-finished`。
- 所选赛狐仓为 FBA，或名称含退货/不良。
- 同步公式无法解释占用、待发货或 `TT123-Cover`。
- 利润不等于该仓 Cost Review `-Cover` 切片（即使报表走的是「发皮壳尾程前」整段黄列，对皮壳 Listing 仍不算通过）。
- 有人要用赛狐复选框或子件 FIFO 替代 Cost Review，或要在赛狐发明后缀部分成本。
- 需要扩大到第二个 SKU、仓库或 Listing，但数量沙盒尚未书面验收；利润项失败时不得以库存通过为由扩大。

## 未来状态

彻底停用通途并由赛狐承担真实仓储后，可以重新评估：

```text
PK# = 有独立库存的普通皮壳商品
KS  = 有独立库存的加工商品
PK# + 其他组件 + 加工单 -> KS
```

这要求仓库实际扫描/操作加工单、采购与入库按真实物料执行、API 写链验证完整，并重新设计成本和退货分类。它不是当前组合代理的自动升级，必须另立迁移项目。
