# 补货交付的状态分桶与批次日期

## Context

2026-11 补货交付包从 v7 走到 v15，外部 Codex 连续指出：151 条风险仍在“可批准”、第二批下单日已过、4 个首批晚于停工仍标可执行、日常候选与春节方案相加、老板表出现“8 款”错误子集。根因不是数字算错，而是**状态与日期口径没冻结**。

## Guidance（本学习沉淀的做法）

1. **生产截止 ≠ 目的仓需要日。**
   - 工厂 1/24 停工是生产约束；
   - 第二批的目的仓需要日是复工 2/22（或覆盖起点），不是 1/24；
   - 用“停工日 − 全程交期”倒推第二批下单日，会人为制造过去日期。
2. **所有批次都要检查下单日。**
   - 首批：决策日下单，检查到仓是否晚于停工；
   - 第二批：目标到仓倒推，检查下单日是否早于今天；
   - 不只检查“换运输补救表”，主候选表也要检查。
3. **状态用互斥、可执行的门，不用模糊词。**
   - 可确认 / 首批要改空运 / 先换运输 / 方案未达95% / 断货风险-无运输可赶上 / 需求看不清 / 需求异常 / 新增资格-待复审 / 催已有 / 不补 / 观察。
   - “风险隔离”说的是**断货风险**，不是数据判断错误。
4. **方案量与日常候选分开，不相加。**
   - 春节方案 12,092 与 D6 日常补货候选 28,491 是两种用途；
   - 老板表必须明确“不要相加”，并分别列可排期/下单日已过。
5. **每行带证据链。**
   - 需求：D5 模型/p50/q95/区间；
   - 供给：C 可发/C 完整键、EN 在途/快照、PO/ETA；
   - 动作：D6 动作原因/服务验证；
   - 春节：批次数量/到仓/轨迹/风险。
6. **60cm 身份规则必须同时用于需求与供给。**
   - 只在目标仍是当前 D1b 活跃键时改码；
   - 需求、C、EN、PO 用同一规则，否则 20 个旧键供给失联；
   - 保留原键后，PO 仍可能缺（本项目 20 键中 17 键无 PO，缺 2,417 件）。

## Why This Matters

- “模拟通过”不等于“能下单”：批次日期过去、首批晚于停工，都会让方案不可执行；
- 把风险量算进可执行量，会让老板批准一个到不了货的方案；
- 把方案量与日常候选相加，会虚增资金/采购；
- 证据链缺失，运营无法判断是模型、库存还是 PO 的问题。

## When to Apply

- 任何带停工期（春节）的备货排期；
- 需要给老板/运营逐商品行动表；
- 有多批到货、换运输、催已有、零中位数/模型异常；
- 60cm 等价、owner 重述等身份规则跨层使用。

## Examples

- 第二批目标从 1/24 改为 2/22 后，17 个过期下单日清零。
- 31 个可复核键中，4 键/271 件首批晚于停工，单列“需重排”；首批改空运后 4 键均可执行（2 fill95/2 cycle95），但状态不变。
- 8 个换运输方案：7 可执行/372，1 fail/52；`KS0321` 换运输无效，根因是总供给 85 vs p180≈94，需加约 18 件。
- 60cm 4,001 件：20 键，C/EN 20/20，PO 3/20，17 键缺 2,417；Top 缺口 ANTHRACITE/IVORY/BLUE。
- DN：11 个台账 DN 全 1:1；EN 14 个 DN 中 3 个缺失；arrive/warehouse_in 全空，到货/入仓需人工补证。
