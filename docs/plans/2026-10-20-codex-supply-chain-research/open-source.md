# 跨境电商供应链计划开源方案独立调研

调研时间：2026-10-20。目标链路是通途订单/库存/采购、ERPNext 的 SO/PP/WO/DN/BOM、赛狐库存和销售、头程、销售分析、未来数月预测、补货、排产与负责人审批。预算、数据量、当前 ERPNext 主版本和运维人力尚未知；所以成本用相对级别与明确假设表示，不编造金额。

## 当前产品约束补充

用户已找回#304历史预测资产：阶段A完成，阶段B未启动；当前方向为分段全局LightGBM、Croston/TSB兜长尾/生命周期、Conformal区间与物料组调和。现阶段不采用TSFM；原开源候选表保留为研究盘点，不能据“候选存在”重启基础模型实施。见[history-handoff.md](history-handoff.md)。

## 结论先行

建议先把 ERPNext、通途、赛狐保留为交易事实来源，做一层只读、可追溯的计划数据模型；将 frePPLe 9.19.0 Community Edition 定位为**需补充库存策略能力的 APS 候选**，并与 ERPNext 原生 Production Plan/MPS/MRP 做基线对照。CE 有有限物料/产能计划和统计预测，但完整 Inventory Planning 屏、安全库存与再订货量策略维护归 Enterprise/Cloud；因此是否采用 CE 取决于我们能否用现有 EN 能力或轻量自建报表补齐策略审阅与审批，若不能就须将商业版报价计入决策。[R19][R1][R20][R21][R33]

当前主要决策不是“迁移到另一个 ERP”，而是决定是否增加一个计划引擎。Odoo Community/Enterprise 是另一条 ERP 替代路线，重叠更大且迁移影响高。已打开 Odoo 18 官方 MPS 源文档：MPS 使用手工可调需求预测并提出补货量，不会自动创建 PO/MO；同一产品若同时用 MPS 与 reordering rules 会产生不准确预测和多余补货。Odoo 18 官方源仓库 LICENSE 标明核心仓库为 LGPLv3，但这不足以证明 MPS 属于哪个 edition、CE/EE 完整功能边界或所有依赖的许可；这些仍待核验。原始官方文档/许可页面 R4/R5 访问失败状态保留，不与新增固定分支来源混记。[R4][R5][R34][R35] 若只靠 ERPNext 现有流程，可先验证销售预测、交期计划、MRP/Production Plan、Item Lead Time 和 Capacity Planning 是否已达到需求；ERPNext 文档说明其 MRP 把订单与手工输入 forecast 汇入 MPS/MRP。[R6]

对任何候选而言，皮壳/海绵配套、套件、拆包裹、多仓调拨和头程都不是靠 SKU 前缀或单一汇总库存能解决的。必须把需求行、组件 BOM/替代关系、仓库可用量、在途/采购/工单、运输批次分摊建为带来源与生效日的事实；计划结果展示“需求—供给—短缺—建议日期—影响原因”，由计划员/老板审核后才写回 ERP。这一数据建模结论也与本仓库已有履约蓝图中的 SO 行/生产物料粒度、多对多头程分配与事实/估算区分一致；本次没有把该蓝图当作候选产品结论的依据。[R7]

## 整套系统 vs 组件组合

| 路线 | 覆盖与系统边界 | 许可/成本/复杂度 | 判断 |
|---|---|---|---|

| ERPNext 原生计划 | SO/MR/预测/交货计划生成 MPS/MRP；生产计划拉 SO/MR、按 BOM 展开，创建 WO/MR；能力规划另核版本和配置 | 无新商业许可；较低增量基础设施成本，但可能需要自定义字段、脚本、报表；低至中复杂度 | **必做基线**。可支撑订单驱动和 BOM 物料需求；长周期预测与跨系统多仓优化是否够用需要在当前 EN 版本实测。预测需人工编制的文档是版本/功能范围线索，不可直接外推到所有 v16+ 部署。[R6] |
| Odoo CE / Enterprise 迁移或新增 | Odoo 18 官方 MPS 文档描述手工可调 forecast、补货建议与手动 PO/MO 创建；同时建议不要对 MPS 产品启用 reordering rules。Odoo 18 core repo LICENSE 为 LGPLv3。[R34][R35] | MPS 所属 edition、CE/EE 功能边界及依赖许可仍待核；原先官方 18.0/17.0 页面 URL R4/R5 打开失败。替换 ERP 的迁移、定制和培训成本高 | **本范围暂不作为主方案**。若公司已决定重建 ERP，再单独立项比较；仅为计划功能而迁移缺少价值证据。FrePPLe 有官方 Odoo connector，但没有证据表明能原样接 EN/Tongtool/Sellfox。[R4][R5][R34][R35] |
| 通用 Python/SQL 组件自行构建计划平台 | DuckDB/数据库 + 统计预测 + OR-Tools/Stockpyl + 自研 UI/API/审批 | 每个小组件许可友好，但团队需自己负责业务约束、计划解释、可重放、权限、部署和长期维护；初始代码可以少，持续维护成本最高 | **只把组件当算法/验证工具**，不建议从零搭完整 APS。特别是 OR-Tools 是求解工具而非供应链产品；Stockpyl 是模型/模拟包，不是可直接接 ERP 的补货应用。[R8][R9] |

### 优先级与边界

1. **计划引擎候选：frePPLe 9.19 CE**。先做离线导入、无写权限、按 SKU-仓库-周/月滚动的决策实验。统计预测已进入 CE（自 8.0 起），CE 官方 Editions 页列有限物料/产能计划；库存规划模块及安全库存/reorder policy 维护屏是 Enterprise/Cloud 功能。10.0 upcoming 文档和旧 edition 宣传页不能替代 9.19 CE 的许可/功能证据。正式部署前锁定 9.19.0 代码 tag、镜像 digest 和 CE MIT 文本。[R1][R19][R20][R21][R33]
2. **现状基线：ERPNext**。它已经拥有 BOM/生产计划/工单体系，也有 MPS/MRP 与 lead-time 文档；先核生产环境实际分支、启用模块和自定义，再量出 frePPLe 能补的缺口。ERPNext 官方支持表列 v15 计划支持到 2027 年底、v16 到 2029 年底（计划值会变）。[R6][R10]
3. **预测：先统计法和朴素基线**。按 SKU × 销售渠道/市场 × 月份做间歇性需求与季节性比较；统计预测输出置信区间/回测误差，再由人修正。StatsForecast 覆盖 AutoARIMA、ETS、Croston 等统计方法，适合候选基线；无神经网络权重文件可供许可推断。任何后续引入的 foundation model 必须逐一核代码许可和权重许可，二者不可混为一谈。FrePPLe CE forecast 能力应先测是否覆盖当前时序需求。[R1][R11]
4. **多仓补货优化：Stockpyl 仅用于离线专项分析**。MIT 许可；包含 EOQ/newsvendor/Wagner-Whitin、SSM/GSM 多级库存优化与仿真，适合对长提前期/库存服务水平做原型与情景研究；它不提供主数据同步、采购建议审批或 ERP 写回。[R12]
5. **数据层：初期无需上大型数据平台**。对只读快照，用 Python/CSV + DuckDB 即可形成可复现的分析仓；把事实、维度、计划快照和来源 ID 分层。SQL 模型增长后考虑 dbt Core (Apache-2.0)；高并发或多人写入时换服务型数据库。dbt 产品/发行版本名近期变动，应按选定 release 核对 OSS 分发包与许可。[R13][R14]
6. **BI：先让审批链可理解，不先做炫目控制塔**。Apache Superset 是 Apache 项目，语义层轻量、可查询 SQL 数据源；Metabase OSS 易上手但 AGPL，嵌入/Enterprise 功能另有商业条件。内部使用场景可以先选一个；如果只需计划员审表和老板签字，简单 Web/Excel 报告的 TCO 可能更低。[R15][R16]
7. **Agent：只作为受限解释器/流程助手**。现有仓库已有 Open WebUI 与只读工具 PoC；Open WebUI v0.6.6 起采用带品牌限制的新许可，小于等于 50 名用户的内部部署可按文档条件去品牌，须以实际版本核对。[R17][R30] 若需编排，LangGraph（MIT）适合可持久化、可暂停的人审流程；OpenAI Agents SDK（MIT）有工具验证、审批和 tracing。两者都不保证业务规则正确；SDK guardrail 不覆盖所有 hosted tool/handoff 路径，最终审批和写权限须由服务端 API/权限层执行。MCP Python SDK（MIT）是工具接入层而非安全边界：只暴露细粒度只读工具，回写工具独立权限、显式人审和审计。[R27][R28][R29][R31][R32]

## 库存/WMS 完整产品候选

| 候选 | 定位、许可与版本证据 | 对当前问题的适配结论 |
|---|---|---|
| OpenBoxes | 多设施库存/WMS，源于医疗物资；GitHub README 明示 EPL-1.0。[R23] | 可用于“替换仓库实物库存作业系统”专项；没有证据支持它能接管长周期多级预测、生产有限产能排程或现有三系统对账，本次淘汰为计划中枢。引入会重复建立库存事实，部署与迁移工作量不小。 |
| GreaterWMS | 仓储作业/WMS，项目 README 声明 Apache-2.0，列出多仓、波次出库、组合拣货等 API 能力。[R24] | 定位是仓库执行层，不是 MRP/APS；README 声明尚未与锁定版本 LICENSE 对照，因此许可核查仍待完成。若未来替换 WMS，可独立评估，不能解决预测/补货/排产。 |
| Inventory Planner（商业产品，仅对照） | 官方手册描述预测、基于 lead time/库存天数、考虑在途采购、补货日期和建议数量。[R25][R26] | 说明商业库存规划器有机会更快实现 SKU 级补货，但本次没有核定其对 Tongtool/ERPNext/FBA 多渠道/BOM 生产的连接和费用，也非开源；不能当作采购推荐。 |

这三类不可与 APS 混为一谈：WMS 管库内收发储配执行；Inventory Planner 侧重零售商品补货；frePPLe/ERPNext 承担计划。选用任何一类都须先定义库存事实系统，防止多套库存并存。

## 集成与语义模型建议

输入快照至少包含：销售需求行（订单/行/客户 SKU/EN SKU/通途 SKU/渠道/承诺日期/数量/状态）；历史出货/销量；各系统 SKU crosswalk 和变更历史；BOM/套件层级及版本/生效时间/拆包裹关系；库存按仓库、状态、可用/冻结/预留量；采购单、调拨、生产计划、工单和预计完工；供应商/工序/生产/头程 lead time 分布；在途批次、ETA 修订与数量分配；运营手工调整及理由。

主粒度推荐 `planning_item × location × week`（若数据仅支持月则先按月），另保留订单需求行、BOM 爆炸行、供给单据行、shipment allocation 明细作为可追溯 drill-through。时间参数须同时记录 source fact time、抓取时间、plan run ID、forecast horizon、lead-time 假设版本。不要把头程 ETA、下单+月数估算、国外仓可售库存合并成同一个确定数。

计划服务建议输出仅为建议：需求、期初可用量、已确认供给、预测需求、计划供给、缺口、预计缺货日期、建议采购/生产/调拨量与最迟下达日、受限资源、组件短缺、数据质量告警、使用的假设与来源记录。皮壳与海绵配套要由有效 BOM/配套规则定义；套件的销售需求按 BOM 爆炸至组件，但“可卖成套量”由最短板约束决定。拆包裹属于配送/头程分配层，不应复制或重复计算最终商品需求。跨仓调拨要先扣除不能挪用的预留库存，并尊重各目的仓的销量和安全库存。

## TCO 假设与工作量级

| 项 | 低 | 中 | 高 |
|---|---|---|---|
| 许可/模型费用 | 以 MIT/Apache/LGPL 的自托管 OSS 为主，不购买商业版 | 仍无 APS 订阅，采购 BI/支持/实施服务少量付费 | frePPLe Enterprise/Cloud、ERP 支持或商业 BI/LLM 费用需报价；当前预算未知，不能量化 |
| 集成和清洗 | 1 个 EN 只读快照、少量标准字段、人工 CSV 头程 | EN + Tongtool + Sellfox 三源 SKU crosswalk、订单/库存/采购/销售历史、重复与缺失处理 | 多实体、多仓/拆单/事件回写，来源历史修复和主数据治理 |
| 部署 | 单机/单容器批量试点，人工触发、快照留档 | 固定应用/数据库、定时抽取、日志与监控、备份恢复 | 高可用、隔离权限、审计、长期历史、告警与灾备 |
| 人力 | 1 位业务计划员 + 1 位兼职数据工程师校验试点 | 计划/采购/生产各 1 位主用户 + 持续工程维护 | 专职产品/数据/平台/安全与计划运维；大多数成本来自适配和持续业务维护，而非开源下载 |

此估算是范围级假设，不是供应商报价或承诺排期。可比 TCO 指标建议记录：首个可复算建议耗时、每周人工计划小时、缺料/过量建议数量、建议接受率及拒绝原因、需求覆盖率、预测 WAPE/bias、迟交/断货风险、系统升级和适配维护工时。

## 最小可运行实验设计（仅设计，未安装、未运行、未验证）

**实验 A：ERPNext 原生计划基线。** 在无敏感凭证的隔离副本/纯手工玩具数据中，准备 3 个成品、6 个组件、2 个仓、12 个月销量、2 个销售需求、一个采购在途、一条生产工序/产能限制和 1 个套件 BOM。基线计算期末库存、组件净需求、缺口日期与建议生产/采购量；记录版本、手算校验表、缺失字段与可否按仓分开计划。不得接生产 API，也不生成真实交易。

**实验 B：frePPLe vs 统计预测 + 原生 MRP。** 对同一组脱敏/合成数据导入某正式稳定 frePPLe CE 版本；以 StatsForecast 的 SeasonalNaive/Croston/AutoARIMA 对 12 个月需求做滚动回测，再将人工调整预测和在途长提前期纳入计划。只导出建议、比较 BOM 展开、采购/生产提前期、产能瓶颈、库存跨仓分配、套件齐套量和计划可解释性。使用差异表对账，检查每个输入需求行 = 计划覆盖 + 未覆盖/原因，输出中记录所有未匹配项。最终不写 ERP。

实验 A/B 先限定 3–10 个 SKU，1–2 个仓，12–24 个月历史；这仅是降低验证成本的实验设计，并非全量生产导入许可。上线范围需业务负责人批准。完成结果后才确定是否引入 frePPLe、哪种 BI、需要多少人力/预算。

## 证据质量与局限
