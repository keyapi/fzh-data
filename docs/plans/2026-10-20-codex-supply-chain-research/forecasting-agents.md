# 通途—ERPNext—赛狐供应链预测与 Agent：独立研究

## 范围与结论

目标是把通途订单/库存、ERPNext 生产/BOM/出库、赛狐库存和头程在途，整理为按 SKU 家族、销售渠道/国家站点、仓库和月份可追溯的需求预测，再给出补货与排产方案供老板审批。预测跨度是未来数月；目前没有读取生产数据，也没有运行回测。本文给出可反驳的实验假设与准入门槛，不是选型或上线批准。

**可反驳判断：不应预设单一“确定性内核”或“Agent 主导”作为答案。** 应先把问题拆成三类分别验：需求信号（销量是否代表需求）、预测分布（含不确定性和分组借力）、约束下决策（库存位置、BOM、头程与产能）。历史规则、统计间歇模型、全局监督模型和时间序列基础模型都进同一滚动回测；LLM/Agent 是可对照的语义界面/调度候选，不能靠语言推理替代库存计算。即便这一组合假设也可被证伪：如果某 Agent 端到端在真实时间切分、业务成本和异常压力测试中持续优于规则与 OR/统计参照，且工具执行正确、结果可审计，就应提高其职责。

早期候选次序不是性能排名：

1. **统计基线**：季节朴素、移动平均/ETS/自动 ARIMA；间歇 SKU 加 Croston、SBA、TSB；新 SKU 用家族/相似品先验和显式冷启动规则。
2. **概率/全局监督候选**：DeepAR 或适合本地特征的梯度提升/回归模型；评估分位数、校准与决策价值，而不只点误差。
3. **基础模型挑战者**：Chronos-2、TimesFM-3、Moirai 2.0；逐 SKU 分层验证上下文长度、未来协变量、缺失与长跨度表现。版本和权重许可在试验前核验。
4. **Agent 候选**：从只读取数、解释差异、询问缺失语义、提交带证据的审批草案开始。任何 ERPNext/赛狐写入都在单独权限边界内，且审批由人完成。

## 本地事实与研究边界

- 本地概念将通途 `-Cover` / `-Foam` 与裸基础码视为相关但不同写法；赛狐 packageSn 也不等于通途历史 P 号。预测键要有可版本化的 SKU/包裹/物料映射，不能把字符串相似当业务等价。
- `ai_access_poc/open_webui/AGENT_HANDOFF.md` 描述当前壳 PoC 为赛狐只读工具、xlsx JSON 摘要与可选沙箱分析。它说明现有验证边界，不构成供应链 Agent 架构结论。用户给出的 `ai_access_poc/AGENT_HANDOFF.md` 路径不存在；另有 `portal/AGENT_HANDOFF.md` 与 `open_webui/AGENT_HANDOFF.md`。
- 当前仓库 `warehouse_restock` 默认数量 1000 是成本拆分用途；`docs/company-context.md` 称赛狐初期非真实库存。该数据必须被标为人工/虚拟成本基数，排除于库存位置和需求训练/回放；这不能推成当前所有赛狐余额均非真实。每个来源按日期、仓、SKU、库存类型做数据血缘，并由业务确认实际可售/冻结/质检/调拨/在途含义。
- ERPNext 生产数量需区分首道工序完成、末道工序完成、已提交的成品入库凭证；只有可用库存/入库状态经业务口径确认后才计入成品供给，首道工序完成不能当可用成品。当前“已生产/在制/仓库”口径存在资料冲突，仓库 owner 与生产 owner 尚待裁定；在裁定前单列待核实量，不做可用库存净额抵扣。
- 根仓库没有提供待审计销售数据与历史预测；没有用未验证的数据状态填补缺口。对其他历史结论只搜索到哪里、没搜索到哪里，需列明查询路径，不能用 main 未发现推断不存在。
- 主 Agent 指出仓库 PR #288 `ops_assistant_demo` 展示了一个相邻的流程模式：`CAPABILITIES` 单注册表、后台角色、不可变摘要与状态版本、审批有效期，以及执行后独立读回；其业务是模拟银行，不是供应链生产验证。本轮未独立审阅 PR diff，因此将它记作待审阅的本地模式参考，不能用来证明 SCM 数据/工具正确性。若沿用，重点验证状态版本和审批快照绑定、过期拒绝、提交后独立读回。

## 需求信号：销量不是无条件的需求真值

订单事实首先保留最终客户实际购买的可售 SKU（销售包装/套件）与对应数量，不把包装拆件后出现的 Cover/Foam 行重复记成独立销售需求。若 Cover/Foam 本身也被独立售卖，只计其独立订单行上的客户需求。预测成品/售卖 SKU 需求后，再依预测时点生效的 BOM 与数量单位单独展开为派生组件需求；输出必须保留“独立客户需求”和“BOM 派生需求”标记，避免同一订单既按套件计一次又按组件再算一次。取消/退货/补发不能直接作为正常销售；跨渠道、国家站点、仓库分开建维度，再按决策目标汇总。多级 SKU 家族汇总可给新品/稀疏 SKU 借力，但不应抹掉尺寸、颜色、国家站点差异。

在途缺货期间 observed sales 常受库存上限截断。将零销量编码成零需求会使模型复制既有缺货政策；候选策略要区分“可售且零销量”与“不可售/缺货/采集缺口”，记录上架、促销、断货起止和可售库存。对已确认的 censored periods，比较仅训练未删失区间、删失似然/需求上界、库存可用性特征及敏感性区间；不能从销售表单独识别未观测的流失需求。促销未来日历只有在预测起点已知时可作未来协变量；实际促销强度、补货到货延误等未来未知信息不可泄漏。新 SKU 需单列冷启动，不以成熟品回测代替。

## 候选、争议与可反驳点

| 主张 | 支持证据 | 反证/边界 | 本地检验 |
|---|---|---|---|
| 间歇需求需要专门基线 | Croston/SBA/TSB 面向非零需求间隔与大小；TSB 更新发生概率，能响应需求消失 | Croston 有偏；SKU 极少/商品生命周期变化会令单序列估计不稳；“间歇”阈值不能照搬 | 先依 ADI/CV² 与业务组分层，按月滚动，报告偏差、零预测率、库存成本、呆滞与缺货成本 |
| 概率预测有库存决策价值 | DeepAR 给相关序列输出预测分布；分位数可映射服务水平/补货风险 | 校准差或分布族不适配仍会让分位数误导；预测精度未必转成低成本 | 看 pinball、覆盖率/区间宽度、CRPS（能算时）及策略仿真成本，而非仅 MAPE |
| 时间序列基础模型值得做 challenger | Chronos/TimesFM/Moirai 展示跨域 zero-shot；Chronos-2 与 TimesFM-3 增加协变量/多序列能力 | 公开 benchmark 有域/频率错配；时序数据预训练集未知或有重叠；GIFT-Eval 的基础模型也存在长跨度、尖峰失败案例。TimesFM-3 自托管权重截至本日是非商用/非生产许可 | 逐 SKU 家族、密度、国家站、跨度、缺货率分层；冻结预训练版本，查预训练重叠可得性；生产许可作为准入条件 |
| 分层/横向信号能改善小 SKU | M5 的层级零售结果显示低层级间歇、随机性更强；共享系列方法可借相关信息 | M5 是日销量、零售门店/促销，不等于跨境长头程/BOM/多仓；聚合一致性可能牺牲 SKU 细节 | 家族/子类/站点/仓对齐底层 SKU；比较分开预测、汇总后分摊、层级协调，报告总量偏差与底层成本 |
| LLM+OR / 人工审批值得与自动策略对照 | InventoryBench 和 2026 两项 inventory-agent 预印本报告 OR/LLM/人互补；一篇发现纯 LLM 解题有“hallucination tax” | 预印本、合成/课堂场景与电商三系统生产流程不同；平均实验收益不可外推；工具/实体匹配仍可能错 | 固定输入分别跑公式/求解器、Agent 草案、人单独和人+Agent；盲化审批实验并计错单、覆盖、延迟和修改理由 |
| Tool calling + HITL 可压低动作风险 | 官方工具调用文档强调结构化输入/输出、应用侧权限校验、幂等与高影响动作审批 | JSON schema 只保证形状，不保证事实正确、业务语义正确或工具返回新鲜 | 单独做权限矩阵、重放/重复调用、部分失败/超时、过期快照、恶意字段与越权写入测试；默认只读 |

**SOTA 观察截至 2026-10-20：** TimesFM-3（Google 官方 2026-08）与 Chronos-2（Amazon Science 2025）是应纳入近期候选的原生多序列/协变量型基础模型；Moirai 2.0（Salesforce，2025）主打分位数和推理效率，但论文明确按独立单变量处理，不做跨变量预测。Google 官方报告 TimesFM-3 在 GIFT-Eval、FEV-Bench、TIME benchmark 上的预训练模型平均排名居前；这属于开发方报告。对照性的 2026-09 模拟预印本在 7,200 条生成序列、九类过程、12 步预注册实验中发现没有一类方法普遍获胜：AutoARIMA 在 4+季节周期的季节 ARIMA 过程比 TimesFM-3 准 21–24%，而低样本只有两个季节周期时自动季节模型会失败；模拟间歇数据上 TimesFM-3 不比简单历史/Croston 基线占优。该预印本的 25–48 步后续分析还观察到平台序列被多个基础模型预测成下滑，但作者限定其过程覆盖，部分长跨度与现实数据分析属 post hoc。此反证足以否定“foundation model 已普遍胜过统计法”的说法，不足以推断公司哪一种胜出。

许可锁定到具体 artifact：TimesFM 官方仓库截至 2026-09 README 称代码 Apache-2.0，TimesFM 权重至 2.5 仍 Apache-2.0，可继续列为可本地候选（各版本仍应核模型卡）；TimesFM 3.0 下载权重另受 non-commercial license 限制，禁止商业/生产自托管。不能把 3.0 的限制倒推到 2.5，也不能把代码许可证套给 3.0 权重。Google 托管云服务有不同商业服务条款，需单独采购/法务核验。

## Agent 工具语义、审批与恢复边界

工具层先做业务语义注册表，再开放调用：规范 SKU 与别名/后缀、BOM 及有效期、数量单位、仓库/库存类型、状态来源、权限角色、工具输入输出版本，都必须有唯一 owner 和机器可校验定义。LLM 可以解析“帮我看看 X”的意图，但规范化结果应由确定规则校验；缺 SKU 或 BOM 时走 `unknown/needs_review`，不能猜近似项。一个只读 `get_stock_snapshot` 应明确 `as_of`、仓库和库存状态；写入型 `create_production_plan` 应只接收经过验证的版本化建议 ID，而不是自然语言 SKU 和自由填写数量。

工具调用是“结构化请求”，执行者是受策略保护的 harness。OpenAI 工具文档要求应用层自行校验每次调用参数/权限，副作用工具要幂等且需高影响审批；OPA 官方文档展示了在执行前独立策略点依据工具名和参数允许/拒绝、并记录决策日志的方式。schema 有效只表示字段形状正确，不能证明 SKU 对应、库存新鲜或补货量合理。

审批单应绑定不可变计算摘要：输入数据截止时间、源记录/版本、映射/BOM 版本、模型/策略版本、forecast 分位数、库存位置、方案行、理由和审批人。用快照哈希或等价状态版本阻止“审批后库存/BOM 已变却照旧执行”；审批有效期到期时重新计算。写入失败/超时不得盲重试；应先按幂等键检查目标系统是否已产生副作用，再恢复。状态分阶段记录（已建议/已审批/提交中/已提交/已读回/失败），执行完成要从源系统独立读回实际行和数量，对差异留失败记录并人工处理。履约与 ERP 接口不支持幂等或状态读回时，先保持人工执行。

真实案例按证据强弱分级：**生产运行但非本目标决策**：AWS 客户案例称 OPLOG 首个生产 Agent 于 2025-08 上线，做多仓履约资源协调，报告决策时间降低 90%、运营成本降 30–40%、SLA +3.5pp；这是有场景和上线时间的供应商/客户自报，缺独立对照，而且不是需求预测/采购/BOM 排产。**成熟供应链预测系统但非生成 Agent**：Amazon 描述 SCOT 在数亿商品上做预测与库存分配，是成熟大规模 ML 运营的证据，不证明 LLM Agent。**产品能力描述**：AWS Supply Chain 公告提到 shortage/delay 洞察和 watchlist/人员采取行动，能参考人机协作流程，不能证明 autonomous agent 已产生业务改善。公开材料缺少足以复制的跨境长头程、删失销量或基础件 BOM 评估。详见来源账本 C-01 至 C-03。

最新结果会快速变动。本文截至 2026-10-20 已检索到 TimesFM-3 官方公告、Chronos-2 论文、Moirai 2.0 论文及一篇 2026-09 对 TimesFM-3 的模拟比较；该比较只有合成九种过程，不能证明供应链效果。没有取得完整且可复现的截至日全模型 leaderboard / 全部最新权重条款，故不宣称普适 SOTA。TimesFM-3 的 headline 是 Google 自报 benchmark；在本地应视为挑战者，不视为结论。

## 数据规范化和库存位置

预测需求事实的基础粒度建议先建日级：`销售日期 × 市场/站点 × 最终客户可售 SKU × 履约/库存仓`，保留独立售卖 Cover/Foam 等 SKU 自己的订单事实；不要把每笔组合/套件订单额外生成组件级实际需求行。另建组件派生需求表，按需求期间有效 BOM 版本将预测售卖 SKU 数量展开到组件，记录来源成品 SKU、BOM 版本、换算因子和派生数量，再按生产/采购计划汇总。事实和派生表均需有 `source_doc/line`、原始 SKU、规范 SKU、单位、促销标记、订单状态、可售状态与取数时间，避免只留转换后的总数。

对每个 SKU/仓形成一条时间线：赛狐真实可售、冻结/质检/调拨；ERPNext 首道工序完成量、末道工序完成量、已提交成品入库量、已入库/领料/出库；通途可售/订单占用；头程已发未到及预计到货区间。首道工序完成是生产进度，不是成品可用量；末道工序完成也需核对质检/入库与库存状态。系统间可能是不同时间快照，先定义唯一业务口径和截止时点，再按来源给状态标签；不要简单相加重复库存。对在途按线路、批次、最近已知状态和历史延误分布建到货窗口，而非把创建标签等同已经发货。仓库状态资料冲突待业务裁定；没有可证据区分的余额先进入“待核实”，不默认为真实可用。

BOM 需求计算需按预测成品需求乘当时计划使用的有效 BOM 数量，并处理损耗、替代料、可替代仓、MOQ/包装倍数、最小批量、交期、产能、生产节拍、资金上限。BOM 计划与实际消耗的偏差单独回测；不能把 BOM 理论量误报成确定采购数。月度财务/老板审批表要展示 P50/P90 或情景区间、库存位置扣除已确认在途、建议补货/排产量、预计缺口日期、成本/服务影响、关键假设和来源链接。

## 回测与业务指标实验

1. **数据截点**：重建至少覆盖多个季节/促销周期的“当时可知”快照；每个起点只用当时已存在的销售、促销计划、库存、BOM/别名版本及订单/到货状态。按月扩展滚动起点，训练窗扩展或固定长度均留档，测试未来 1/2/3/6 月（如数据覆盖允许）。最近月份成熟度/退款迟到需右删失处理。
2. **对照组**：简单季节朴素和去年同期；ETS/ARIMA；Croston/SBA/TSB；业务现有规则；本地特征模型；Chronos-2/TimesFM-3/Moirai 2.0；纯 LLM 端到端；Agent 解析语义后调用固定计算/OR；人工单独、人+Agent。所有模型用同一数据切分、同一促销可知假设和相同库存策略。
3. **预测指标**：MASE/RMSSE、WAPE（聚合且注明小分母问题）、偏差；间歇层按非零命中、概率/数量双指标；分位数 pinball loss、P50/P90 覆盖率和校准曲线；分组与总量层级一致性。MAPE 不用作零销量主指标。对比置信区间而非只报一个平均值。
4. **库存回放**：用历史 lead time、MOQ/整箱倍数、补货周期、BOM 损耗、仓库间不可互换限制、计划冻结窗运行离线仿真。报告缺货天数/缺货 SKU、fill rate、逾期/取消销售代理、库存周转、平均/峰值持有成本、过期/呆滞与加急运输成本、生产加班/换线成本和现金占用；做成本权重敏感性分析。没有真实 lost-sale 标签时，清楚标作模型假设区间，不能宣称已计算实际利润改善。
5. **数据问题分层**：另报缺货删失、新品、间歇、促销、仓间调拨、包裹拆分、BOM 变更、高退货、低销量/新市场、头程延误的指标；分支测试错配 SKU/缺 BOM/重复订单/过期在途。主指标改善不能掩盖任一高风险切片恶化。
6. **Agent 正确性**：准备金标准样例，每条含规范 SKU、换算因子、库存快照时点、BOM、lead-time 情景及应有工具调用；检查抽取准确率、工具/参数选择、证据完整、数值复算一致、拒绝无权限写入、异常重试幂等、报错保留、过期数据提示、审批前后差异与最终动作一致。提示注入文本不能改权限。拒绝率不等于正确率。

先通过历史回测和只读试运行，再由业务确定阈值和审批范围；导入前按仓库规则确认范围，任何指标门槛由库存/财务/生产共同确定，不把模型自报置信度作为自动执行条件。
