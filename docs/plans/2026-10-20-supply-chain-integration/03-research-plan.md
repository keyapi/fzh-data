# 03 — 深度调研计划

> 目标不是写一份「技术综述」，而是回答三个决策问题：
> **① 业界成熟架构里哪些该抄？② AI Agent 现在到底能承担哪一段？③ 哪条路能用开源拼出来、成本多少？**
>
> 调研结果直接决定 02 能力地图里 P0/P1 的取舍，以及「自研 / 开源 / 采购」的比例。

## 0. 调研纪律（先读）

1. **区分事实与宣传**：厂商博客/白皮书只算「厂商主张」；结论优先引用独立评测、公开案例、
   可复现的 benchmark、GitHub 数据（stars 不等于质量）。
2. **每个结论带来源**：URL + 访问日期 + 原文关键句；写入文档时不只放链接。
3. **标注时效**：本项目在 2026-10，AI 领域 6 个月就会变；写明「截至 2026-10」。
4. **不编数字**：没有来源的效果提升/成本节省，一律写「未证实」。
5. **先小后大**：优先找**中小规模、跨境电商、多仓、多平台**的案例，而不是只看世界 500 强。
6. **可运行性**：开源方案必须看最近 release/commit、issue 活跃度、License、部署复杂度、
   中文/国内网络可达性。
7. **不重复造轮子**：先查本仓库（含未合并分支）是否已有结论，再上网。

## 1. 调研线 A：业界成熟架构与最佳实践

### 要回答的问题

1. **S&OP / IBP**（销售与运营计划）在中小企业的落地形态是什么？月度节奏、角色、输入输出？
2. **DDMRP**（需求驱动 MRP）与经典 MRP/MRP II 的差别？缓冲库存、解耦点怎么定？
   对我们的「多仓 + 长头程 + 断货频繁」是否更合适？
3. **MEIO**（多级库存优化）在「工厂 → 头程 → 海外仓 → 平台」这种链路上怎么用？
4. **APS**（高级排产）与 MRP 的边界；产能约束、换型、节假日（春节停机）怎么建模？
5. **控制塔 / 可视化**：业界成熟的控制塔看什么指标、怎么定义「异常」、如何避免告警疲劳？
6. **预测治理**：预测准确率怎么考核（MAPE/WAPE/bias/FVA）？谁对预测负责？如何回测？
7. **资金约束下的补货**：库存周转、现金占用、服务水平怎么权衡？有没有可抄的决策框架？
8. **中小跨境电商标杆**：Shein/Temu 之外的中间规模卖家，公开分享过哪些做法？

### 要看的来源类型

- 供应链经典教材/协会材料（APICS/ASCM 的 CPIM/CSCP 体系、S&OP 成熟度模型）；
- 头部厂商的**方法论**（Kinaxis、o9、Blue Yonder、RELEX、ToolsGroup、SAP IBP、Anaplan）——
  只看方法论与产品能力清单，**不要把营销话术当证据**；
- 独立分析机构/学术综述（IJPE、JOM 等）与公开案例；
- 国内跨境 ERP/服务商的公开方案（领星、积加、店小秘等）—— 了解本地化实践。

### 产出

`05-research-a-industry-practices.md`：

- 一张「方法 → 适用条件 → 我们是否适用 → 落地成本」表；
- 3~5 个可直接抄的做法（含模板/指标定义）；
- 明确排除项（为什么不用）。

## 2. 调研线 B：AI / Agent 的 SOTA 与可落地边界

### 要回答的问题

1. **时间序列基础模型**（2026 年现状）：Chronos / TimesFM / Moirai / TimeGPT / Lag-Llama 等，
   在**稀疏、间歇、断货删失、促销**的 SKU 级需求上，是否真的优于统计基线？
   有没有独立对比（GIFT-Eval、M5 等）？推理成本、私有化部署可行性？
2. **LLM 做需求预测**：哪些环节真的有效（特征生成、异常解释、新品类比、文本信号），
   哪些是伪需求（直接让 LLM 报数字）？
3. **Agentic 架构**：
   - 工具调用 / MCP / function calling 的成熟度；
   - 多 Agent 编排（planner-executor-critic）在数据任务上的可靠性；
   - Text-to-SQL / 语义层：如何避免「看起来对但口径错」；
   - 长期记忆与知识库（本项目已有 `enterprise-agent-knowledge-system.md`）。
4. **LLM + OR**：LLM 负责建模/解释、求解器负责优化，业界有没有可复用的模式？
5. **HITL（人在环）**：审批、纠错、反馈如何设计？如何评估「建议采纳率」？
6. **风险**：幻觉、非确定性、数据泄露、提示注入、成本失控；有哪些工程护栏（schema 校验、
   双跑对拍、回放、评测集）？
7. **真实落地案例**：2025–2026 有没有公开的供应链 Agent 生产案例？效果与失败原因？

### 要看的来源类型

- 论文/benchmark（arXiv、GIFT-Eval、M5/M4）；
- 官方文档（OpenAI/Anthropic/Google 的 agent 指南、MCP 规范）；
- 开源实现的 README + issue（看真实使用问题）；
- 独立评测博客/工程团队复盘（优先有代码和数据）。

### 产出

`06-research-b-ai-agent-sota.md`：

- 「能用 AI 做 / 不能用 AI 做 / 只能辅助」三栏清单；
- 推荐架构模式（含反例）；
- 成本估算（每次跑批的 token/推理成本）与可靠性数据；
- 一个最小验证实验设计（例如：用同一品类对比统计基线 vs 基础模型 vs LLM 辅助）。

> **本项目的强假设**：AI 应该做**编排、解释、异常归因、对话取数**，
> 关键数字由确定性代码算。调研要**主动找反例**：有没有证据表明 LLM 直接参与数值决策更优？

## 3. 调研线 C：开源方案与自建成本

### 要回答的问题

1. **编排/调度**：Airflow vs Dagster vs Prefect vs 轻量 cron/脚本 —— 对 5 人团队哪个不过度？
2. **数据存储/变换**：Postgres / DuckDB / ClickHouse；dbt 是否值得引入？
3. **BI/看板**：Superset / Metabase / Grafana / 自研 FastAPI+前端；非技术同事能否自助？
4. **预测库**：StatsForecast / sktime / Darts / GluonTS / PyTorch Forecasting / Prophet；
   哪个对「多 SKU、稀疏、层级」最省事？是否支持断货删失与回测？
5. **优化**：OR-Tools / Pyomo / CVXPY；补货与排产分别适合哪种建模？
6. **ERP/计划**：Odoo、ERPNext（已在用）、OpenBoxes 等能否承担计划层？还是只做事实源？
7. **Agent 框架**：LangGraph / PydanticAI / OpenAI Agents SDK / Claude Agent SDK / MCP；
   与本仓库现有 `ai_access_poc`、`web_automation` 如何衔接？
8. **许可证与维护**：Apache/MIT/AGPL 的商用影响；最近 12 个月 release/commit；
   是否有商业公司背书；国内网络能否安装。
9. **总拥有成本**：服务器、人力、维护、升级；对比「买 SaaS」的年费。

### 产出

`07-research-c-open-source.md`：

- 一张「层 → 候选 → 推荐 → 理由 → 风险」表；
- 最小可运行组合（reference stack）与替代方案；
- 明确「不引入」的清单（避免技术栈膨胀）。

### 建议的对照组合（待验证，不是结论）

| 层 | 候选组合 1（轻） | 候选组合 2（标准） |
|---|---|---|
| 调度 | cron + Python | Dagster / Prefect |
| 存储 | SQLite / DuckDB | Postgres |
| 变换 | Python | dbt |
| 预测 | StatsForecast | StatsForecast + 基础模型 |
| 优化 | OR-Tools | OR-Tools / Pyomo |
| BI | FastAPI + 简单前端 | Metabase / Superset |
| Agent | Claude Agent SDK / MCP | LangGraph |

> 以上只是**待验证的候选**，不要写进最终方案前先跑通一个纵向切片。

## 4. 三条线共同的交付格式

每篇调研文档必须包含：

1. **结论先行**（3~5 条，直接回答「我们该怎么做」）；
2. **证据表**（主张 / 来源 URL / 日期 / 证据强度：强/中/弱）；
3. **适用性判断**（结合本公司的系统、数据、人力、预算）；
4. **反例与风险**；
5. **待验证实验**（能在 1~3 天内跑完的最小验证）。

## 5. 验收标准

- 每条关键结论都能点到来源；没有来源的写「未证实」；
- 至少给出 1 个「业界这样做但我们不该照抄」的例子；
- 至少给出 1 个「AI 不该做」的明确边界；
- 输出一份**推荐技术栈 + 理由 + 成本**，而不是罗列所有项目；
- 调研文档经过第二个 Agent 交叉审阅（见 04 的分工与评审规则）。
