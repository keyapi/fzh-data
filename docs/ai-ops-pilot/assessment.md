# 黄总《FZH AI运营试点计划 1.0》评估

> 评估对象：老板 2026-09-15 提出的《FZH AI运营试点计划 1.0 — 30天落地行动方案》（10 页）
> 评估目的：2026-09-16 面谈可行性的准备材料
> 评估人：张克勇（老板指定的「AI 负责人」角色）

## 1. 文档定位与读法

| 约定 | 含义 |
|------|------|
| `[事实]` | 可在仓库/文档/官方资料中核验 |
| `[判断]` | 基于事实的推理，可能有其他解释 |
| `[建议]` | 可被否决的行动项 |

**本文的立场**：不否定计划的框架，主张对其中 3 处做最小修改。

## 2. 一句话结论

**`C0`** 计划的管理骨架是扎实的（小范围、真实业务、人机共判、明确暂不做、G1–G4 关口），但有 **3 处假设不成立**，其中 2 处会让第 30 天拿不到计划自己定义的成果。

**`C1`** 更重要的发现：计划所要做的事，项目里**已经做了一半**，而且**正好卡在计划想验证的那一步**——见第 5 节。这不是重复投资，是合并机会。

## 3. 计划客观摘要

| 节 | 内容 |
|----|------|
| 01 管理层一页共识 | 30 天 / 6–8 人 / 4 个标准 AI 助手 / 50 分周度评分；验证「效率、质量、人才」三问题；成功定义 = 3–5 个可复用案例 |
| 02 范围与治理 | 一个 Business Workspace，每人独立账号；Owner/Admin/Member + 运营群组；资料边界排除工资/人事/银行/股权/完整财务与未授权成本 |
| 03 知识与助手 | 6 类共 30–50 份资料；4 个助手（市场与竞品研究 / 产品表达 / Amazon广告复盘 / 运营经营）；发布机制由 AI 负责人维护核心指令与知识版本 |
| 04 30 天分周行动 | W1 启动与准备 → W2 搭建与培训 → W3 实战与纠偏 → W4 固化与验收；关口 G1 第 5 天 / G2 第 10 天 / G3 第 20 天 / G4 第 30 天 |
| 05 使用规则与复盘 | 每人每周 1 个完整闭环「问题—分析—结论—行动—结果」；每周 30 分钟 AI 复盘会；4 个看板阈值（提交率 / 落地率 / 高质量案例 / 事实合规） |
| 06 周度能力评分 | 5 维 × 10 分 = 50 分；<20 分暂停独立对外使用；40+ 作为标杆案例 |
| 07 预算与暂不做 | 3 个月 1–1.5 万元；暂不做：ERPNext 深度集成/复杂接口、复杂 RBAC、外部重型知识库、全员铺开、重型咨询 |
| 08 第 30 天验收 | 6 项验收清单；进入第二阶段 3 个必要条件（稳定使用 / 成功案例 / 管理层认可）；决策 A 扩围 / B 调整后继续 / C 暂停 |
| 09 启动会确认页 | 可打印签署页，逐项确认 Owner 与截止日 |

## 4. 可取之处

| # | 具体 | 为什么值得保留 |
|---|------|----------------|
| 1 | 第 07 节「明确暂不做事项」 | **全文最有价值的一页**。列出 ERPNext 深集成、复杂 RBAC、外部重型知识库、全员铺开、重型咨询五项，并各写「何时重新评估」。这是有克制力的计划，不是愿望清单 |
| 2 | 第 01 节「不以使用次数为成绩，以输出质量和业务落地为成绩」 | 避开了 AI 试点最常见的 KPI 陷阱（用量指标会激励表演性使用） |
| 3 | 第 05 节红线「未标明来源、存在事实疑问、涉及敏感经营数据的 AI 输出，不得直接用于对外发布或经营决策」 | 与第 02 节资料边界配套，是负责任的治理设计 |
| 4 | 第 04 节 G1–G4 关口各有「放行条件」与「最晚时间」 | 有止损点，不是无限期投入 |
| 5 | 第 05 节要求记录「运营本人明确同意/修正/否定哪些内容」 | 埋下了「人机共判」可测量化的种子——见第 12 节实验设计 |

## 5. 【核心】计划与项目已有工作的三个关系

这一节是本评估最重要的部分。计划是独立起草的，**未引用项目里已有的三项研究成果**——其中一项的结论与计划的假设直接相关。

### 关系一：数据侧已有落地方案，且**正好卡在计划想验证的那一步** `[事实]`

`ai_access_poc/` 下已有三个 PoC，均为已合并状态：

| 组件 | 内容 | 状态 |
|------|------|------|
| 壳 `open_webui/` | Open WebUI + Open Terminal Docker 沙箱 + Skill `sellfox-search-term-pull` | PR #113 已合并 |
| 板 `board/` | IvyeaOps fork，赛狐只读搜索词数据集 → 出否词/收割候选 CSV | PR #116 已合并 |
| 门户 `portal/` | nginx `/chat` + `/ops` + 钉钉 OIDC | 已就绪，标注为「新专题，需确认启动」 |

技术验收 S1–S4 / B1–B6 **已绿**。2026-07-24 标定跑通快照：店铺 `TOODDLY-Daneey-US`，7 天窗口，1922 行 → 1389 唯一搜索词 → **19 条候选**（否词 17 / 收割 2）。

**当前唯一阻塞**：`ai_access_poc/board/docs/specs/ops-review-brief.md` —— 需要**运营负责人签字**（把候选分三类：可直接用 / 阈值要改 / 不适用家纺）。签字前「不得把候选当自动执行依据」。

**`C1` 判断**：老板的 30 天试点，目标正是「让运营真的用起来并验证方法是否成立」；而既有 PoC 卡住的正是同一个环节。**计划的 W3「实战与纠偏」与既有的「运营审」是同一件事。**

> **这意味着：广告复盘助手不是从零开始，而是把已卡住的 PoC 推过运营审。** 这应该是第 30 天最容易拿到的那个「成功案例」。

### 关系二：`advertise/` 不能当已验证资产——此结论**在项目内已经做过了** `[事实]`

`docs/research/2026-07-24-unified-ai-access-independent-review.md` 的 `revision_note` 与 §8.1 明确记载：**撤销「advertise/ 已验证」论据**；`advertise/` 仅可作「列名映射试验、赛狐 xlsx 形状样本、脚本骨架参考」。

同文档 §8.2 另有一条**硬约束**：**赛狐广告无写 API**——拉报告 ✅、读实体 ✅、创建/修改广告/否词下发/改竞价预算 ❌（用户确认 + 文档无 put/create 路径）。

**`C2`**：因此对广告侧，「不做写回」**不是取舍，是当前技术条件下的必然**；且分析结论的可信来源应转向**运营专家本人**，而不是脚本输出。

### 关系三：2026-09 复核后，ChatGPT Business 已可作为「前台 + 工具编排层」 `[事实]`

上游裁决（2026-07-24）的选型权重排序为：Level A 可落地（×5）> 有手脚/能连赛狐 API 与执行代码（×4）> 维护者不绑死个人（×4）> 桌面+Web 知识同源（×3）> 4C8G 可部署（×2）> OIDC/RAG（×1）。最终推荐 **C′ 门户融合**（OWUI 壳 + IvyeaOps 板 + nginx + 钉钉 OIDC）。该裁决当时**没有评估 ChatGPT Business**，因此不能直接拿来支持或反对老板的载体。

2026-09-16 的官方资料复核补上了这个真空：ChatGPT Business 已提供 **Workspace Agents、Company Knowledge、共享发布，以及管理员创建/发布远程 MCP app**；MCP 可暴露搜索、读取和写操作。故 Workspace 并非天然「连不上赛狐、不能用工具」，但仓库脚本也**不能原样上传后执行**——必须先封装为远程 API/MCP tool 或受控工作流。详见 [assistant-platform-research-2026-09.md](assistant-platform-research-2026-09.md)。

**`C3` 判断**：老板选的 ChatGPT Business 可以做运营的低门槛统一入口；项目已有 PoC/脚本应转为其背后的只读工具层。推荐「**ChatGPT Workspace Agent 前台 + Git 真源 + FZH MCP 薄适配层**」，而不是让运营直接使用 Git/CLI，也不是立即再启一套 Open WebUI 主入口。

边界仍要说清：Business 的连接器治理弱于 Enterprise；首期只做自有、只读、窄接口，赛狐广告写回仍然不存在。

### 三个关系的合并含义

```
老板的 30 天试点           项目已有的 PoC
├── 缺：数据手脚  ────────→  ✅ 已有（壳+板+门户，技术验收绿）
└── 有：运营使用机制  ────→  ❌ 缺（卡在运营审 + Portal 待启动）
                            ↑
                 两者互补，合并即可闭环
```

## 6. 三个结构性问题

### `P1`「4 个标准 AI 助手」没有定义——计划最大的空洞

**`[事实]`** 计划第 03 节只给了 4 个助手的**名称**、要求它们各有一个「标准输出」和「业务 Owner」，并规定「AI 负责人维护核心指令与知识版本」。**全文没有说明「助手」的载体是什么。**

候选载体有两类，性质完全不同：

| 维度 | ChatGPT Workspace Agent | 仓库内 skills + docs + scripts（工程真源） |
|------|-------------------------|--------------------------------------------|
| 载体 | 平台内的 instructions/skills + Company Knowledge + apps/tools | Git 仓库内的 `SKILL.md` / `docs/` / 脚本 / schema / 测试 |
| 版本管理 | 平台内发布；Business 的工具更新与细粒度治理弱于 Enterprise | git diff / PR / 审批，适合保留权威版本与审计记录 |
| 谁能维护 | Owner/Admin 配置与发布，成员使用 | 任何获授权者可提 PR，技术与业务 Owner 可分工审核 |
| 运营使用门槛 | 低（浏览器打开即用） | 高（若直接使用则需 Agent、uv、git） |
| 能否连赛狐 / 执行代码 | **可调用远程 MCP/API 工具**；但不能把本地仓库或上传的 `.py` 当生产运行时 | **能承载和测试代码**；但需封装为窄 API/MCP/受控工作流后才能给 Workspace 调用 |
| 适合承担的角色 | 运营统一入口、知识检索、任务编排 | instructions、代码、schema、测试与版本记录的 source of truth |
| 失效模式 | 资产只留平台形成孤本；Business 发布与权限治理不足；工具接口过宽 | 直接暴露给运营导致技术门槛过高，使用率低 |

**`[判断]` P1 的严重性**：计划第 04 节的 G2 关口要求「4 个助手 V1 发布，知识关键事实抽测通过」——**如果「助手」没定义，这个关口无法验收**。第 08 节的验收清单同理。

**`[事实]` 另有一条会直接影响 G2 设计的已验证结论**：`docs/non-tech-team-agent-guide.md` 明确写道——**「AGENTS.md 的规则是概率性的，不是绝对强制执行。Agent 会根据上下文权衡，不是你写什么它就一定照做。」**

**`[判断]`** 因此「关键事实抽测通过」不能设计成一次性的放行测试，而应是**每次使用时的持续校验**（计划第 03 节的「红线」正是这个意思，两者应合并表述）。

### `P2` 数据可得性，与「暂不做集成」的表述冲突

**`[事实]`** 计划第 03 节要求「广告复盘助手」和「运营经营助手」分别产出「诊断树 + 优先级 + 下周动作」与「经营判断 + 风险 + 行动计划」。这两件事都需要赛狐数据（广告报告、订单、库存）。

而计划第 07 节把「ERPNext 深度集成 / 复杂接口开发」列入**暂不做**，理由是「使用场景与数据口径尚未验证，易先做系统后找需求」。

**`[判断]` 方向正确，但表述粒度太粗。** 该排除的是**写回**与**复杂集成**，不应连**只读的最小导出**一起排除：
- 写回本来也做不了（赛狐广告无写 API，见关系二）
- 只读最小导出**无需新开发**——既有 PoC 已经跑通（见关系一）

**`[建议] R2**：把第 07 节该项细化为「**不做写回、不做复杂集成；允许只读、单店铺、最小范围的数据导出**」，并注明已有可复用实现。这不是推翻「暂不做」的精神，而是让它可执行。

#### 附：外部市场/竞品数据要花钱，不是配置问题

计划第 03 节要求「市场与竞品研究助手」产出市场容量、竞品、价格带、人群、评论、机会点。

| 数据源 | 实际状态 `[事实]` | 影响 |
|--------|-------------------|------|
| ERPNext / 赛狐 / 通途 / Google Sheets / 承运商 | 已接通 | **全部是内部数据**（订单/库存/成本/广告/物流） |
| 卖家精灵 | **仅作网页工具在用；MCP 未开通**（较贵，未采购） | 需重新采购并论证必要性 |
| Sorftime MCP | 某运营同事**个人**试用一个月，已到期 | 公司无相关计划 |
| 优麦云 | 历史广告+销售，**仅 Excel 导出、无 API** | 且不含竞品情报 |

**`C4`**：这是 4 个助手里**唯一需要新增采购、且必须先行证明必要性**的一个。计划第 07 节预算（1–1.5 万）只覆盖席位与资料整理，**没有「数据源/工具」这一行**。

**`[判断]`** 无数据源时，「市场与竞品研究助手」只能靠运营手工整理竞品页面——那不是研究助手，是把手工活换个界面。

### `P3` 30–50 份知识资料的工作量被严重低估

**`[事实]`** 计划第 03 节列了 6 类资料，第 04 节要求 **W1 交出「30–50 份资料清单含 Owner/版本」**，**W2 完成「导入并校验知识」**。项目现状：

| 计划类别 | 项目现状 |
|----------|----------|
| ④ 关键词/广告复盘方法 | ✅ **有，且超出资料范畴**：`advertise/docs/` 20+ 篇字段口径、官方文档核对、方法论文档 + 可运行脚本；但方法结论未经运营验证 |
| ② 优秀 Listing 案例 | ⚠️ 仓库内仅见 1 个户外沙发完整案例（`advertise/参考文档/`）；NAS 是否还有案例需盘点 |
| ① 产品资料 | ⚠️ **不是“基本为零”**：NAS `/产品信息/` 已按 ERPNext 物料组建立 404 个目录，标准子目录含「调研报告 / 设计稿 / 图片 / 视频」；历史资料可能存在，但格式、完整性、Owner、时效与事实可信度未盘点 |
| ③ 市场调研模板/历史调研 | ⚠️ 产品研发人员过去可能在 NAS 留有 PDF、Excel 等调研材料；当前未形成统一模板，也未核实可解析性、重复与失效情况 |
| ⑤ 图片与页面表达原则 | ❓ 未确认是否有独立规范；NAS 有图片/设计稿目录只证明素材容器存在，不证明已沉淀表达原则 |
| ⑥ 新品冷启动 SOP | ❓ 当前仓库未找到，是否存在于 NAS 或其他业务目录需由运营 Owner 核实 |

**`[事实]`** `nas_itemgroup_folders/` 已有只读扫描脚本，可统计路径、文件数、大小与最后修改时间并保存快照。这提供了 W1 盘点的技术基础，但**目录存在 ≠ 资料完整 ≠ 可直接进入知识库**。

**`[判断]`** 原计划把两件不同的工作压成了一个数字：一是发现和盘点历史资产，二是把资产清洗、定责、验证并发布成模型知识。即使 NAS 已有 30–50 份文件，也不能据此认为 W2 可直接「导入并校验」。①③⑤⑥ 都需要产品/视觉/运营负责人参与，不是 AI 负责人一个人能完成。

**`[建议] R3**：W1 的交付物改为「**资料资产与缺口表**」——至少记录物料组/路径、文件类型、数量、Owner、最后更新、是否可解析、是否重复、敏感性、是否可进入知识库及缺失项。首期只抽样 1–2 个产品族，并优先使用已确认的 ④ 与一个 ② 案例；不做 NAS 全盘 OCR，也不把文件数量等同于知识质量。

## 7. 项目现状盘点

**`[事实]`** 本项目（fzh-data）主要是**工程/执行仓库**；运营原始资料另有 NAS 容器，但尚未形成可直接发布给 Agent 的受控知识库：

| 项 | 数量/状态 |
|----|-----------|
| `.agents/skills/` | 约 52 个，其中约 50 个是数据导入/执行类（stock-init、item-cost、item-weight、category、multi-attr、warehouse-restock、erpnext-item-create、sellfox-*、tongtool-*、missing-products、对账类…） |
| `docs/solutions/` | 约 74 篇，绝大多数是架构/集成/工作流/工具决策 |
| 运营策略类资料 | 仓库内主要是 `advertise/docs/`（广告口径与未经运营验证的方法）+ `docs/ai-for-amazon-ops-2026.md`（分享稿） |
| 产品研发原始资料 | NAS `/产品信息/` 已有 404 个 ERPNext 物料组目录及标准子目录；内容数量、质量、版本与可用性待盘点 |
| 已接通数据源 | ERPNext（生产 REST / 测试 fac MCP）、赛狐 OpenAPI、通途 ERP2.0、Google Sheets、FedEx/UPS/GLS |
| 外部市场/竞品数据源 | **0** |

**`[判断]`** 这解释了 P3：工程仓库天然擅长数据一致性和执行；NAS 天然保存原始业务材料，但两者之间还缺「盘点—清洗—Owner 确认—选择性发布」这一层。**不能因为 Git 里没看到就断言资料不存在，也不能因为 NAS 有文件就断言知识已就绪。**

## 8. 计划与已有硬结论的对照

以下四条在上游文档中已有证据，计划若与之冲突需专门说明理由：

| # | 已有结论 | 来源 | 对计划的影响 |
|---|----------|------|--------------|
| 1 | 混合架构：确定性路径（脚本/模板/规则引擎）与 AI Agent 应分工，各管一段 | `docs/non-tech-team-agent-guide.md` §4.4 | 广告报告处理属**确定性层**，不该让 Agent 每次重做。支持「数据管道与助手分工」，反对把取数也交给助手 |
| 2 | Excel/表格类 Agent 在复杂任务上准确率约 **57%**（SpreadsheetBench），需人工监督 | 同上 §4.3 | 计划「人机共判」正确且必要；但抽检强度必须够，不能只靠自觉 |
| 3 | 自进化 Skill 会**固化「看起来对」的错误**（V2EX 实测：第 7 天自动合入半成品 PR） | 同上 §4.1 | 计划第 04 节「助手/知识 V1.1」的迭代**必须有审核门**，不能自动生效 |
| 4 | 所有「团队共享 Memory」产品都不是装上就能用的现成方案 | 同上 §6.3 | 计划第 07 节「外部重型知识库系统暂不做」**是对的**；「Git + docs + skills」是已验证答案 |

## 9. 对「AI 负责人」角色的承接建议

**`[事实]`** 计划第 02 节给 AI 负责人的责任是「定方向、定资源、主持第 30 天决策」，交付物是「平台配置、助手版本、使用支持」；第 04 节另有「每周一页数据快照」「修订清单」。用户明确表示**精力有限**。

**`[建议]`** 把精力约束写成设计约束，主动划分认领边界：

| 归属 | 内容 |
|------|------|
| **认领** | ChatGPT Workspace Agent 的平台与发布机制；FZH 只读 MCP/API 薄适配层；只读数据导出（复用既有 PoC）；Git 中 instructions/schema/脚本/测试的技术真源；培训中「工具怎么用」部分 |
| **部分认领 / 需协同** | NAS/ERPNext 资料资产盘点的技术扫描与字段设计；每周数据快照（可与运营负责人的周复盘合并，不单独产出） |
| **不认领** | Agent 的**业务内容与事实确认**（产品事实、视觉规范、冷启动节奏）；周度评分；第 30 天业务质量签字 |
| **无人接会掉的项目** | 历史资料的业务 Owner 与有效性确认；「助手」的日常业务维护 Owner；运营审的召集人 |

**`[判断]`** 若无人接「助手维护 Owner」，「AI 负责人」会变成 4 个助手的长期保姆——而上游裁决已把「维护者不绑死在个人」列为 ×4 权重标准。这一点应在会上明确。

## 10. 反提案

| # | 改什么 | 为什么 | 改成什么 |
|---|--------|--------|----------|
| `R1` | 第 03 节「4 个助手」 | 无载体定义则 G2/第 08 节无法验收（P1） | 每个助手先定义四要素：**载体 + 输入输出边界 + 业务 Owner + 验收口径**；且**首批只做 2 个**（建议：**广告复盘** + **产品表达**），第 3–4 周视情况加。**明确暂缓「市场与竞品研究」**——它是唯一需新增采购且必须证明必要性的（C4） |
| `R2` | 第 07 节「暂不做集成」 | 表述过粗，会连只读导出一起排除，导致两个数据侧助手落空（P2） | 细化为「**不做写回、不做复杂集成；允许只读、单店铺、最小范围的数据导出**」，并注明已有可复用实现 |
| `R3` | 第 04 节 W1 交付物 + 第 08 节成功案例判据 | 历史资料可能在 NAS，但未盘点、清洗和确认，不能按文件数直接导入（P3）；成功案例判据偏感觉 | W1 改交「**资料资产与缺口表**」，只抽样 1–2 个产品族并记录 Owner/时效/可解析性/知识库准入；第 08 节增加一条硬判据：**至少 1 个助手产生可量化的业务变化**（ACOS / CTR / CVR 前后对比），不只靠「管理层感受到提升」 |

**为什么不推翻计划**：计划的三项验证问题（效率 / 质量 / 人才）与「人机共判」原则方向正确。`R1`–`R3` 是把不可执行的表述改成可执行、可验收的表述。

## 12. 可选实验设计：运营自产 vs 既有脚本方法

**`[建议]`** 对同一个任务（建议选广告复盘），做**对照实验**：

| 组 | 做法 |
|----|------|
| A 组 | 运营**先用 ChatGPT 自行产出方法与结论**（不给我们的脚本与文档） |
| B 组 | 同期跑既有 `advertise/` / board PoC 的输出 |
| 对照 | 由运营负责人评估两组的质量、耗时、可执行性；结论入库 |

**为什么值得做**（三条理由，均为方法论层面）：
1. 计划第 01 节把「**人才：哪些运营具备 AI + 经营思维，能判断、修正并落地 AI 建议**」列为三大验证问题之一。**若 AI 先给出答案，就测不出人的判断力。** 先让运营自产，是有方法论依据的，不是谦让。
2. 计划第 05 节已要求记录「运营本人明确同意/修正/否定哪些内容」——本实验正是这条的可测量版本。
3. 它同时回答了 `advertise/` 与 board PoC 的**方法本身是否成立**（上游 §7 建议的下一步原话是：「用运营负责人校验『规则引擎方法论』本身……**不要**拿未验证的 `advertise/` 输出当真理」）。

**`[判断]`** 这个实验的成本很低（不新增开发），但能同时产出第 30 天需要的「可量化案例」和「方法是否成立」的答案。**建议作为 W3 的一个专项。**
