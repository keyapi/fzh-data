# AI 运营试点计划 — 落地配套建议

> **给黄总**：第 1 节是人看的结论，两分钟读完。
> **给 Agent**：第 2 节起是编号条目，可按第 3 节的回执协议逐条回复。
> **本文不改变计划的范围、目标与时间表**，只补充「让计划自己的关口能判达标」所需的条件。

## 1. 给黄总的一页

计划框架没问题，可以照跑：30 天、6–8 人、一个 ChatGPT 工作区、小范围真实业务、人机共判、明确暂不做、四道检查关口（计划里叫 G1–G4，分别在第 5、10、20、30 天）——这几条都建议原样保留。

只有 3 件事建议在启动会上定一下。它们有个共同点：**不定，卡的不是「能不能做」，而是「计划自己的验收关口没法判达标」。**

**一、4 个助手的「形态」先定一下。**

计划给 4 个助手起了名字，也在第 10 天设了一道检查关口（计划里叫 G2），要求「4 个助手 V1 发布、知识关键事实抽测通过」。但「助手」具体是什么形态——是 ChatGPT 里的助手，还是仓库里的技能加文档——计划里没有写。

形态不同，**能不能读到赛狐数据、由谁维护、怎么算通过**，答案完全不一样。这个不定，第 10 天那道关口就没有判据。

**二、「市场与竞品研究助手」的外部数据，可能是个缺口。**

内部数据（ERPNext / 赛狐 / 通途 / 物流）都已经接通；但外部市场与竞品数据目前还没有来源：卖家精灵只用了网页版，MCP 未开通；Sorftime 是同事个人试用一个月，已到期。这类外部数据能力通常需要单独开通，并有一定费用。

建议先把它列为一个待确认项。在开通之前，这个助手可以先做成「研究流程模板」，不承诺市场容量这类数据结论。

**三、资料清单改成「先盘点，再导入」。**

计划要求第一周（计划里叫 W1）交出 30–50 份资料清单、第二周（W2）完成导入校验。实际情况是：NAS `/产品信息/` 下已经按 ERPNext 物料组建了 404 个目录，历史的产品设计稿、调研报告很可能就在里面——但格式不统一（PDF / Excel / 图片），没有指定负责人，没有版本，也没有人确认过还准不准。

**有文件不等于知识已经能用**，30 多份一周内整理完不现实。建议第一周先交一份「资料资产与缺口表」，先抽 1–2 个产品族看看。

一句话：**这三条不是否决计划，是让计划自己的关口能判达标。**

## 2. 补充条目（供 Agent 逐条核对）

### R1 · 助手先定义四要素，再谈发布

| | |
|---|---|
| **问题** | 计划第 03 节只给了 4 个助手的名称。第 04 节 G2（第 10 天关口）要求「4 个助手 V1 发布，知识关键事实抽测通过」；第 08 节验收清单同理。**没有定义就无法验收。** |
| **建议** | 每个助手写清四要素：**载体 / 输入输出边界 / 业务 Owner / 验收口径**。发布分两批：先跑通 2 个，第 3–4 周视情况补齐另外 2 个。 |
| **依据** | 载体决定能力边界。2026-09 官方资料复核：ChatGPT Business 现已支持 Workspace Agents、Company Knowledge 和管理员发布**远程 MCP app**，所以「平台内助手」并非天生读不到赛狐数据——但必须先把手上的脚本封装成**远程只读工具**，**仓库脚本不能原样上传运行**。这个区别不写清楚，G2 的「抽测通过」无法设计。 |

### R2 · 「暂不做集成」的粒度要细化

| | |
|---|---|
| **问题** | 第 07 节把「ERPNext 深度集成 / 复杂接口开发」列入暂不做。方向正确，但表述过粗——会连**只读导出**一起排除，导致「广告复盘」和「运营经营」两个数据侧助手无数据可用。 |
| **建议** | 改为「**不做写回、不做复杂集成；允许只读、单店铺、最小范围的数据导出**」。 |
| **依据** | 写回本来也做不了：**赛狐广告目前没有写 API**——拉报告、读实体可以；否词下发、改竞价预算不行。所以「不做写回」是当前技术条件下的必然，不是取舍。把这条写进计划，反而能避免第 30 天被追问「为什么没自动执行」。 |

### R3 · W1 交付物改为「资料资产与缺口表」

| | |
|---|---|
| **问题** | 第 04 节要求 W1 交 30–50 份资料清单、W2 导入并校验——排期不成立。现状：广告方法类资料已有且超出资料范畴；产品资料、市场调研材料**可能存在**于 NAS，但未盘点；图片/页面表达原则、新品冷启动 SOP 是否已有，需业务侧确认。 |
| **建议** | W1 交付「**资料资产与缺口表**」，字段至少含：物料组/路径、文件类型、数量、Owner、最后更新、是否可解析、是否重复、是否含敏感信息、能否进知识库、缺失项。**先抽样 1–2 个产品族，不做全盘 OCR。** |
| **依据** | 这里其实压着两件事：一是发现和盘点历史资产，二是把资产清洗、定责、验证、发布成模型知识。第二件必须产品 / 视觉 / 运营负责人真正投入，排进 30 天内不现实。另外，「关键事实抽测通过」不应设计成一次性放行测试，而应是**每次使用时的持续校验**（与第 03 节的红线是一回事，建议合并表述）。 |

### R4 · 每个助手要有业务 Owner，且落到具体的人

| | |
|---|---|
| **问题** | 计划第 03 节写「AI 负责人维护核心指令与知识版本」。若只有技术侧维护，四类业务内容（产品事实、表达规范、冷启动节奏、广告规则）无人负责，助手会在第 30 天前退化成空壳。 |
| **建议** | 每个助手明确两类责任：**业务 Owner**（内容与规则：产品事实 / 表达规范 / 广告规则 / 经营口径）与**平台维护**（载体配置 / 只读工具接口 / 发布机制 / 版本管理）。 |
| **依据** | 计划第 01 节把「人才：哪些运营具备 AI + 经营思维，能判断、修正并落地 AI 建议」列为三大验证问题之一。**若助手的业务内容没人负责，第 30 天就分不清是「工具不好用」还是「内容没人维护」**——两个验证问题会同时测不出来。 |
