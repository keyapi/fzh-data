# 工单驱动的渠道接入办理助手

> 全部业务、工单、规则、地址与结果均为模拟；不接 ERPNext、不连真实银行系统、不发外网请求。

## 一句话

把一份有旧模板、漏项与重复注册风险的渠道接入工单，变成**可核对、可执行、可恢复**的跨页办理结果。

## 痛点与目标用户

渠道接入测试环境办理要跨三页（终端注册、注册参数、固定 IP）。现有表单只解决「填」，真正的难点在判断：

- 工单里往往夹带**过期模板值**（并发 8、同步回调、超时 30、重试 2），与现行规范冲突；
- 同代码终端**可能已存在**，直接照办会重复创建；
- 材料常常**缺一项**（如客户端实际监听端口），需要问人而不是猜；
- 参数、IP 与终端三页互相约束，人工逐项改**容易漏、难复核、不可恢复**。

目标用户：科技运营/渠道接入经办岗。他们手里已有工单和制度，缺的是**把三者对齐并把整组变更一次办对**的助手。

## 主线流程

```
用户只给一份工单
   ↓
Agent 读工单 + 版本化知识 + 当前三页状态
   ↓
发现：已有终端（复用）/ 旧模板冲突 / 真正缺项
   ↓
只追问不可推断的一项（客户端端口）
   ↓
跨三页组成整组最小变更方案（每字段带可核查来源）
   ↓
用户一次确认 → 后台原子执行 → 独立读回 → 本地模拟验收
   ↓
失败变体：保存成功但验收失败 → 生成完整逆向恢复方案 → 再确认恢复
```

## 架构与分工

| 层 | 职责 |
|---|---|
| 模型（真实） | 理解工单、检索规范、选规则、组织整组操作、解释依据。**没有执行工具。** |
| 后台（确定性） | 身份/岗位、任务范围、来源有效性、字段级值与版本精确匹配、整组完整性、原子事务、独立读回、模拟验收、恢复 |
| 前端 | 工单选择、四步进度、事实卡、三页预演、整组确认卡、验收报告、刷新恢复 |

四种模型工具：`read_task_context`、`search_task_knowledge`、`ask_task_question`、`prepare_task_plan`。
**执行只能由后台在人工确认后完成**，模型不能调用。

## 创新点

1. **从「代填」到「办理」**：用户不必知道参数，助手从工单 + 规范 + 现状推导，并主动指出冲突与缺项。
2. **字段级证据绑定**：每个变化值都必须引用后台登记的 evidence id，且经「属于本任务 / 版本有效 / 允许目标 / 值与类型精确相等 / 档位与环境匹配」逐项核验，杜绝编造来源、照搬旧模板、跨字段借数。
3. **一次确认的整组事务**：三页 5 项操作在一个事务里提交，失败整体归零；摘要绑定确认内容，防旧确认重放。
4. **保存 ≠ 通过**：提交后从 SQLite 独立读回，再跑本地模拟契约测试，明确区分「保存成功」与「验收通过」。
5. **可恢复**：验收失败可生成完整逆向方案（含删除本任务新增的参数），仍须再确认，且不覆盖他人后续修改。

## 局限（不隐藏）

- 全部模拟；模拟验收是本地确定性逻辑，不是网络连通性或生产认证。
- 身份是 `workspace + role` 模拟主体，不是 SSO / 双人授权。
- 工单为内置结构化文本，未做任意 PDF/OCR 解析。
- 知识检索返回全部模拟文档，未做向量检索。
- 未测人工基线，故不报效率数字。

## 推广路径

1. **当前 POC**：模拟三页 + 模拟工单 + 真实模型，验证「工单 → 判断 → 受控执行 → 验收」闭环。
2. **接入真实前端**：把三页换成真实渠道管理系统的读写 API，任务层不动。
3. **接入真实身份与审批**：SSO + 双人复核 + 工单系统对接。
4. **扩展场景**：同一编排可复用到其它「多页关联 + 版本化规范 + 需要验收」的运营办理（如限额、密钥轮换、路由变更）。
